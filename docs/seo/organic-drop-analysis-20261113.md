### 3.4 `/?lang=en` 302 판단: **유지(코드 변경 없음)**
- [근거] 도착 페이지는 200이고 정규 URL이 파라미터 없는 주소다(`/en/?lang=en` → canonical `/en/`, `/ggulggul/?lang=ko` → canonical `/ggulggul/`). `?lang=` URL은 사이트맵에 0개다. 수집 원자료(GSC·네이버·Bing)에서 `/?lang=en`은 GSC '크롤링됨-색인 안 됨'의 1건(마지막 크롤링 2026-08-15)뿐이다.
- [근거] 같은 분기가 명시 쿠키 선택도 처리한다. 쿠키로 정해지는 이동은 요청마다 달라지므로 302여야 한다. `?lang=`의 쿼리 보존은 결제·OAuth 복귀와 앱 입력 때문에 의도된 동작이고, 기존 테스트 2곳이 그 계약을 지킨다.
- [추론] 301로 바꿔도 크롤러에게 이득이 거의 없다(색인 대상이 아니고, 도착 페이지의 canonical이 이미 신호를 모은다). 반면 계약을 바꾸는 위험이 있다. 그래서 바꾸지 않았다.
- 후속 제안(사용자 판단): 내부 링크가 리다이렉트를 거치지 않게 하는 쪽이 이득이 더 크다. `app/yeongnyangi/layout.tsx`·`LocalizedFortuneHome.tsx`의 `/?lang=${locale}` 링크와 `LocaleSwitcher`의 대안 `/?lang=` 링크를 도착 URL(`/en/`, `/ggulggul/` 등)로 바로 거는 것이다. UI 링크 변경이라 이번 단계에서는 하지 않았다.

- 별개 관찰: 아직 생성되지 않은 미래 날짜(예: `/fortune/date/2026-11-14/rat/`, 11/13 기준 내일)도 404 대안으로 `/fortune/today/rat/`에 **301**된다. 다음 날이면 200이 되는 URL에 영구 이동을 주는 셈이다. 내부 링크가 없으면 영향은 작지만, 302로 바꾸거나 내일 URL로 보내는 편이 맞다. 손대지 않았다(§6).

## 7. 사용자 결정이 필요한 것과 후속

- `/fortune/date/*` noindex: 권고는 A(유지)다. 되돌리려면 사용자 승인이 필요하다.
- `/?lang=` 내부 링크를 도착 URL로 바로 바꿀지(§3.4).
- 미래 날짜 URL의 301 → 302 또는 내일 URL로 보내기(§4 별개 관찰).
- 해외 IP 운영 실측은 하지 못했다. 필요하면 해외 출구(VPN 등)로 `/`, `/fortune/`, `/fortune/tomorrow/rat/`를 다시 확인한다.
