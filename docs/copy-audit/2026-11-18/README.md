## sepia 핵심 (발췌)

- 진단 없이 바꿔 말하기만 하면 AI 흔적이 오히려 더 잘 보인다. 결함 목록부터 만든다.
- 고칠 때는 교체 74% / 삭제 18% / 추가 8%. 의심스러우면 덜어낸다. 더 밋밋한 말로 바꾸는 것은 개선이 아니다.
- 반대 극단을 겨누지 않는다. 모든 신호를 뒤집으면 그것이 새 지문이 된다. 평범한 문장, 덜 다듬은 문단은 남긴다(slack).
- 한 작품에 사람 쪽 수법을 3~5개만 고르고, 드문 구조 선택은 정확히 1개만 둔다.
- 소설 진단 축 (rubric 5그룹)
  - A 주제 과잉: 화자가 주제를 직접 설명함, 대사가 철학 토론이 됨
  - B 감각·신체 과연출: 감정을 신체 감각으로만 처리, 배경이 심리를 비추는 거울
  - C 구조 매끈함: 인과가 한 줄로 이어짐, 주인공 선택과 내적 수용으로 해결
  - D 사람 쪽 표지
  - E 시간 구성
- 담론: 문단마다 암묵적 질문이 "무슨 일 → 왜 → 결과 → 의미" 순서로 줄줄이 이어지는지 본다. 끝을 성찰 꼬리로 맺는지, 비교·반박·여담이 하나도 없는지, 중반부가 처지는지도 본다.
- 표면 (style-pass §1 우선순위): 어색한 단어 > 문장 구조 > 중복 설명 > 상투어 > 구체성 부족 > 과장된 미문 > 시제 혼란.
- 증거 없이 지적하지 않는다. 지적마다 원문을 짧게 인용한다.

## 한국어 보정 규칙 (사용자 지정, sepia에 추가)

**문장 표면**

- 번역투를 걷어낸다: "~에 의해", "~로 하여금", "~을 통해", "~에 대한/대해" 남발, "~하는 것이 가능합니다", "되어지다" 같은 이중 피동, "~적(的)" 남발.
- 같은 어미(~합니다, ~입니다, ~했다)가 3번 이상 이어지면 고친다. 문장 길이를 섞어 리듬을 만든다.
- 추상어로 뭉갠 표현을 구체적인 말로 바꾼다. 예: "에너지의 흐름", "운명의 실타래", "인사이트", "여정", "깊은 울림".
- 존댓말과 반말, 호칭, 화자 톤을 한 화면·한 장면 안에서 통일한다.

**서사·스토리** (소설, 캐릭터 대사, 세계관 텍스트)

- 화자가 주제를 직접 설명하는 대사는 행동과 장면으로 바꾼다.
- 원인과 결과가 지나치게 깔끔하게 맞아떨어지면 어긋남이나 우회를 넣는다. 이번 단계에서는 제안만 한다.
- 감정을 "심장이 쿵", "숨이 멎었다" 같은 신체 감각으로만 표현하지 않는다. 판단, 행동, 말의 선택으로도 드러낸다.
- 인물마다 말투를 구분한다. 서로 같은 말투로 말하면 고친다.
- 라이트 노벨의 의도된 문체(과장, 독백, 장르 관습)와 의도하지 않은 어색함(일본어 직역체 등)을 구분한다. 의도로 보이면 유지하고, 애매하면 비고에 "의도 확인 필요"로 둔다.
- 설정, 고유명사, 사건 순서, 복선은 바꾸지 않는다. 고쳐야 한다고 판단되면 수정안 칸에 "제안:"으로만 쓴다.

## 캐릭터 보이스 기준 — design-canon 유지 (사용자 결정 2026-11-18)

정본은 `docs/context/design-canon.md`다. 요청서의 캐릭터 설정과 다른 부분은 summary의 "확인 필요"에 적었다.

- **연이 (꽃돼지 🌸)**
  - 부드러운 편지체 존댓말을 쓰고, 사용자를 "당신"이라 부른다.
  - 위로보다 답과 근거를 먼저 준다.
  - 단정적 예언과 공포 조장을 하지 않는다(비운명론).
  - 방은 꽃빛 상담실, 기능은 운명의 찻집이다.
- **네오 🦁**
  - 짧고 단정한 존댓말을 쓰고, 사용자를 "당신"이라 부른다.
  - 결론부터 말한다. 존중은 지키되 돌려 말하지 않는다.
  - 방은 별빛 전략실, 기능은 팩폭 전략실이다.
- **영냥이**
  - 기본은 반말이고, 선택적으로 해요체와 "손님" 호칭을 쓴다.
  - 핵심 판단 → 이해 → 작은 행동 하나 순서로 말한다.
  - "~냥"은 짧은 추임새에만 쓴다.
- **UI 문구** (버튼, 안내, 결제, 법적 고지): 해요체로 짧게, 행동을 앞에 둔다.
- **모든 화자 공통 금지**
  - 공포 조장
  - 확정 예언(재회, 합격, 돈, 건강)
  - 결과 보장
  - 결제 압박
  - 의료·법률·투자 판단 대행
  - 사용자를 돼지나 상담사 이름으로 부르기
  - 🌸·🦁 외의 새 장식 이모지
- **운명의 찻집 "손님"** = 십성이다. 용신·희신 계열은 좋은 손님, 기신·구신·흉신 계열은 나쁜 손님이다. 이 컨셉을 해치지 않는다.

## 유료 기능 문구 기준 (C)

- 컨셉 있는 분위기보다 **읽자마자 뭘 해주는지 아는 설명**이 먼저다. 분위기가 설명을 가리면 안 된다.
- 기능마다 코드를 읽고 실제 동작을 확인한다. 코드에 없는 기능, 분량, 결과물은 쓰지 않는다.
- 구조
  - **한 줄 정의**: 20~35자
  - **넣는 것**: 사용자가 입력하는 정보
  - **받는 것**: 결과물의 형태와 구성
  - **이용 조건**: 결제·이용권 방식. 가격과 수량은 코드의 실제 값만 쓴다
  - **분위기 한 줄**: 선택이며, 설명 뒤에 둔다
- 쉬운 말을 쓴다. 명리 용어는 처음 나올 때 한 번만 풀어 쓴다. 문장은 동사로 끝낸다(예: "~를 알려줘요").
- 금지 표현: "100% 적중", "반드시 이루어집니다", "운명이 바뀝니다", "비책/비법/비결"처럼 결과를 보장하거나 추상적으로 부풀리는 말, 불안을 자극하는 문구. 단, 기능명 "연애 비책"은 그대로 두고 이름 변경은 제안으로만 남긴다.
- 결제 직전 화면(팝업, 버튼)에서는 **무엇을 받는지·무엇이 소모되는지**가 분위기 문구보다 먼저 보여야 한다.
- 같은 기능은 목록, 상세, 팝업, 결제 화면에서 같은 이름과 같은 설명을 쓴다. 불일치는 전부 표로 정리한다.
- 결제 실행 파일과 동결 영역 안의 문구는 수정안을 내지 않는다. "결제 파일 내 문구 — 보고만"으로 표시한다.
  - 해당 파일: `config/payment-freeze.json` 대상, `worker/payments/*`, `worker/lib/portone.js`, `app/hooks/usePayment.ts`, `app/checkout/*Checkout*.tsx`, `apps/toss/service/{billing,Checkout,PreparedCheckout}.jsx`
  - `worker/lib/paid-feature-registry.js`의 `reason`은 결제창·영수증 이름이므로 RED로 표시하고 제안만 한다.

## 불변 규칙

- i18n 키 이름은 바꾸지 않는다. 값만 수정 대상이다. 새 키가 필요하면 비고에 "새 키"로 표시한다.
- 하드코딩 문자열은 i18n으로 옮기지 않는다. 위치만 보고한다.
- 수정안은 원문 글자 수의 ±20% 안에 둔다. 넘으면 비고에 "레이아웃 ±20% 초과(n%)"로 적는다. 데스크톱 960px 기준.
- 다른 언어 파일은 수정하지 않는다. 의미가 달라지는 ko 값은 비고에 "번역 동기화 필요"로 적는다.
- 제외 대상: 테스트 픽스처, 로그 메시지, 개발자용 주석, `public/` 미러와 생성물(`*.generated.*`, `public/data/novel/`). 정본에서만 진단한다.
- 운세 엔진, `sajuAdapter.ts`, `normalizeSaju.ts`, 결제 실행 파일은 읽기만 한다.
