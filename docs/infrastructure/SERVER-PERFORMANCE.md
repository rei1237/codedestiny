- **연결 방식:**
  - 요청마다 새 MongoClient를 만든다. 요청 컨텍스트가 끝나면 소켓이 죽기 때문이다.

  - 결제 요청은 별도 클라이언트(`PAYMENTS_DB_SOCKET_LANE=1`)를 하나 더 만든다.
  - 연결에 실패하면 새 클라이언트로 다시 시도한다(`MONGO_WORKER_CONNECT_RETRIES=2`, `MONGO_PAYMENT_CONNECT_RETRIES=1`).

## 판정 규칙과 판정

Task 9 규칙이다. 규칙을 먼저 적고, 판정은 위 표의 수치로만 한다. 등급 판정(M10 vs Flex)은 [COST-OPTIMIZATION](COST-OPTIMIZATION.md#등급-판정-m10-유지-vs-flex)에 있다.

### 1. DO 연결 프록시

**규칙**

- 다음 두 조건을 모두 만족할 때만 파일럿 계획을 별도 문서로 세운다.
  - `shared [db-connect] p50 > 150ms`
  - DB를 쓰는 요청 비중 > 50%
- 파일럿 대상은 핫 라우트 1~2개의 읽기 경로뿐이다.
- 기준 밖이면 "도입하지 않음"과 수치를 기록한다.

**배경**

- 2026-09 검토에서 이미 기각됐다. mongoose 모델과 트랜잭션은 DO RPC로 돌려줄 수 없기 때문이다([yeongnyangi-paid-result-attach-503](../handoff/yeongnyangi-paid-result-attach-503.md)).
- Hyperdrive는 MongoDB를 지원하지 않는다.

**실측**

- shared p50: 90ms(표 T-2, n=7,239)
- DB 사용 비중: 46.5%(표 T-7, 7,406/15,927). 평시만 보면 48.4%다.

**판정:** 도입하지 않음.

**뒤집히는 조건**

- 운영 승격 뒤 재측정에서 두 조건이 함께 성립하면 판정이 바뀐다.
  - shared p50 > 150ms
  - DB 사용 비중 > 50%
- 그때도 하는 일은 파일럿 계획 문서 작성까지다. 착수는 승인 항목 7이다.
- 지금 값으로는 p50이 60ms(150 − 90), 비중이 3.5%p(50 − 46.5) 모자란다. 평시 비중은 1.6%p 모자라 문턱에 가깝다.

**규칙 밖의 위험**

- 이 규칙은 중앙값만 본다. 이번 장애(신규 연결 생성률)는 다루지 않는다.
- DO 같은 연결 재사용 구조는 신규 연결 수를 줄이므로, 장애 대응안 중 하나가 될 수 있다.
- 재평가는 장애 후속에서 연결 생성률 실측(serverStatus 1분 샘플링)을 기준으로 한다.

### 3. `SECURITY_DB_TIMEOUT_MS = 1000`

**규칙:** ICN 이후 첫 op p95 < 800ms이면 유지한다. 800ms 이상이면 조정안을 승인 항목으로 올린다.

**현재 설정**

- `worker/lib/security/index.js`의 코드 상수다.
  - 시도 타임아웃 1,000ms, 재시도 0
  - 동시 2, 대기 250ms
- 관리자 진입과 찻집 카운터만 3,000ms다.
- 코드 주석에 따르면 enforce 모드에서 필수 호출 제한 확인이 실패하면 503을 돌려준다. 로그·점수 기록이 실패해도 그 실패는 다른 작업으로 번지지 않는다.

**실측**

- 첫 op p95는 **미측정**이다. 가드 op만 따로 잰 로그가 없다. `[db-slow-op]`은 라우트 단위로만 집계된다.
- 측정 방법(택일):
  - 스테이징에서 가드 op에 첫 op 타이밍 로그를 붙여 tail로 잰다.
  - `[db-slow-op]` 줄에 가드 op 식별자를 남기도록 한 뒤 필터해서 잰다.
  - 둘 다 코드 변경이라 이번 범위 밖이다.

**참고 수치**

판정 입력이 아닌 맥락 자료다.

- shared 연결 p95는 전체 2,424ms, 평시 1,100ms다(표 T-2, T-3).
- 찻집 카운터 주석은 시도 타임아웃에 연결 수립이 포함된다고 적고 있다. 1,000ms 가드도 그렇다면, 연결 꼬리에 걸린 요청에서 가드가 실패할 수 있다. 1,000ms 가드에 대해서는 확인하지 않았다.
- fetch 503 823건 중 791건은 장애 창에서 났고, 연결 오류와 같은 시각이다(T-SPLIT). 가드가 낸 503이 섞였는지는 확인하지 않았다.

**판정:** 현행 유지. 판정 입력이 미측정이라 근거는 규칙의 기본값뿐이다.

**뒤집히는 조건:** 위 방법으로 잰 첫 op p95가 800ms 이상이면, 조정안(시도 타임아웃 상향 또는 연결 포함 여부 분리)을 승인 항목으로 올린다.

  2. 크론 시작 때 약 20개 태스크가 동시에 기동하면서 이벤트 루프가 경합한다.

**해석**

- 느린 연결은 거리 때문이 아니다. hello 왕복이 5ms이기 때문이다.
- 지연은 소켓 준비 단계(TLS+SCRAM 인증 구간으로 추정)에 몰린다.
- 느린 연결은 늘 조금씩 나는 것이 아니라 몇 분짜리 에피소드로 난다. 장애는 그중 가장 큰 에피소드다.
- 에피소드도 장애와 같은 연결 생성률 압박일 가능성이 있지만, 확인하지 않았다. 확인 방법은 장애 후속의 serverStatus 1분 샘플링이다.

**고객 영향**

- 연결 꼬리가 큰 라우트일수록 처리 시간 꼬리도 크다.
  - `GET /api/rpg/characters`: p95 24,175ms(표 T-1). 느린 op p50 분해에서 연결이 676ms, op가 3ms다(표 T-5).
  - `GET /api/honey/attendance`: p95 5,848ms. 느린 op p50에서 연결 693ms, op 3ms다(표 T-5).
- 두 라우트는 CF 7일 경로 집계에서 각각 31,435건, 46,790건이다(CF-PATH).
- rpg/characters는 프로필 캐릭터 카드(`js/core/profile-character-card.mjs:109`)가 부른다.

**다음 조치:** 장애 후속으로 합친다([장애 인수인계](../handoff/2026-11-01-db-connection-rate-limit-outage.md)). 연결 재사용은 요청 컨텍스트 한계 때문에 지금 구조로는 불가능하다. 구조를 바꾸는 안(DO 등)은 승인 7이다.

## 확장 계획 (임계값 → 단계)

- 임계값 중 "제안"이라고 표시한 것은 측정값이 아니라 정책 값이다. 실측 최대치의 배수로 계산했으며, 사용자가 조정할 수 있다.
- 연결·ops·CPU의 30일 값은 ATL 30일 집계(1시간 단위)다.

| 신호 | 현재(출처) | 임계값 | 단계 |
|---|---|---|---|

| 연결 거부(serverStatus `connections.establishmentRateLimit.rejected`) | 누적 31,035. 08:12~15:51Z에 +13,512(MDB2, MDB3). 같은 구간에 P1 장애 | 증가 자체 | [장애 후속](../handoff/2026-11-01-db-connection-rate-limit-outage.md): 1분 샘플링으로 시각 확정 → 요청당 연결 수 축소·재시도 백오프 → 그래도 부족하면 등급 상향 검토(승인 7) |
