## 등급 판정: M10 유지 vs Flex

**규칙**(Task 9)

- 판정 입력:
  - 30일 ops/s p95·max(Flex 상한 500)
  - 연결 수 max(Flex 상한 500)
  - 데이터 크기(Flex 상한 5GB)
  - 청구서 항목
- Flex의 제약:
  - PITR·주문형 스냅샷·Performance Advisor가 없다.
  - RPO가 24시간이다.
  - 전용 클러스터에서 내려갈 수 없다. 새 클러스터를 만들고 데이터를 이전해야 한다.
- 기본 결론은 M10 유지다.
- 이전 계획(승인 필요)은 두 조건을 모두 만족할 때만 쓴다.
  - 모든 수치가 Flex 상한의 30% 미만이다.
  - 사용자가 RPO 24시간을 받아들인다.

**실측**(ATL 30일, MDB)

| 입력 | 값 | Flex 상한 대비 | 30% 미만? |
|---|---|---|---|
| ops/s, 단일 노드 max | 47.79(노드 01) | 47.79 / 500 = 9.6% | 예 |
| ops/s, 노드 max 합 | 22.86 + 47.79 + 44.31 = 114.96 | 114.96 / 500 = 23.0% | 예 |
| ops/s, 노드 p95 합 | 19.18 + 24.96 + 27.97 = 72.11 | 72.11 / 500 = 14.4% | 예 |
| 연결 수, 프라이머리 max | 100 | 100 / 500 = 20% | 예 |
| 연결 수, 노드 max 합(동시 값이 아닌 상한) | 81 + 95 + 100 = 276 | 276 / 500 = 55.2% | **분명하지 않음** |
| 데이터 크기 | dataSize 80.5MB | 80.5 / 5,120MB = 1.6% | 예 |
| 복구 | 현재 PITR 7일 + 스냅샷 정책([DISASTER-RECOVERY](DISASTER-RECOVERY.md#rpo)) | Flex는 PITR 없음, RPO 24시간 | **제약 충돌** |

**판정:** M10 유지. 다음 두 가지가 근거다.

- 복구 제약과 충돌한다. 이것이 결정적이다.
- 연결 수 조건이 분명하게 충족되지 않는다. Flex 상한 500이 클러스터 전체 기준인지 노드 기준인지 확인하지 않았기 때문이다. 노드 합으로 보면 55%다.

**뒤집히는 조건:** 다음 두 가지가 모두 성립해야 이전 계획 문서를 쓴다. 실행은 승인 항목 7이다.

1. 사용자가 RPO 24시간을 명시적으로 받아들인다.
2. 클러스터 전체 동시 연결 수를 포함한 모든 입력이 Flex 상한의 30% 미만으로 측정된다.

- 그때도 절감액은 Flex 실제 가격을 확인해야 계산할 수 있다. 지금은 미측정이다.

**참고**

- 컴퓨트 자동 확장은 꺼져 있고(scaleDown 꺼짐, 상한 없음) 디스크 자동 확장만 켜져 있다(ATL). 예상하지 못한 등급 상향 비용은 생기지 않는다.
