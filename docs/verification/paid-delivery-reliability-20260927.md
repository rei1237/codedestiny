# 결제 지연·유료 결과 복구·비용 통제 — 구현 및 검증 기록

기준일: 2026-09-27 KST. **전체 계획 완료 아님.** 실제 PG 거래와 과금 LLM 호출은 실행하지 않았다. 운영 DB는 읽기 전용 집계만 수행했다. 아래 구현은 전체 상품의 자동 전달 보장을 의미하지 않는다.

## 원인과 변경

- 최근 7일 웹 PG 표시 표본에서 SDK 준비 지연의 긴 꼬리가 확인됐다. `CheckoutRouteClient.tsx`에서 기존 인증 확인과 병렬로 기존 결제 런타임/SDK 로더를 준비한다. 새 결제·개인정보 조회를 추가하지 않는다. 서버의 최종 인증·금액·통화·서명·소유권 판정은 그대로다. 인증 모듈에는 이미 in-flight 요청 병합이 있어 중복 병합기를 추가하지 않았다.
- `paid-narrative-delivery.js`는 항목 최소 글자 수 미달 출력을 저장하지 않았다. 이제 공급자·근거 해시·반복 검사와 기존 상품별 producer 검사를 통과하고 문단이 완결된 초안을 저장한다. 해당 항목을 한 번 보완하고 실패 시 저장된 후보를 재사용한다. 원래 항목당 최대 3회 예산을 공유한다. 명시된 총 분량을 충족하지 못하면 완료로 처리하지 않고 `DELIVERY_REVIEW_REQUIRED`를 반환한다. 구조 검사만으로 상담의 의미적 품질이 입증되는 것은 아니므로 실 LLM 품질 검토는 별도로 남아 있다.
- 저장 CAS에 잠금 만료 시각을 추가했다. 만료된 작업자가 늦게 반환해도 저장하지 않는다. 기존 저장 후 재조회와 원래 결제의 환불/취소 검사는 유지한다.
- 공통 상담의 기존 10분 스케줄에 지연 탐지를 추가했다. 활성 잠금과 최근 진행은 제외하고, 알림 발송 성공 후에만 표시한다. 알림 채널 미설정·실패는 다음 틱에서 재시도한다. **이 모니터는 서버 자동 이어생성을 구현하지 않는다.**
- 영냥이 프롬프트에서 `systemPrompt`와 user 본문에 중복 전송하던 system 메시지를 제거했다. user 데이터와 응답 스키마는 유지한다. 영냥이·공통 상담 토큰 로그에 실행·항목·시도·호출 종류를 연결했다. 개인정보·질문·생년월일은 새 로그 필드에 포함하지 않는다.
- 모델별 실측 토큰과 검토된 단가를 먼저 합산한 뒤 주문 단위 평균·p95를 계산한다. 단가·주문 식별·재시도 귀속이 빠지면 비용을 0으로 간주하지 않는다. 실패 호출의 공급자 usage가 빠지는 한 청구서 대조 없이 비용을 완결된 것으로 해석할 수 없다.

## 운영 DB 읽기 전용 관측

`report-paid-delivery-health.mjs --db code_destiny --days 7 --env-file <local env>` 및 90일 조회. 외부 HTTP 금지, 실제 연결 DB 이름 검사, 조회 제한 시간을 적용한다. 이름·질문·주문 ID를 결과에 출력하지 않는다.

- 조회 창 내 활성 영냥이 PG 결제 연결 3건, 요청 없음 0건, CREATED로 남은 연결 0건.
- 사주 고등어 요청 5건: 현재 완료 2, 환불 3, 누적 시도 44. 부분 저장 1건은 상태와 별개 집계이며 환불 건일 수 있다.
- 사주 참치 요청 1건: 현재 완료 1, 누적 시도 33.
- 고등어 완료 2건의 요청 생성→완료 p50 14,024,467ms, p95 23,989,171ms. 참치 1건 51,285,037ms. **고객 결제 대기까지 포함하므로 LLM 지연이 아니다.**

- PG 외부 승인 재조회, 실제 고객 주문 재실행, 환불, 운영 DB 수정은 하지 않았다.

## 운영 절차와 관찰 경로

1. 읽기 전용 건강 보고와 상품 대응표를 먼저 실행한다. 실행 시각과 SHA, 기간, 표본 수를 함께 남긴다.
2. 기존 주문 진단은 `scripts/recover-yeongnyangi-request.mjs`의 dry-run을 사용한다. 원래 PG/차감 증빙·소유권·취소/환불·저장 입력·부분 결과를 확인하고 실제 구매 고객을 우선한다.
3. 수동 적용에는 대상 ID, 사유, 담당자를 지정하고 스크립트가 기록하는 변경 전 상태를 보관한다. 예산 증액/실 LLM 실행은 구체적 승인 없이 수행하지 않는다. 구매 증빙이나 입력이 부족하면 자동 재실행하지 않는다.
4. 제공 불가 주문은 운영 검토를 유지하고 제공/환불을 별도로 판단한다. 성공으로 바꾸거나 재결제를 요구하지 않는다.
5. 로그를 확보한 뒤 `report-llm-token-usage.mjs --prices <reviewed tariffs>`로 모델 단가와 주문별 평균/p95를 집계한다. 실제 옵션은 스크립트 도움말을 따른다. 공급자 청구와 합계를 대조하고 누락 호출은 별도로 표시한다.
6. 배포 후 24시간, 이후 같은 조건의 7일 창에서 PG 지연/영냥이 주문 연결/완료 상태/토큰 비용을 비교한다. 전체 복구 성공률 및 모든 상품 주문 누락률은 현재 집계만으로 계산할 수 없다. 기간 경과 결과는 아직 없다.
