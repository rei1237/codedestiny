# CR-006 — 결제 준비 단계의 영속 계산 선택

status: approved-implemented-default-off-local-only

2026-11-01 사용자 승인: “준비 단계부터 생성·재개까지 계산 버전과 명반을 고정하도록 기본 OFF로 구현”. 승인 구현과 검사 기록은 [10-preparation-pinning-report.md](../10-preparation-pinning-report.md)에 있다. 아래는 승인 전 제안의 근거를 보존한 기록이며, “미구현/미승인” 표현은 당시 상태다. 운영 활성화·push·배포는 승인 범위 밖이다.

CR-005 승인 구현 중 확인한 **운영 활성화 선행 차단**이다. 기존 결과를 바꾸는 결함 수정이나 현행 고객 오류 확정이 아니다. 현재 기본 OFF, 이 요청의 코드·저장소·플래그는 변경하지 않았다.

## 확인한 제한

`worker/routes/ziwei-ai.js::handleEnsureAccess`는 명반을 계산해 입력을 검증한 뒤 접근 토큰/결제 정보를 반환한다. 이 시점에 계산 snapshot이나 선택 버전을 영구 보존하지 않는다. `handleBasis`도 별도 계산이며 DB 접근 없는 현재 계약이다. 생성 `handleStart`는 기존 `(userId, idempotencyKey)`와 `llmMeta.chartSnapshot`을 사용하지만 prepare 시점에는 아직 생성 문서가 없을 수 있다.

CR-005에서 구현한 최초 **생성 문서 + chartSnapshot 원자 저장**는 생성/재개 버전을 고정한다. prepare 이후 서버 설정 변경·연도 전환·결제 복귀까지 같은 선택임을 보증하려면 그보다 앞선 영속 선택이 필요하다. 요청 body나 브라우저 저장값은 신뢰할 수 없고 프로세스 메모리는 재시작/다중 Worker에서 보존되지 않는다.

또한 현재 `normalizeConsultationInput`의 정규화된 `birthInfo`에는 출생지가 없다. 따라서 원래 요청의 비서울 출생지가 버려진 뒤 서울 기본값으로 v2 적격 처리되지 않도록, 활성화 전 **원 입력의 적격 판정**과 기존 입력 해시 계약을 함께 검토해야 한다. 이번에는 정규화나 입력 해시를 바꾸지 않았다.

## 재현 시나리오 / 기대 계약

- 합성 입력: 서울 양력 `2023-02-04 11:42`, male, 요청 키 A. prepare에서 선택한 버전과 기준 연도 Y를 고정한 뒤 플래그 OFF/프로세스 재시작/연도 Y+1을 거쳐 generate A.
- 기대: 서버가 보존한 동일 선택·snapshot 사용, 또는 명시적인 안전 보류. 기존 주문·권리·입력 해시·동일 요청 키를 바꾸거나 현재 버전으로 재추첨하지 않음.
- 같은 A를 두 Worker가 동시에 준비하면 선택은 하나만 확정. 같은 A의 다른 입력은 기존 충돌 계약으로 거절. 저장 조회 실패는 신규로 간주하지 않음.
- 이 계약은 현재 미구현/미검증이다. generation 이후의 CR-005 mock 통과를 위 구간의 통과로 확대하지 않는다.

## 제안 변경과 추가 승인 경계

최소 후보는 엔진 밖의 서버 소유 **준비 선택 레코드**다. 기존 결제 문서나 결과를 재사용·덮어쓰지 않는다. 실제 저장 구현 전에 기존 저장 장치 재사용 가능성을 검토하고, 새 형식이 필요하면 아래 신규 전용 계약을 구체화한다.

```diff
+ 신규 준비 선택: owner + featureKey + 기존 requestId (unique)
+ 입력 지문 + 기준 연도 + 계산 옵션/자료 버전 + 기존 형식의 chartSnapshot
+ 최초 생성만 허용, 중복은 확정본 조회, 입력 충돌/저장 불명은 중단
+ prepare/basis/generate는 해당 확정본만 참조
```

이는 개념 diff다. 새 컬렉션/인덱스/필드와 보관 기간·결제 이후 보존 정책은 아직 확정하지 않았다. DB·KV/R2·자산 형식을 임의로 추가하지 않는다. 선택 저장은 과금/권리 부여가 아니며 실제 결제 실행 파일·차감/환불 순서는 이 CR에 포함하지 않는다. 기존 토큰/결제 payload에 선택 필드를 무단 추가하는 우회도 금지한다.

CR-005의 “새 필드/키가 필수면 … 별도 저장 CR로 제출하고 멈춘다”는 경계를 적용했다. 사용자 승인 전 저장 형식 확장·prepare/basis 전환·운영 ON은 보류한다. 사주 유료/다른 소비자의 저장 계약도 별도 검토하며 한꺼번에 편입하지 않는다.

## 승인 후 완료 기준

- 준비 저장 원자성, 두 Worker/두 탭, 타 계정, 입력 변경, 응답 유실, 상태 조회 실패, 기준 연도 변경, OFF 전환, 결제 복귀를 mock으로 검증.
- prepare/basis/generate의 snapshot·버전·기준 연도 일치. 기존 저장/유료 결과의 원문·소유자·키·접근권·과금 횟수 불변.
- 과거 metadata 없는 기록과 신규 기록을 구분하고, 신규 선택 자료 손실을 legacy 재계산으로 숨기지 않음.
- 새 자료를 포함한 결과도 롤백 후 읽을 수 있도록 호환 reader 보존. 전이 의존·Swiss 차단과 공식 CI의 안전 실행 조건 확인.
- 위 조건 충족 후에도 기능 기본 OFF. 운영 활성화·push·배포는 별도 승인.
