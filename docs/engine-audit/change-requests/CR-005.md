# CR-005 — 신규 계산 선택·유료 재개 버전 고정

status: approved-generation-boundary-implemented-default-off

사용자 승인 후 최초 생성 문서의 snapshot 원자 저장·재개 고정을 기본 OFF로 구현했다. [09 구현 보고서](../09-execution-selection-report.md)가 현재 결과다. prepare/basis의 영속 선택과 신규 저장 형식은 [CR-006](CR-006.md)으로 분리했으며 미승인·미구현이다. 아래는 원 제안 이력이고 운영 활성화 승인으로 확대하지 않는다.

기준: `5e2e5499e76581507ff7e876c7c0c8522495a590`. [08 단계 연결 계획](../08-service-rollout-plan.md)의 R0/R1 선행 검토다. **문서 제안이며 구현·활성화·push·배포 승인 요청을 한 번에 묶지 않는다.**

## 현재 제한과 근거

검증된 계산 옵션은 호출별 인자다. `lib/korean-calendar/policy.js::DEFAULT_AUTHORITY_FLAGS`와 `sajuAdapter.ts::computeNatalFromInput`에는 운영 집단 선택·저장 요청별 고정 기능이 없다. 기본 OFF 계산 회귀 통과가 유료 재개의 버전 고정을 증명하지 않는다.

`worker/routes/ziwei-ai.js`는 `handleEnsureAccess`와 `handleBasis`에서 각각 명반을 계산한다. 생성 시에는 신규 문서를 `llmMeta.resumeBody/groups/attempts`와 함께 만든 뒤 `doc.llmMeta?.chartSnapshot || calculateZiweiAiChart(...)`로 명반을 얻어 저장한다. 이 흐름에 현재 시점의 전역 플래그만 넣으면 **prepare 이후 설정 변경 또는 chartSnapshot 저장 전 중단/재개**에서 선택이 달라질 가능성이 있다. 이번에는 실행 재현하지 않았으며 실제 고객 오류라고 확정하지 않는다.

`worker/routes/fortune.js`의 사주 생성은 `resumeBody`, 기존 execution/resultId와 저장 챕터를 재사용한다. 자미와 저장 계약이 같다고 가정하지 않는다. `app/ziwei-ai/ZiweiAiClient.tsx::pollZiweiResult`는 같은 sessionId로 조회·재개한다. 이 ID와 소유자·결제 연결을 유지해야 한다.

## 재현 시나리오와 기대값 — 구현 전 mock으로 확정

| 가상 입력/상태 | 전환 시나리오 | 기대 |
|---|---|---|
| 서울·양력 `2023-02-04 11:42`, 성별 male, 신규 request A | 적격 v2 선택 후 명반 저장 전에 중단, 설정 OFF, 같은 A 재개 | 최초 확정 선택으로 처리하거나 안전 보류. v1로 재추첨·추가 과금 금지 |
| 같은 입력, request B의 v2 명반/일부 장 저장 | OFF 후 재개 | 저장 명반/장의 해시 유지. 결함 의심 시 보류, 다른 버전 장 혼합 금지 |
| 과거 완료 request C, 버전 메타데이터 없음 | rollout 100% 상태에서 재열람 | 기존 원문만 제공. 생성/LLM/차감 0 |
| 기존 request 조회 오류 또는 두 탭 경합 | 동일 idempotency key로 동시 진입 | 조회 실패는 신규가 아님. 기존 원자적 claim·잠금·중복 방지 유지 |

새 계산의 천문 기대값은 기존 공식 골든을 재사용하고 숫자를 새로 추정하지 않는다. 여기의 대상은 요청 생명주기와 저장 보존이다.

## 제안 변경 단위

1. **외부 래퍼 선택:** 엔진 밖에서 승인 기능·신규 여부·지원 집합을 판정한다. 클라이언트가 보내는 임의 플래그는 신뢰하지 않는다. 공개 어댑터에만 검증 옵션을 전달하고 원래 기본값은 OFF로 둔다.
2. **최초 선택 고정:** 기존 실행 ID/잠금 체계 안에서, 유료 부작용 전 지원 판정을 완료하고 새 요청의 계산 snapshot/버전을 한 번 확정한다. 실패·중복·재개에서도 같은 결정을 사용한다. 이미 존재하는 저장 요청은 마이그레이션하지 않는다.
3. **준비·표시·생성 동일성:** 준비/근거/생성에서 같은 선택을 사용한다. 준비 이후 입력이 바뀌면 기존 입력 충돌 계약으로 처리한다. 기존 저장 결과의 근거 화면을 현재 계산으로 바꾸지 않는다.
4. **저장 계약 검토:** 기존 `llmMeta.chartSnapshot/resumeBody` 및 사주 저장 근거가 선택을 충분히 담는지 직렬화·모델·캐시·재개 경로를 검증한다. 가능하면 기존 형식을 그대로 이용한다. 새 필드/키가 필수면 정확한 forward-only diff·호환 reader·mock 근거를 별도 저장 CR로 제출하고 멈춘다.

제안 diff의 **계약 예시**이며 적용 가능한 코드 패치가 아니다:

```diff
- 신규 생성/재개 때마다 현재 설정으로 계산 옵션을 다시 선택
+ 기존 요청이면 저장 snapshot/선택과 기존 재개 계약을 사용
+ 진짜 신규면 적격 판정 -> 승인된 선택 1회 고정 -> 공개 어댑터 호출
+ 선택/명반 저장 실패 또는 지원 판정 불일치면 부작용 없이 중단
+ prepare/basis/generate는 동일 선택, 완료 result 조회는 계산 호출 0회
```

첫 줄은 **피해야 할 미래 구현**이며 현재 코드에 이미 있는 전역 플래그 동작을 삭제한다는 뜻이 아니다. 실제 diff는 승인된 소비자 하나의 기존 잠금·과금 순서를 검토한 뒤 작성한다. 라우트 전체를 새 구현으로 교체하거나 결제 함수를 이동하지 않는다.

## 불변 규칙과 승인 범위

| 경계 | 처리 |
|---|---|
| 엔진 읽기 전용·어댑터 접근 | 추가 내부 수정 없음. 자미 전체 명반 등 공개 출력이 부족하면 새 어댑터 계약을 먼저 검토. 내부 함수 직접 연결로 우회하지 않음 |
| `calculateLocalResult`, prefetch timezone, normalizeSaju timezone | 변경 요청에 포함하지 않음 |
| 저장/유료 결과·사용자 자산·KV/R2 | 기존 원문/키/소유자/결제 연결 보존. backfill·덮어쓰기 금지. 신규 필드/키 필요 시 별도 CR |
| PortOne/Inicis·차감·환불 실행 파일 | 변경 요청에 포함하지 않음. 필요한 경우 결제 별도 승인 게이트에서 멈춤 |
| Swiss/통합 import | 현재 차단 유지. 라우트 mock에 실제 DB/LLM/Swiss fallback 금지; 실행 허용 그래프 입증 전 전체 라우트 import 금지 |

이 CR은 이미 확정된 A 결함을 수정하는 요청이 아니라 **신규 운영 연결에서 회귀를 막기 위한 추가 계약**이다. 승인 없이 코드 수정하지 않는다. 운영 저장소 접근, 실결제, LLM 전송, 플래그 ON, push·배포는 각각 별도 승인 대상이다.

## 완료 기준

- 08 계획 §7의 기존 OFF/정확도와 신규·완료·부분·실패·메타데이터 없음·경합·되돌림 행렬 통과.
- 저장/유료 결과 해시 불변, 재열람 계산·LLM·차감 0, 신규 선택 1회, 대운 외 해석의 예상 밖 변화 0.
- prepare/basis/generate의 버전·snapshot 일치, 플래그 OFF와 재개 경합 리허설 통과.
- Swiss 비연결 그래프·실네트워크 차단과 허용 mock 검사 증거 확보. 전체 CI가 미실행이면 활성화 준비 완료로 선언하지 않음.
- 문서로 구현 범위/검증/남은 차단을 보고한 뒤 별도 활성화 승인 전 OFF 유지.
