## 1. 디자인 방향과 근거

`impeccable` 스킬과 프로젝트 디자인 정본을 적용하라. `CLAUDE.md`, `docs/context/design-canon.md`, `DESIGN.md`, `styles/theme-tokens.css` 및 달빛 예화 생성 소스를 확인하라.

‘달빛 예화’는 막연한 보라 그라디언트가 아니라 **달·꽃의 얇은 라인아트, 정돈된 여백, 로즈/아이보리/골드 또는 네오의 달빛 팔레트, 책과 편지를 펼치는 듯한 타이포와 읽기 리듬**을 가진 기존 시각 체계다. 기존 코드의 `--cd-yehwa-*`와 모티프를 재사용하고 서비스별 색상 계열을 지켜라. 운명 찻집의 초승달·연꽃 표현과 `tea-question.module.css`, `tea-button.module.css`를 실제 참고하라. 생성 CSS는 생성기로 관리하고 영냥이 `--yn-*`를 꿀꿀 화면에 무분별하게 섞지 마라.

현재의 단순 버튼·테두리 카드 반복을 기준으로 사소한 색만 덧입히지 마라. 화면의 위계, 타이포, 콘텐츠 밀도, 에셋 배치, 행동 배치를 함께 설계하라. 전역 DESIGN.md와 무관한 화면 전체를 재디자인하지 말고 이번 표면의 결정을 별도 브리프로 남겨라. 큰 장식·불필요한 유리 효과·새 장식 이모지·과도한 애니메이션은 피하라. 연이 에셋을 새로 제작해야 한다면 지정된 원본 `C:\Users\user\Desktop\CodeDestiny-Build\연이 프로필1.png`를 확인하고 임의의 다른 캐릭터로 대체하지 마라.

## 2. 기록 보관함: 개인적인 달빛 서가

대상은 `/records/`, `app/records/RecordsClient.tsx`, `RecordFrame.tsx`다.

제목 ‘나의 기록 보관함’, 안내 ‘받았던 운세와 상담을 다시 펼쳐보세요’를 유지한다. 작은 달·꽃 장식과 차분한 제목 영역 아래 검색·필터를 배치하고, 기록은 서비스를 구분할 수 있는 서가의 기록물처럼 구성하라. 서비스명·실제 제목/질문·날짜·상태·다시 보기 행동이 한눈에 읽혀야 한다. 재구매 CTA가 읽기 행동보다 앞서지 않아야 한다.

최신순·전체/대표 상담/대화 등 필터·검색·페이지네이션·검색어/필터/스크롤 복원을 유지한다. 긴 문장은 카드에서 제한하고 상세에서 온전히 표시한다. 로그인 필요·로딩·실제 빈 기록·전체 오류·일부 조회 실패를 구분한다. 개인정보와 내부 필드를 카드에 노출하거나 요약용 LLM을 호출하지 마라.

## 3. 상담 허브: 고민에 맞는 상담을 고르는 곳

대상은 `/consultations/`, `app/consultations/ConsultationHub.tsx`다.

‘지금, 어떤 답이 필요한가요?’ / ‘당신의 고민에 맞는 깊이 있는 운명 상담을 골라보세요.’의 방향을 유지하라. 운명 찻집·팩폭 전략실·초융합 운세·공식 명칭 ‘마스터 인연의 서’를 먼저 발견하게 하라. 서비스별 실제 대표 에셋을 적절히 배치하고 고민·결과 형식·가격·진입 행동의 순서가 분명해야 한다. 모든 서비스에 똑같은 이미지와 카드 틀을 복제하지 않되 비교는 쉬워야 한다.

운영 중인 나머지 대표 상담과 별도의 ‘캐릭터와 대화하기’ 영역을 유지한다. 기록 보관함 연결도 명확히 한다. 실제 PriceBadge/상품 설정을 재사용하고 숫자·프로모션·혜택을 하드코딩하지 마라. 준비 중인 기능을 구매 가능하게 보이거나 내부 용어 ‘LLM’, ‘저품질’을 노출하지 마라.

## 4. 핵심 추가 요구: 결과는 각 서비스의 고유 화면으로 읽기

**기록 목록의 디자인 통일과 서비스 결과 디자인 통일을 혼동하지 마라.** 사용자는 각 운세 결과를 볼 때 원래 기능의 화면과 톤앤매너에 맞는 UI/UX로 읽어야 한다. 같은 달빛 카드 안에 모든 데이터를 넣거나 서비스명·색상만 바꾸는 것으로 완료 처리하지 마라.

`docs/records-service-inventory.md`, `lib/records/service-registry.js`, `app/records/view/StoredReading.tsx`를 읽고 전체 25개 저장 어댑터와 공통 저장 25개 상품 유형의 **서비스 ID → 기존 결과 진입점 → 저장 포맷 → 기존 결과 컴포넌트/스타일 → 읽기 전용 연결 → 과거/부분 포맷 처리 → 검증** 대응표를 작성하라. 동일 서비스의 별칭과 상품 변형을 중복 등록하지 마라. 실제 구현을 확인한 공식 이름과 기능 범위를 따른다.

이미 재사용 중인 전용 리더는 보존하고 그 화면의 바깥 래퍼까지 서비스 정체성에 맞춰라. 원본 UI의 표시 컴포넌트를 분리·재사용하는 방식을 우선한다. 예:

- 운명 찻집: `SavedTeaReading.tsx`와 기존 찻집 결과 컴포넌트. 연이의 편지·찻집·로즈 계열과 전체 챕터/저장 근거를 유지한다.
- 팩폭 전략실: `SavedNeoDocuments`, `NeoOperationRoomResultPage.tsx`와 전용 스타일. 판단·전략·행동을 읽는 문서 위계를 보존한다.
- 초융합: `FusionResultThread`와 `fusion-fortune.module.css`. 통합 리포트·근거·시각화·장문 읽기 리듬을 유지한다.
- 마스터 인연의 서: `CodexReader`, `codex.module.css`. 개인판/궁합판, 챕터·인연 구조를 보존한다.
- 사주·자미두수·숙요·베다·점성술: 각 체계의 기존 명식·명반·관계표·차트와 해당 기능의 설명 위계를 보존한다. 저장된 계산값만 사용한다.
- 타로 및 다른 저장 상품: 기존 카드 에셋·스프레드·자리별 해석·도형·보고서 표현을 조사해 재사용한다. 대화는 캐릭터와 역할/메시지 순서를 유지한다.
- 최애 운명: 저장된 완전한 형식은 기존 포토카드 앞뒤·탭·명식 UI를 유지하고, 불완전한 형식은 재계산하거나 값을 만들어 채우지 않는다.

위 예시에 없는 서비스도 조사표에서 빠뜨리지 마라. 현재 `Structure`의 일반 재귀 표시로 처리되는 서비스는 원래 결과 UI로 개선하라. 과거 포맷에 필요한 값이 없으면 호환 어댑터로 저장된 내용을 그 서비스의 읽기 화면에 표시하고 누락 상태를 정직하게 안내한다. JSON 키나 운영 메타데이터를 사용자 화면에 노출하지 마라. 기존 전체 서비스 화면을 그대로 마운트해 생성/결제 훅을 시작하는 방식은 금지다.

`/records/view/` 직접 URL, 새로고침, 모바일 뒤로 가기, 기존 서비스 직접 결과 URL과 공유를 보존하라. 공통 상단 안내는 읽기 위치·기록 복귀·상태에 한정하고, 본문 폭·타이포·차트·탭·챕터 내비게이션은 각 서비스의 표현을 존중하라. 목록 복귀 시 검색·필터·스크롤 위치를 유지하라.

## 5. 기능 및 안전 경계

- 완료 기록 재열람은 **결제·차감·LLM·새 운세 계산·생성/복구 POST 0회**다. mock 네트워크 검증으로 확인하라.
- `GET /api/records`, `GET /api/records/detail`의 서버 소유권·중복 제거·정렬·커서·부분 실패 계약을 보존한다. 목록에서 대용량 본문을 내려받지 마라.
- 영냥이의 제한된 자동 복구→실패 시 환불 처리와 기존 환불 후 접근 정책, 결제·이용권·월정석·상품 가격은 이번 UI 작업에서 변경하지 마라.
- 전체 챕터·저장된 구조화 결과·HTML sanitizer를 보존한다. 부분 결과를 완료로 꾸미거나 TTL 삭제/미저장/요약만 남은 결과를 복원했다고 주장하지 마라.
- i18n 정본과 에셋 출처를 유지하고 실제 사용자 운세를 로그·스크린샷에 사용하지 마라. 개발환경은 mock, 실제 연동 폴백 금지다.

## 6. 검증과 완료 보고

방향과 성공 기준을 짧게 공유한 뒤 실제 구현하라. 사용자가 이미 달빛 예화 방향과 서비스별 읽기 경험을 요청했으므로 같은 범위의 승인을 반복 요청하지 마라.

360/390/430px와 데스크탑에서 보관함·허브 및 각 서비스 계열의 실제 저장 결과를 검증하라. 긴 제목/질문, 과거/부분/생성 중/실패 결과, 모든 로딩/오류 상태, 직접 URL·새로고침·뒤로 가기를 포함한다. 모든 레지스트리 대상의 복원은 자동 검사로 확인하고, 전용 레이아웃마다 실제 렌더 증거를 남겨라. 테스트하지 않은 유형은 구분해 보고한다.

본문 대비 4.5:1, 큰 글씨/UI 3:1을 합성 배경 기준으로 측정하고 44px 터치·입력 16px·safe-area·가로 넘침·하단 내비게이션과 마지막 CTA의 실제 위치·키보드 포커스·reduced-motion을 확인하라. 장식은 aria-hidden과 pointer-events를 적절히 적용한다. visual-checker가 실제 캡처를 독립 검토하고 critique→audit·polish 및 변경 UI의 기계 검사를 수행한다. ‘실행했음’과 ‘통과했음’을 구분하라.

관련 targeted 검사와 `npm run check:fast -- --plan` → `npm run check:fast`, 필요 시 `sync:public`/미러 검증을 실행하고 공식 main CI를 확인하라. 동시 작업 변경은 보존하고 현행 main 전달 계약을 따른다. PR·운영 승격·실결제·실환불·실LLM·운영 DB 쓰기는 하지 마라.

최종 보고에는 수정 파일·디자인 의도·서비스별 읽기 화면 연결표·모바일 전후 자료·실행 명령/결과·유지한 정책·남은 제약·main SHA와 CI 링크를 제출하라. 화면을 예쁘게 만들면서 기존 기록의 실제 조회와 재열람을 빠뜨리지 마라.
