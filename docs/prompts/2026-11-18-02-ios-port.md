# Code Destiny iOS 앱 — 이식 설계·구현·출시 마스터 프롬프트 (v2)

> 이 문서는 **여러 세션에 걸쳐** 실행하는 마스터 프롬프트다. 한 세션에서는 **한 Phase만** 수행한다.
> Phase가 끝날 때마다 보고서를 `docs/ios/reports/phase-{N}.md`에 저장하고 멈춘다. 다음 세션은 이 문서와 직전 보고서를 읽고 시작한다.
> 경로는 저장소 구조를 확인한 뒤 조정할 수 있으며, 조정하면 보고하라.

## 0. 역할

너는 아래 일곱 명의 시니어 전문가로 이루어진 팀이다. 모든 결정에 어느 관점에서 판단했는지 한 줄로 밝혀라.
**7번(레드팀 심사관)은 매 Phase 보고서 끝에 "이 상태로 제출하면 반려될 사유" 목록을 작성한다.**

| # | 역할 | 책임 |
|---|---|---|
| 1 | iOS 아키텍트 | Swift 6(strict concurrency), SwiftUI, WebKit, 모듈 설계 |
| 2 | StoreKit 2·App Store Server 엔지니어 | IAP, JWS 검증, Server API, Server Notifications V2 |
| 3 | 인증·보안 엔지니어 | Sign in with Apple, ASWebAuthenticationSession, 세션, 브리지 보안 |
| 4 | 백엔드 엔지니어 (Cloudflare Workers + MongoDB) | 검증·지급·알림·푸시 서버 구현 |
| 5 | 성능·안정성 엔지니어 | 실행 시간, WebKit 메모리, MetricKit, 크래시 |
| 6 | iOS 제품 디자이너 | HIG, iOS 26 디자인(Liquid Glass), 위젯, 햅틱, 접근성 |
| 7 | **레드팀 App Review 심사관** | 반려 사유를 사전에 찾고, 심사 패키지와 반려 대응을 맡는다 |

**목표**: ① 첫 제출에 심사 통과, ② 웹 자산 최대 재사용, ③ 사용자가 "웹뷰 앱"이라고 느끼지 않는 체감 품질, ④ Android와 하나의 계약으로 유지보수할 수 있는 구조.

## 1. 프로젝트 컨텍스트

- 서비스: code-destiny.com. 한국어 운세 플랫폼이며 사주, 타로, 자미두수, 서양 점성술, 숙요점, 베다(낙샤트라) 6개 엔진을 제공한다.
- 스택: Next.js 15 + Cloudflare Pages/Workers, MongoDB Atlas M10이다.
  - connectionGuard가 있고 기본 읽기는 secondaryPreferred다. **결제와 인증은 primary에서 읽는다.**
  - 스테이징 환경은 `codedestiny-staging`이고 R2 버킷은 `bugs-staging`, `codedestinyassets-staging`이다.
- 배포: Cloudflare 네이티브 Git 연동을 쓴다. **GitHub Actions 사용량(비용)을 줄이는 중**이므로, macOS 러너 비용이 큰 Actions보다 **Xcode Cloud를 우선 검토**한다.
- 기준 구현은 **Android 하이브리드 앱 `com.codedestiny.app`**이다.
  - 자체 `@JavascriptInterface` 브리지, Google Play Billing, Custom Tabs OAuth, `pricing.app.ts`(앱 가격은 웹보다 20–30% 높다)를 쓴다.
- 결제 이력: 멱등 orderId, D1 분산락, 버튼 상태머신. 웹훅은 즉시 2xx로 응답한 뒤 비동기로 처리한다. 결제했는데 기능이 해금되지 않던 장애를 이미 겪었다.
- 고유 자산 (4.3(b) 대응의 핵심)
  - 경력 10년차 명리학자가 설계하고 자문한 사주 엔진
  - 6개 엔진을 하나로 통합한 "초융합 운세"
  - 캐릭터 상담: 연이(따뜻함), 네오/사자(직설), 꽃돼지(치유)
  - 운명의 섬, 운명 찻집, 네오 팩폭 전략실 등 콘셉트 기능
- 디자인: "하나의 신비로운 세계" 프리미엄 미학, **달빛 예화(月花)** 디자인 언어, 주 타깃은 20–30대 여성이다.
- 사업자: 개인 간이과세자다. Apple Developer Program에는 **개인(Individual)**으로 등록한다. 스토어의 판매자명은 실명으로 표시된다.

### 2-3. 결제 방식 결정
- 한국 스토어의 외부 결제(StoreKit External Purchase Entitlement)는 수수료가 26%이고, 한국 전용 별도 바이너리가 필요하며, 환불과 고객 지원을 직접 해야 한다.
- 반면 **Small Business Program(연 100만 달러 이하)의 IAP 수수료는 15%**다. 따라서 **StoreKit 2 IAP로 단일화**한다.

## 4. 크로스플랫폼 브리지 계약 v1 (핵심 산출물)

> **Android에 이미 있는 메서드 이름과 시그니처가 우선한다.** 아래는 기본 설계안이다. Phase 0에서 Android 실제 구현과 대조해서 `native-bridge-contract.md`로 확정하라. 웹은 **이 계약만 알고 플랫폼은 몰라야** 한다.

### 4-1. 전송 규약
- iOS는 `WKScriptMessageHandlerWithReply`(이름 예: `cdNative`)를 쓰고, Android는 기존 `@JavascriptInterface`를 쓰는데 응답은 콜백 ID 방식이다. 두 방식 위에 **공통 JS shim**(`window.CodeDestinyNative`)을 주입해서 Promise API로 통일한다.
- 요청 envelope: `{ v: 1, id: string, method: string, params?: object }`
- 응답 envelope: `{ id, ok: true, result } | { id, ok: false, error: { code, message, retryable } }`
- 이벤트(네이티브 → 웹): `window.dispatchEvent(new CustomEvent('cdnative:<event>', { detail }))`
- **보안**
  - 메시지의 `frameInfo.isMainFrame`과 `securityOrigin`이 허용 도메인(prod, staging)인지 검증한다.
  - 허용 목록에 없는 출처는 `E_FORBIDDEN_ORIGIN`으로 거부한다.
  - 민감한 메서드(store, auth)는 메인 프레임에서만 허용한다.
- 타임아웃은 기본 15초이고 `store.purchase`는 예외(무제한, 사용자 동작 기반)다.

### 4-2. 메서드 (초안)
| 메서드 | params → result | 비고 |
|---|---|---|
| `app.getInfo` | → `{platform, appVersion, build, bridgeVersion, osVersion, locale, safeArea}` | 핸드셰이크 |
| `app.ready` | `{route}` → `void` | 웹 첫 의미 있는 페인트 신호. 스켈레톤 → 웹 크로스페이드에 쓴다. |
| `auth.signIn` | `{provider: 'apple'\|'google'}` → `{status}` | 세션 쿠키 주입이 끝난 뒤 resolve |
| `auth.signOut` | → `void` | 네이티브와 웹 저장소를 함께 정리 |
| `store.getProducts` | `{ids[]}` → `[{id, displayPrice, type, title}]` | 가격 표시는 이것만 쓴다. |
| `store.purchase` | `{productId, context}` → `{status: 'granted'\|'pending'\|'cancelled', grantId?}` | **서버 지급이 끝난 뒤에만 granted** |
| `store.restore` | → `{restoredIds[]}` | 비소모성 |
| `consent.getAI` / `consent.requestAI` | → `{granted, version}` | 거부하면 AI 기능 진입 차단 |
| `push.getStatus` / `push.request` | `{channel: 'service'\|'marketing'}` → `{status}` | 마케팅은 야간 동의를 분리 |
| `haptics.play` | `{type: 'success'\|'error'\|'light'\|'medium'\|'selection'}` | |
| `share.open` | `{url?, imageUrl?, text}` → `{completed}` | 이미지는 서버 생성 URL을 우선 |

### 4-3. 버전 정책
- 계약은 `bridgeVersion`(정수)으로 관리한다. 메서드 추가는 같은 버전 안에서 하위 호환으로 처리하고, 의미가 바뀌면 버전을 올린다.
- 웹은 `app.getInfo`로 기능을 감지한다. 지원하지 않으면 우아하게 축소한다.
- 서버 `/app/config`의 `minSupportedBuild`보다 낮은 버전이면 강제 업데이트 화면을 띄운다.

## Phase 5 — 인증

- **Sign in with Apple (네이티브)**
  - 클라이언트: 원본 nonce를 생성하고 SHA256 해시를 요청에 넣는다. `fullName`과 `email`은 첫 로그인 때만 오므로 즉시 서버로 보낸다.
  - 서버 `/auth/apple/native`
    - identity token을 Apple JWKS로 검증한다(`iss`, `aud`=번들 ID, `exp`, nonce).
    - authorization code와 client secret(SIWA 키로 ES256 JWT 서명)으로 refresh token을 교환해서 **암호화해 저장**한다. revoke에 필요하다.
    - `sub` 기준으로 사용자를 찾거나 만들고, 1회용 세션 교환 코드를 발급한다.
  - 앱 시작 시 `getCredentialState(forUserID:)`를 확인하고 `revoked`면 로그아웃한다. Apple 서버 간 알림(이메일 변경, 동의 철회, 계정 삭제)도 처리한다.
- **Google**: ASWebAuthenticationSession(`prefersEphemeralWebBrowserSession`은 UX 영향을 비교해서 결정) + PKCE + state. 유니버설 링크나 콜백 스킴으로 복귀한다.
- (있다면) 카카오·네이버: 같은 원칙(시스템 인증 세션)으로 처리한다.
- **세션 주입 (레이스 제거)**: 교환 코드 → `/auth/session/exchange` → Set-Cookie 값 → `WKHTTPCookieStore.setCookie` **완료 콜백 후** 로드 또는 리로드. 쿠키 속성(Domain, Secure, HttpOnly, SameSite)이 서버 발급값과 일치해야 한다.
- 오류 분류: 401만 재로그인, 503과 네트워크 오류는 재시도 화면(과거 오인 로그아웃 재발 방지).
- **계정 삭제**: 설정 → 영향 고지(남은 이용권 소멸, 복구 불가) → 재인증 → 서버 삭제 → **SIWA revoke 호출** → 푸시 토큰 해제 → 로컬(쿠키, Keychain, App Group) 정리 → 첫 화면.
- 로그아웃: 쿠키, 웹 스토리지(`removeData`), Keychain, 위젯 데이터를 정리한다.

## Phase 6 — StoreKit 2 결제 (⚠️ 별도 승인 게이트)

### 6-1. 클라이언트 (`StoreService` actor)
- 앱 시작 즉시 `Transaction.updates`를 구독한다. 앱 밖 결제, Ask to Buy 승인, 프로모션 구매를 놓치지 않는다.
- 시작할 때 `Transaction.unfinished`를 순회해서 서버 검증 → 지급 → `finish()`를 재시도한다.
- 구매 흐름 상태머신: `idle → loadingProducts → presenting → purchasing → (pending | cancelled | verifyingServer) → granted → finished`, 실패하면 `error(retryable)`. 앱이 종료돼도 `unfinished`로 재개한다.
- `purchase(options: [.appAccountToken(uuid)])`: uuid는 서버가 사용자별로 발급하는 **고정 값**이고 `/iap/apple/account-token`으로 받는다.
- `VerificationResult.unverified`이면 지급하지 않고 로그를 남긴다.
- **`finish()`는 서버가 `granted`를 응답한 뒤에만** 호출한다.
- 비소모성 상품: 복원 버튼은 `AppStore.sync()` + `Transaction.currentEntitlements` → 서버 동기화로 처리한다. 소모성 잔액은 **서버 원장이 진실**이다.
- 가격: `Product.displayPrice`만 쓴다. 상품 로드에 실패하면 재시도 UI를 보여주고 결제 버튼을 비활성화한다.
- 중복 탭 방지, 결제 중 화면 이탈 방지, 결제 시트가 1초 안에 뜨도록 상품을 미리 로드한다.

### 6-2. 서버 (Cloudflare Workers) — 엔드포인트 제안 (기존 라우팅 규칙을 따름)
| 엔드포인트 | 역할 |
|---|---|
| `GET /iap/apple/account-token` | 사용자의 appAccountToken(UUID) 발급과 조회 |
| `POST /iap/apple/verify` | 클라이언트가 보낸 `jwsRepresentation`을 검증하고 지급(멱등)한 뒤 `{granted, grantId}`를 응답 |
| `POST /iap/apple/notifications` | Server Notifications V2 수신: **즉시 200** 후 큐로 처리 |
| `POST /iap/apple/sync` | 복원과 동기화 (트랜잭션 이력 조회 기반) |

- **JWS 검증**: 헤더 `x5c` 체인을 **Apple Root CA G3**까지 검증하고(번들된 루트 인증서와 비교), ES256 서명을 검증하고, `bundleId`, `environment`, `appAccountToken`↔사용자 일치를 확인한다.
  - Workers 런타임에서 Apple 공식 `app-store-server-library`(Node)가 `nodejs_compat`으로 동작하는지 먼저 확인한다. 안 되면 WebCrypto로 직접 구현하고 테스트 벡터로 검증한다.
- **App Store Server API 호출**: In-App Purchase 키로 ES256 JWT를 만들어 Get Transaction Info, Transaction History로 교차 검증한다. Sandbox와 Production 엔드포인트를 분리한다.
- **멱등성**: `transactionId` 유니크 인덱스를 쓰고, 기존 orderId와 분산락 체계에 `appleTransactionId`로 매핑한다. 클라이언트 검증 경로와 알림 경로가 **동시에 들어와도 지급은 정확히 한 번**이어야 한다.
- 데이터 모델(제안, forward-fix): `apple_transactions { transactionId(unique), originalTransactionId, productId, type, appAccountToken, userId, environment, purchaseDate, revocationDate, revocationReason, grantId, status, rawSignedHash, createdAt }`
- MongoDB 쓰기와 읽기는 primary에서 하고, connectionGuard를 준수한다.

### 6-3. 알림 처리 표

## Phase 7 — 네이티브 가치 기능 (4.2와 4.3(b) 대응의 핵심)

1. **AI 데이터 처리 동의 (5.1.2(i))**
   - 첫 AI 호출 전에 네이티브 시트를 띄운다. 내용: **어떤 데이터**(생년월일시, 성별, 출생지, 질문 내용), **누구에게**(LLM 제공자 실명), **왜**(해석문 생성), **보관과 학습 여부**, 철회 방법.
   - 버튼은 [동의하고 계속] / [나중에]로 한다. 거부하면 AI 기능 대신 비AI 콘텐츠로 안내한다.
   - **서버 강제**: LLM 호출 전에 `ai_consents(userId, version, grantedAt, platform)`을 확인하고, 없으면 `E_CONSENT_REQUIRED`를 반환한다. 웹과 Android에도 같은 규칙을 적용할지는 제안만 한다.
   - 설정에서 확인하고 철회할 수 있게 한다. 문구가 바뀌면 version을 올리고 다시 동의를 받는다.
2. **게스트 체험**: 로그인 없이 오늘의 운세 미리보기나 샘플 결과를 볼 수 있게 한다(5.1.1(v), 첫 인상, 전환에 모두 유리). 저장과 결제가 필요한 순간에 로그인을 유도한다.
3. **WidgetKit "오늘의 운세"**
   - 크기: small, medium, 잠금 화면(`accessoryRectangular`, `accessoryInline`)
   - 데이터: 서버 `/widget/daily`(사용자별 일진 요약, 캐릭터 한 줄 메시지) → App Group 캐시 → TimelineProvider는 자정에 갱신하고 앱을 실행할 때 `WidgetCenter.reloadAllTimelines()`를 호출한다.
   - 인증: Keychain 공유 그룹의 토큰을 쓴다. 로그인하지 않은 상태면 "탭해서 오늘의 운세 받기"를 보여준다.
   - 디자인: 달빛 예화 톤, 다크·틴트·클리어 렌더링 모드를 모두 검증한다. 탭하면 결과로 딥링크한다.
4. **푸시**
   - 서비스 알림(오늘의 운세 도착, 상담 답변 완료)과 마케팅 알림(이벤트, 할인)을 **채널과 동의로 분리**한다(2-4 법규).
   - 권한 요청: 가치를 경험한 직후에 사전 설명 화면을 보여주고 시스템 프롬프트를 띄운다. `.provisional`(조용한 전달)도 검토한다.
   - 발송 경로: Android가 FCM을 쓰면 **FCM HTTP v1으로 단일화**하는 것을 우선 검토한다. APNs 직접 발송은 HTTP/2가 필수이므로 Workers 호환성(호환 라이브러리 존재 여부, 안정성)을 검증한 뒤 선택한다.
   - 토큰 등록과 해제(로그아웃, 계정 삭제), 알림을 탭하면 `route`로 딥링크, 마케팅 알림은 야간 발송을 차단한다.
5. **결과 공유**: 서버에서 결과 카드 이미지를 생성하고(두 플랫폼 공통, 브랜드 템플릿), `ShareLink`로 공유하고 사진 앱에 저장할 수 있게 한다(사진 추가 권한 문구 포함).
6. **햅틱**: 결과 공개는 success, 카드 뒤집기는 light, 오류는 error. 접근성 설정을 존중한다.
7. **리뷰 요청**: 결과를 끝까지 읽었거나 공유를 완료한 직후에만, 버전당 1회 이하로 요청한다.
