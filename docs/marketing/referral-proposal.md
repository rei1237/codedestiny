# 공유·추천 양쪽 혜택 — 제안, 미승인

> **상태: 제안, 미승인.** 구현하지 않았다. 금액·지급 조건·DB·결제·이용권 정책은 바뀌지 않았다. 아래 숫자는 결정을 돕는 예시이며 사용자 승인 전에는 화면·서버 어디에도 넣지 않는다.

작성 2026-11-16. 출처: 전환 개편 계획 ②-6.

## 목표

공유한 사람(추천인)과 링크로 들어와 처음 결과를 받은 사람(신규) 양쪽이 작은 혜택을 받게 해, 무료 결과 → 공유 → 신규 첫 결과 흐름을 만든다. 병목은 전환 UI가 아니라 모수이므로(유입 확대) 이 제안은 유입 장치로 본다.

## 선택지

| 안 | 내용 | 장점 | 약점 | 추천 |
|---|---|---|---|---|
| A. 신규 첫 유료 결과 수령 시 양쪽 월정석 | 신규가 첫 유료 결과를 **받은 뒤** 양쪽에 월정석 지급(만료 30일) | 기존 first_paid 수령 판정을 그대로 재사용. 결제만 하고 환불하는 악용에 강함 | 추천인 보상이 늦게 온다 | **추천** — 기존 "결과 수령 후 지급" 원칙과 같다 |
| B. 신규 가입·무료 결과 완료 시 양쪽 소액 | 가입 또는 무료 사주 완료만으로 지급 | 체감이 빠르다 | 다중 계정 악용에 가장 약함. 결제와 무관한 비용 | 비추천 |
| C. 추천인만 누적 단계 보상 | N명 첫 결과 수령마다 단계 보상 | 열성 공유자 강화 | 신규 쪽 동기 없음. 단계 설계·표시 복잡 | 보류 |

## 재사용할 수 있는 기존 장치 (실측 경로)

- `worker/lib/activation-rewards.js` — `findFirstDeliveredCashPurchase(userId)`(첫 현금 구매 결과 수령 판정), `settleActivationReward(userId, kind)`(종류별 1회 지급). 안 A의 신규 판정과 지급 골격으로 쓸 수 있다. 새 kind를 추가하려면 `js/core/activation-reward-policy.mjs` `ACTIVATION_REWARD_KINDS`와 `activationRewardId` 규칙을 함께 확장해야 한다.
- `js/core/activation-reward-policy.mjs` — `FIRST_PAID_REWARD`(500, 30일), `FIRST_PAID_REWARD_START`. 금액 정본을 한곳에 두는 패턴.
- `worker/lib/review-reward.js` — `buildReviewRewardSourceId`로 lot ID를 고정해 재시도·재승인 중복 지급을 막는 방식. 추천 보상도 `referral:<신규ID>` 같은 결정적 lot ID로 1회만 지급하게 만들 수 있다.
- `lib/share.v2.ts` — `buildUtmShareUrl`(`utm_medium=share&utm_campaign=public_share`)과 `share_receive` 계약. 추천 링크도 이 계약을 깨지 않게 별도 파라미터로 붙여야 한다. 단, 이 모듈의 공유 이벤트는 cdTrack 정제 과정을 우회한다(계획 0-4-6) — 추천 이벤트를 붙이기 전에 먼저 정리해야 한다.
- `docs/review-rewards.md` — 관리자 승인·만료·현금 교환 불가·대상 상품 구매 제외 정책 문구를 그대로 따를 수 있다.

## 개인정보 원칙

- 추천 링크에는 **명식·이름·생년월일·결과 본문·주문 ID·사용자 ID를 넣지 않는다.** 서버가 발급한 무작위 추천 코드(추측 불가, 계정과의 대응은 서버만 앎)만 쓴다.
- 링크를 연 사람에게 추천인의 이름이나 결과를 보여 주지 않는다. "친구가 보낸 링크" 수준만 표시한다.
- GA4에는 추천 코드 원문을 보내지 않는다. `referral_link_open` 같은 비식별 이벤트와 placement만 보낸다.
- 공유 이미지·문구에는 기존 후기 공유처럼 공개 홈페이지 주소만 넣는다.

## 악용 위험과 막는 법

| 위험 | 막는 법 |
|---|---|
| 자기 추천(한 사람이 두 계정) | 지급을 결과 수령 후로 미룸(안 A). 같은 결제 수단·기기 지문 대조는 개인정보 범위가 커서 1차에는 넣지 않고, 추천인당 지급 상한(예: 월 N건)으로 한도를 둔다 |
| 결제 후 환불로 보상만 챙김 | 결과 수령 후 지급 + 환불 시 해당 lot 회수(기존 환불 접근 회수 규칙과 맞춤) |
| 추천 코드 대량 살포·스팸 | 코드는 계정당 1개, 지급 상한, 관리자 화면에서 이상 건 확인 |
| 이미 가입한 사람을 "신규"로 위장 | 신규 판정은 가입 시각이 링크 최초 열람보다 뒤이고, 그 계정의 첫 유료 결과일 때만 |
| 중복 지급(재시도·경합) | 결정적 lot ID(`referral:<신규ID>`)로 1회 지급, 기존 review-reward 패턴 재사용 |

## 결정이 필요한 것 (사용자)

1. 안 A/B/C 중 선택(추천 A).
2. 양쪽 금액과 만료(예시: 양쪽 월정석 500, 30일 — 기존 첫 구매 혜택과 겹칠 때 합산 여부 포함).
3. 추천인 지급 상한.
4. 시작일과 종료 여부(상시 vs 기간).

## 구현 시 위험도

RED — 지급·DB·인증 경로를 건드린다. 승인 후 `payment-gating` 문서 절차, paid-gate-auditor 감사, mock 검증, 운영 DB 쓰기 금지 원칙을 따른다. 이 문서 단계에서는 아무것도 구현하지 않는다.
