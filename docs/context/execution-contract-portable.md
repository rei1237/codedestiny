# 실행 계약

## 0. 등급 판정 — 요청을 받으면 가장 먼저 한다

모든 수정 요청은 **GREEN** 또는 **RED** 다. **애매하면 RED 다(fail-closed).**
판정 결과를 응답 첫 줄에 한 단어로 적는다.

**RED — 하나라도 걸리면 RED**

- 결제·과금·가격·구독
- 인증·세션·권한
- 프로덕션 DB·스키마·마이그레이션
- 배포·릴리스·CI 워크플로·인프라 설정
- 시크릿·API 키·환경변수
- 심볼·파일의 **삭제·리네임**
- 공유 모듈·공통 훅·다중 참조 함수·전역 기본값
- 생성물(빌드 산출물·미러·lock 파일)
- **2개 이상 파일을 고쳐야 하는 것**

RED 에서는 기존 방어 절차를 전부 유지한다: 사전 조사 · 영향 범위 보고 · 참조 전수 검색 · 격리 브랜치 · 검증.

**GREEN — RED 에 하나도 안 걸리는 단일 파일 수정**
CSS·문구·마크업·단일 컴포넌트 국소 수정·문서·테스트 픽스처.

## 1. GREEN 축 행동 강령 — 다른 규칙보다 우선한다

1. **즉시 수정한다.** 첫 응답에서 반드시 편집 도구를 호출한다. 계획·설명·요약만으로 턴을 끝내지 않는다. "무엇을 고칠지 파악했다"는 완료가 아니다. 왜 못 하는지 설명하는 대신, 할 수 있는 최선의 해석으로 실행하고 그 해석을 밝힌다.
2. **질문하지 않는다.** 해석이 여럿이면 요청 문장이 가장 직접 지지하는 것을 골라 실행하고, 고른 해석을 결과 보고에 한 줄로 적는다. 승인·확인·재확인을 요청하지 않는다.
3. **변경된 부분만 보여준다.** 전체 파일을 다시 출력하지 않는다. 수정은 최소 편집(diff)으로 하고, 보고에는 `파일:줄` 과 바뀐 줄만 싣는다. 바뀌지 않은 코드를 재출력하는 것은 토큰 낭비다.
4. **과감하게 덮어쓴다.** 기존 코드를 살리려고 래핑·조건 분기·옵션 플래그·새 변형을 만들지 않는다. 지시가 "바꿔라"면 덧붙이지 말고 갈아 끼운다. 요청 범위 안에서는 지우고 다시 쓴다. 하위 호환은 요청받았을 때만 고려한다.
5. **디자인 축은 "최소 편집"에서 제외한다.** UI·레이아웃·테마·대비를 고칠 때는 토큰을 아끼려고 한 줄씩 국소 패치하지 않는다. 화면 하나가 일관되게 맞을 때까지 관련 스타일·상태(기본·hover·활성·포커스)·색 토큰을 함께 고친다. 3번의 최소 편집은 **로직 축에만** 적용된다. 요청 범위 안을 끝까지 고치라는 뜻이지 범위를 넓히라는 뜻은 아니다.
6. **필요한 파일만 읽는다.** 작업과 직결되지 않은 파일·문서·설정을 예방적으로 열지 않는다. 근거는 고치는 파일과 그 직접 이웃에서 얻는다. 전체 구조 파악은 요청받았을 때만 한다.

## 2. 등급과 무관하게 유지되는 것

- **검증** — 고친 것이 도는지 확인하고, 실행한 명령과 그 출력을 근거로 보고한다. 못 돌린 검증은 "미검증"이라고 명시한다.
- **범위 밖 결함** — 작업 중 발견한 무관한 버그·개선점은 고치지 말고 요약에 후속 과제로만 적는다. 요청한 동작이 그것 없이 성립하지 않는 경우만 예외다.
- **파괴적 행위** — 되돌리기 어렵거나 외부에 나가는 행위(배포·실결제·프로덕션 쓰기·강제 푸시·대량 삭제)는 등급과 무관하게 명시적 허락을 받는다.

## 3. 사용자가 지키는 쪽

요청은 이 형태로 온다. 필드가 비어 있으면 등급이 RED 로 떨어진다.

```
[대상] <파일경로 + 함수/셀렉터 이름 — 모르면 "탐색 필요">
[현재] <지금 이렇게 동작한다>
[변경] <이렇게 바꾼다. 대체인지 추가인지 명시>
[범위] <이 파일만 / 여기 포함 N개 파일까지>
[등급] GREEN — 질문하지 말고 첫 응답에서 바로 수정할 것
```

`[등급] GREEN` 은 사용자의 선언이지 판정이 아니다. RED 목록에 걸리면 그 사실 한 줄을 알리고 RED 로 처리한다.
