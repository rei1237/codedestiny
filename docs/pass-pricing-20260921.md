# 꽃돼지 이용권 신규 정책과 판매 조건

2026-09-21 사용자 승인안. 이후 실제 PG·서버·Google 비용을 반영해 흑자 범위로 재검토하라는 요청에 따라 아래 표는 판매 전 후보안이며 확정 판매 조건이 아니다. 정책 버전은 `flower-20260921`, 버전 없는 구매는 `legacy`다.

| 신규 이용권 | 30일 판매가 | 건당 상한 | 누적 한도 | 프로필 |
| --- | ---: | ---: | ---: | ---: |
| 꽃돼지 스탠다드 | 9,900원 | 5,000원 | 20,000원 | 3개 |
| 꽃돼지 프리미엄 | 29,900원 | 10,000원 | 50,000원 | 7개 |
| 꽃돼지 VVIP | 59,900원 | 30,000원 | 90,000원 | 15개 |

자동갱신 없음. 상담 횟수 제한을 추가하지 않는다. 실제 상품 가격만큼 차감하고, 초과분을 자동 청구하지 않는다. 영냥이는 기존 1,000~30,000원 단건 결제를 유지하며 이용권·월정석에서 제외한다. Family와 기존 4종의 신규 주문은 닫되, 이미 생성된 주문·구매·선물·환불·재열람은 유지한다.

정본은 `lib/payment/pass-policy.js`. 기존 `pass-pricing.js`와 `profile-limits.js`의 4종 값은 과거 구매 해석용으로 보존한다. 새 주문 ID는 `*_1m_v2`, Play 상품은 `cd_pass_*_30d_v2`. 주문 metadata, 선물 productSnapshot, 활성 profileSubscription에 정책 버전을 저장한다. 서로 다른 정책의 활성 기간은 합산하지 않는다. 구정책 구매자의 VVIP 건당 20,000원과 Family 권리를 신정책으로 바꾸지 않는다.

## 단건 가격

운명 찻집 5종은 5,000원. 기존 30,000원 상품은 모두 유지한다. 나머지 꽃돼지 운세 상품은 3,000→3,000원, 5,000→3,000원, 7,000/10,000→5,000원, 20,000→10,000원이다. 무료·판매 중단 이력 키는 유지하며 프로필 관리 수수료도 운세 상품 인하에 포함하지 않는다. 변경 상품·해금 ID·코스별 대조표는 `docs/verification/flower-price-changes-20260921.json`이다. 결제 완료 주문의 실제 결제액은 과거 주문에서 읽는다.

## 판매 차단과 원가 검증

현재 실원가 증거가 없어 **새 이용권 3종 모두 웹·앱 판매 차단**이다. `lib/payment/pass-cost-evidence.js`의 빈 객체를 mock이나 추정 단가로 채우지 않는다. GET `/api/payments/pass-offers`가 화면과 신규 주문의 공통 판매 상태를 제공한다. Play는 웹과 별도 증거와 `verifiedProductId`가 필요하다. 기존 주문 확정·선물 수령·복원에는 신규 판매 차단을 적용하지 않는다.

`node scripts/audit-pass-profitability.mjs [evidence.json]`은 읽기 전용이다. 차단된 항목이 있으면 종료 코드 2다. 각 등급/채널별 증거 형태:

```text
{ vvip: { web: {
    reviewedAt, sourceRefs,
    priceKRW: 59900, maxCoveredCoin: 300, monthlyLimitCoin: 900,
    netRevenueKRW, paymentFeeKRW,
    products: { canonicalFeatureKey: { priceKRW, maxCostKRW, sourceRefs } }
} } }
```

- `netRevenueKRW`: 세금 제외 매출. PG/Play 수수료는 채널별 `paymentFeeKRW`에 별도 반영한다.
- `maxCostKRW`: 계산·생성·허용된 전체 재시도·저장·지원·환불 충당을 포함한 상품 1건의 보수적 최대 원가. 단순 평균이나 토큰 비용만 넣지 않는다. 요청 실패·중단·재개·수리 호출도 포함한다.
- 코스별 키는 `featureKey::reason`. 일반 카탈로그뿐 아니라 해금 ID·레거시 reason 경로까지 비용 증거를 요구한다. 중단 키가 보수적으로 남아 비용 증거를 요구할 수 있다. 누락을 0원으로 처리하지 않는다.
- 예산 내에서 반복 구매 가능한 가장 비싼 원가 조합을 동적 계획법으로 계산한다. 표면 판매가가 가장 큰 상품만 반복한다고 가정하지 않는다.
- `(세금 제외 매출 - 최대 사용 원가 - 결제 수수료) / 세금 제외 매출 >= 40%`여야 한다. 이는 승인된 내부 목표이며 실측 수익률이나 무손실 보장이 아니다. 고정비와 판매량에 따른 사업 전체 손익은 별도다.

## 토큰 집계와 남은 실측

`node scripts/report-llm-token-usage.mjs llm.log --prices tariffs.json`으로 provider/model별 단가를 적용한다. 미등록 모델·추정 토큰은 비용 `null`, `complete:false`다. 캐시 입력·thinking 토큰을 별도로 반영한다. 단가 파일 키는 `gemini/실제모델명` 등이며 값은 `reviewedAt`, `sourceRefs`, `inputUsdPerMillion`, `cachedInputUsdPerMillion`, `outputUsdPerMillion`, `thinkingIncludedInOutput`을 포함한다. 실제 모델 청구 방식에 맞게 thinking 중복 여부를 확인한다. 파일에 실제 공급자 단가와 적용일·출처를 기록한다. 확인한 Flash Standard 단가는 `config/llm-tariffs-20260921.json`에 있다. candidatesTokenCount와 thoughtsTokenCount를 별도로 기록하므로 이 파일의 thinkingIncludedInOutput은 false다. 캐시 보관료·검색·그 외 모델과 요금제는 이 파일로 계산하지 않는다.

기존 단일 단가 모드는 추정 비교용이며 판매 증거가 아니다. 공통 LLM 클라이언트를 거치지 않던 MindScan·love-reading에도 토큰 로그를 추가했다. 요청 내용·개인정보는 새 로그에 넣지 않는다. 이력 전체의 원가가 소급 수집된 것은 아니다. 로그 유실, 타임아웃 과금, unlabeled serviceId, 공통 love-reading 경로의 실제 SKU 연결, USD→KRW 환산 근거, 저장·지원·환불 원가는 별도 실측이 필요하다. 관측 합계가 곧 허용 재시도 전체의 상한이라는 가정도 금지한다.

## 운영 적용 조건

1. 상품별 실원가·재시도 상한 증거와 최대 소진 조합이 40% 기준을 충족할 것.
2. Play 신규 SKU의 KRW 가격·국가별 상품 정보·비자동갱신 조건을 확인하고, 이전 SKU의 신규 판매 종료와 기존 영수증 복원을 함께 검증할 것.
3. 구정책 활성 이용권·미수령 선물·결제 후 미지급 주문의 복구를 실환경에서 승인받아 확인할 것.
4. 명시 승인 후 운영 승격. 실 PG·유료 LLM·운영 DB 쓰기는 별도 승인. Pages `/version.json`과 Worker `/api/version`이 승격 SHA와 일치해야 배포 완료다.
5. 승격일 +7일/+30일에 등급별 최대 사용 고객 원가·공헌이익·재구매·환불·전달 실패를 점검한다. 승격일이 아직 없으므로 점검 날짜는 확정하지 않는다.

카카오 채널 소개는 영냥이 중심 문구로 저장했고 기존 경력·예측 이력은 보존했다. 채널 이름 변경은 카카오 UI가 비즈니스 채널 제한으로 거부했다. 프로필 PNG는 준비했으나 Chrome 확장 프로그램의 파일 URL 접근 권한이 없어 업로드를 완료하지 못했다. 메시지 발송·환영 메시지 활성화는 하지 않았다.

## 추가 손익 재검토 (사용자 제공 예산)

- PG 수수료 5% 이하: 사용자 제공. 부가세 포함 여부가 미확인이므로 계산은 결제 총액의 5.5%를 사용한다. 포트원·부가서비스·건당 최소 수수료가 있다면 별도 추가한다.
- Cloudflare 기본 $5, MongoDB M10 월 100,000원 예산: 사용자 제공. 실제 송장이 아니다. 환율 1,600원/USD는 현재 환율 주장이 아닌 스트레스 가정이다. 합계 108,000원/월, 증가 시 216,000원/월도 비교한다. 추가 백업·트래픽·스토리지·이메일·지원 인건비·광고비·환차 비용이 포함됐다고 가정하지 않는다.
- Google Play 15% 프로그램 가입 미확인. 30일 비자동갱신 상품에 자동갱신 구독 15%를 적용하지 않는다. 한국 적용 약관·계정 프로그램·앱 출시일 규정을 재확인한다. 15%/30%를 모두 계산하며 미확인 상태는 30% 시나리오로 검토한다. 계산은 보수적으로 결제 총액에 수수료를 적용한다. 실제 정산의 세금 제외 기준이 확인되면 net 기준으로 계산한다. Play Billing에 웹 PG 수수료를 중복 합산하지 않는다. 한국 대체결제는 Google 수수료 감면분과 PG 비용을 함께 계산해야 하므로 별도 검토한다.
- 세금 제외 매출은 국내 VAT 10%를 가정한 판매가/1.1. 사업자의 실제 세무·정산 조건을 검증해야 한다.

허용 변동원가는 이용권 한도를 전부 썼을 때 생성·재시도·변동 서버·저장·지원·환불 충당의 합이다. 위 표는 실제 원가 또는 수익률이 아니다. 고정 서버 예산이 두 배면 손익분기 판매량도 각각 60/20/10개다. 등급별로 단독 판매하는 비교이며 혼합 판매에서는 공헌이익 합계로 고정비를 회수한다. 손익분기는 이익 0원의 경계이므로 흑자를 위해 이를 넘어야 한다. 다른 고정비가 있으면 추가한다.

VVIP의 앱 원가 여유를 30,000원 상담 3회에만 나누면 건당 약 4,900원이다. 그러나 저가 상담을 반복하는 조합이 더 비쌀 수 있어 이 수치만으로 판매를 열지 않는다. **현재 가격을 무조건 올리거나 품질·기존 권리를 줄이지 않는다.** 상품별 상한 원가가 확인되면 `passEconomics`의 `minimumPriceForTargetKRW`와 최대 소진 조합을 이용해 신규 판매 가격/누적 한도를 조정한다. 웹은 통과해도 앱이 실패하면 앱 판매만 보류한다. 같은 가격을 원하면 더 비싼 채널을 통과하는 정책으로 확정한다.

판매 증거에는 financials가 추가로 필요하다: `{ channel, basis: "reviewed", reviewedAt, sourceRefs, vatRate, feeRate, feeBasis: "gross" 또는 "net", fixedMonthlyKRW, minimumMonthlySales }`. 정산액과 수수료 합계가 일치해야 하며, 최소 월 판매량 가정에 고정비를 배분한 후에도 이익이 양수여야 한다. 최소 판매량은 보장된 매출이 아니며 근거와 민감도 검토가 필요하다. 기존 40% 공헌이익 조건과 함께 적용된다. 미검증 예산·평균 토큰만으로 evidence를 채우지 않는다.

### 비용 증가에 대한 추가 내부 판매 기준

사용자가 유지비 증가를 재차 강조하여 신규 판매 심사에 **상품별 최대 변동원가 2배, 고정 서버비 5배** 스트레스 조건을 추가했다. 이는 미래 비용의 정확한 예측이나 손실 보장이 아니라 보수적인 내부 여유분이다. 기준 예산 108,000원의 5배는 월 540,000원이며 그 이상 증가가 예상되면 더 높은 값을 사용한다. 상품 최대 원가 2배에는 환율·단가·재시도 증가 여유를 포함하며, 실제 변동 증가가 2배를 넘으면 다시 심사한다. 기존 구매의 권리를 줄이지 않는다.

증거에 `stress: { sourceRefs, productCostMultiplier: 2 이상, fixedMonthlyKRW: 기본 고정비의 5배 이상 }`를 포함한다. 이 스트레스 후에도 공헌이익률 40% 이상이고 최소 판매량 가정으로 나눈 고정비를 뺀 이익이 양수여야 판매 가능하다. 위 허용 변동원가 표는 스트레스 적용 후의 상한으로 해석한다. 따라서 실제 확인된 기본 최대 원가의 허용치는 표의 절반이다. 앱 30% 조건에서 VVIP는 기본 전체 원가 약 7,351원 이하가 필요하다. 상품별 비용이 이 기준을 넘으면 신규 가격을 올리거나 누적 한도를 줄여 재심사하며, 적정 숫자가 확인되기 전 현재 후보를 확정하지 않는다.

보고서는 고정비 2/3/5배를 모두 계산한다. 환율 2,000원/USD 가정은 달러 비용 25% 증가, 기본 서버 예산 110,000원으로 따로 표시한다. 이는 현재 환율이 아니다. 최소 판매량을 임의로 높여 심사를 통과시키지 말고 실제 매출 근거와 부진 시나리오를 함께 검토한다. 이용권 수익만으로 서버비 전체를 회수하는 보수적 계산이므로 다른 단건 매출을 이중 산입하지 않는다.
