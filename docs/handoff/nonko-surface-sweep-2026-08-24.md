## 측정 방법 (재현 가능)

`dist/` 를 정적 서버로 띄우고 `?lang=` 로 전환한 뒤, **보이는** 텍스트 노드의 한글만 센다(숨은 노드 제외).
도구는 커밋하지 않았고 scratchpad 에 있다 — 아래 "도구" 절.

```bash
npm run build:cf                       # dist 생성. 끝나면 build 가 건드린 추적 파일을 되돌린다
node tmp-locale-collect.mjs <routes.txt> <out.json> en 6
```

## 🔴 다음 세션이 알아야 할 것

### 1. 전달 경로는 이미 있다 — 마크업을 고칠 필요가 없다

`repairUnmarkedKoreanText`(`lib/i18n/dictionary.ts:186`)가 **한국어 원문 역인덱스**로 마커 없는 텍스트 노드를 치환한다.
같은 로직이 정적 셸에도 이중 구현돼 있다(`js/cd-lang-native.js:435`). 둘 다 `REPAIR_NAMESPACE = "shellRuntime"` 하나만 읽는다.

실험으로 확인했다(2026-08-24): `dist/i18n/{ko,en}/shellRuntime.json` 에 문자열을 넣자 `/saju/?lang=en` 에서 즉시 치환됐다.
**즉 React 페이지든 정적 셸이든, 사전에 ko 원문과 번역을 넣기만 하면 된다.**

- ko 는 repair 가 즉시 반환하므로 **한국어 화면은 영향을 받지 않는다.**
- 역인덱스는 **2자 미만을 넣지 않는다.** 1글자 라벨(`월`·`수`·`금`)은 이 경로로 못 고치고, 넣어서도 안 된다(오행/요일 중의성).

### 2. 🔴 상당수는 "조각"이라 사전으로 고칠 수 없다

`{별자리}의 행운 포인트` 처럼 JSX 변수 사이에서 잘린 텍스트 노드다. 실제로 남아 있는 것들:

```
의 행운 포인트 / 와 잘 맞는 상대 / 는 어떤 기질인가 / 의 운세 점수 / 의 기본 결
가 늘 지니는 성향입니다. 위의 점수·관계가 …
```

한국어는 조사가 뒤에 붙어 이렇게 잘려도 읽히지만, **어순이 다른 언어에서는 문장이 성립하지 않는다.**
이건 소스에서 **보간 키로 승격**해야 한다(`t("luckPoint", { sign })`). 사전에 조각을 넣지 말 것 — 넣으면 영어 화면이 더 이상해진다.

조각이 몰려 있는 곳: `/fortune/*` 템플릿(약 100 라우트), `/nakshatra/*`(27 라우트).

### 3. 사업자 정보 4건은 고칠 대상이 아니다

`SiteFooterHub.jsx:228` 이 `data-cd-no-trans` 로 명시 제외한다 — 상호·대표자·신고번호·주소는 **등록된 그대로가 법적 형식**이다.
`verify-i18n-public-parity.mjs` 도 `LEGAL_VERBATIM_KEY` 로 이 키들만 "한글이면 실패"가 아니라 "ko 와 다르면 실패"로 검사한다.
252개 라우트에서 한글로 잡히지만 **정상이다.** "한국어 0" 의 정당한 예외로 남긴다.

같은 성격의 예외가 하나 더 있다: `withdrawModal.confirmMismatch` 의 `회원탈퇴`.
`worker/routes/auth.js` 가 confirmText 를 그 리터럴로 검증하므로 안내 문구도 그 단어를 인용해야 한다.
**비한국어 사용자에게 한글 입력을 요구하는 UX 문제는 남아 있다** — 고치려면 서버 검증까지 같이 바꿔야 하므로 별건이다.

### 4. 정책 페이지는 번역이 아니라 **라우팅** 문제다

`/terms/` 는 한글 4,904자인데 `/en/terms-of-service/`·`/ja/...`·`/zh/...` 에 **완역본이 이미 있다**(각 110자만 한글 = 사업자 정보).
`lib/i18n/routes.ts` 의 `I18N_ROUTE_MAP` 에는 정책 라우트 키가 없어서 푸터가 로케일과 무관하게 `/terms/` 로 보낸다.
번역을 새로 만들지 말고 **링크를 로케일 라우트로 보내는 것**이 맞다.

### 5. 셸 푸터에 5개 로케일 표를 import 하지 말 것

`SiteFooterHub.jsx:29` 에 근거가 있다 — `AppChrome`("use client")이 이 파일을 import 하므로
`lib/i18n/siteFooterHubCopy` 를 끌어오면 layout 청크가 41KB → 63KB 가 된다(2026-08-16 실측).
그래서 이 표면의 정답은 **런타임 사전**이다. 위 1번이 그 이유다.

### 왜 `f*` 접두사인가

`shellRuntime` 네임스페이스의 `s<N>` 키는 `scripts/i18n-extract-runtime-ui.mjs` 가 **재생성**한다(인덱스가 밀린다).
`f*` 는 손으로 저작한 계열이라 그 재생성과 충돌하지 않는다. 이어서 저작할 때도 `f*` 를 쓸 것. 현재 최대는 `f203`.

### 저작 파일 자체 검사

`merge-authored` 는 "12개 로케일 누락"과 "비-ko 한글"만 본다. 그것만으로는 부족해서 별도 체커를 썼고,
실제로 **네덜란드어에 키릴 문자 `е` 가 섞인 오타**를 잡았다(`Geluksklеur`). 커밋하지 않았으니 scratchpad 에서 가져다 쓸 것.
검사 항목: 12로케일 누락 / 비-ko 한글 / 키릴 혼입 / 라틴권에 CJK·데바나가리 혼입 / hi 에 데바나가리 없음 /
**ko 원문이 실제 렌더 목록에 있는가**(마지막 항목이 제일 중요하다 — 오타 나면 그 키는 영원히 안 걸린다).

### 🔴 링크로 갈린 조각은 번역해도 된다 — 변수로 갈린 조각과 다르다

`제작 기준은 [링크] 와 [링크] 에서 확인할 수 있습니다` 처럼 **인라인 링크**로 끊긴 조각은
가운데 들어가는 것이 임의값이 아니라 **이미 번역된 링크 라벨**이다. 그래서 앞뒤 조각을 언어별로
다시 분배해 번역하면 문장이 성립한다. 실제로 그렇게 했고, 분배가 언어마다 다르다:

- en 은 뒤 조각이 `.` 한 글자로 줄고 앞 조각이 길어진다
- de 는 링크 라벨이 주격 고정이라 앞 조각을 `… enthält` 로 바꿔 격 충돌을 피했다
- hi 는 후치사가 필요해 뒤 조각이 `में देखा जा सकता है।` 로 길다

### 🔴 한 글자는 사전으로 못 고친다 — 마커를 쓴다

역인덱스(`buildKoReverseIndex`)는 **공백 정규화 후 2자 미만을 버린다**. 그래서 `홈`·`와`·요일(`월`·`화`)·
오행(`목`·`화`·`토`·`금`·`수`)은 사전에 넣어도 **영원히 매칭되지 않는다.**

실제로 PR #1099 에서 `홈`(f97) 을 넣었다가 죽은 키가 됐다. 제거하고, **코어 사전에 이미 있던**
`home.nav.home` 을 `data-cd-trans` 마커로 5곳에 붙여 해결했다.
🔴 **마커 키는 코어 사전에서만 해석된다**(`LocaleRuntimeBridge` 가 네임스페이스 없이 `loadDictionary` 를 부른다).
`shellRuntime` 네임스페이스에 넣으면 안 된다.

남아 있는 한 글자 노드는 46개(라우트 가중 651). 대부분 주간 표의 `weekdayKo` 와 지지·오행 표기다.
요일은 소스에서 로케일 인지로 바꿔야 하고, 지지·오행은 도메인 표기라 그대로 두는 편이 맞을 수 있다 —
**사용자 판단이 필요하다.**
