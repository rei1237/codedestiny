# 2026-10-01 영냥이 자미두수 강약 상담 + 설명마다 명반 — 사용자 요구 원문

> 사용자가 대화에 붙여 넣은 브리프 원문이다. 다음 세션은 이 원문을 볼 수 없으므로 그대로 보존한다.
> 예외: 줄 끝 공백만 지웠다(`git diff --check` 차단 회피). 문장은 고치지 않았다.
> 진행·결정·남은 작업은 [진행 문서](2026-10-01-ziwei-strength-consultation.md).

당신은 자미두수 고전 연구자이자 숙련된 상담가, 시니어 개발자다

Code Destiny의 영냥이 자미두수 상담을 실제로 분석하고 수정하라

현재 결과는 기본적인 별의 성질은 설명하지만 각 궁에 배치된 별의 묘왕리함 등 강약을 충분히 반영하지 못한다
이를 개선해 별의 이름만 풀이하는 상담에서 벗어나, 실제 명반의 강약·동궁·삼방사정·사화·보조성과 살성의 관계를 종합하는 전문 상담으로 업데이트하라
추가로 설명을 할때마다 각 명반을 보여주면서 할 수 있도록 수정하라
이것은 자미두수 뿐만이 아니라 모든 운세 서비스에서 그렇게 적용이 되어야한다. 한 세션에서 어렵다면 인수인계로 넘겨서 이 작업은 완벽하게 진행한다.

기획이나 프롬프트 제안으로 끝내지 말고 현재 코드의 데이터 흐름과 상담 생성 로직을 확인한 뒤 구현하고 검증하라

## 1. 먼저 실제 원인을 찾아라

영냥이 자미두수의 명반 생성 → 서버 저장 → 상담 입력 데이터 → LLM 프롬프트 → 결과 표시까지 추적하라

다음을 구분해서 확인하라

- 명반 엔진에 강약 데이터가 원래 없는가
- 엔진에는 있으나 직렬화·저장 과정에서 누락되는가
- 저장되어 있으나 LLM에 전달되지 않는가
- 전달되지만 프롬프트가 사용하도록 요구하지 않는가
- 실제로 사용하더라도 별의 기본 성격을 반복하는 수준인가
- 꿀꿀 운세와 영냥이가 서로 다른 강약표나 해석 규칙을 사용하는가

별의 강약, 궁의 중요도, 사화의 작용, 상담 문장의 확신도를 서로 다른 개념으로 구분하라

기존 결과 몇 건을 개인정보를 제거한 상태로 비교하고 원인을 파일과 함수 단위로 특정하라

## 2. 강약 데이터를 신뢰할 수 있게 정리하라

현재 엔진이 채택한 강약표와 유파를 먼저 확인하라
검증 없이 다른 유파의 표로 교체하거나 여러 표를 섞지 말라

묘(廟), 왕(旺), 득지(得地), 리·이익(利·利益), 평(平), 부득지(不得地), 함(陷) 등의 표현은 실제 원본 체계에 맞춰 정규화하라

모든 엔진이 같은 등급 수나 분류를 쓴다고 가정하지 말라
원문 표기와 정규화 값을 함께 보존하고, 알 수 없는 값이나 없는 값은 임의로 평 또는 함으로 바꾸지 말라

각 별에 다음 정보가 연결되도록 하라

- 고유 식별자와 한글·한자 이름
- 실제 위치한 궁과 지지
- 주성·보조성·살성 등 엔진의 분류
- 원본 강약 표기와 정규화 값
- 강약표의 출처·유파·버전
- 생년사화 및 실제 제공되는 운한 사화
- 해당 궁과의 동궁·대궁·삼합 관계
- 누락·충돌·미지원 여부

강약표 적용은 검증된 서버 로직으로 수행하라
LLM이 기억에 의존해 별과 지지만 보고 강약을 계산하게 하지 말라

14주성은 채택한 표를 기준으로 전수 확인하라
보조성·살성·잡요는 해당 체계에 강약 규정이 확인되는 경우에만 적용하고, 모든 별에 주성의 등급을 억지로 부여하지 말라

화록·화권·화과·화기는 기본적으로 해당 별에 적용되는 변화 정보로 다루며, 임의로 별도의 강약 등급을 만들지 말라

## 3. 실제 상담에 적용할 해석 원칙

각 궁의 주요 해석은 다음 순서로 종합하라

① 궁의 주제와 주성의 기본 성질
② 주성 각각의 강약에 따른 발현 방식
③ 동궁한 별 사이의 협력·긴장
④ 보조성·살성·공겁 등의 보완·부담 조건
⑤ 해당 층위의 사화
⑥ 삼방사정의 지원·충돌
⑦ 실제로 제공된 대운·유년 등의 시기 조건
⑧ 고객의 질문과 연결되는 현실적인 해석과 조언

이 순서는 읽기 위한 틀이며 고정된 수치 가중치 공식으로 만들지 말라

반드시 다음 원칙을 지켜라

- 묘왕이라고 무조건 좋은 결과를 단정하지 말라
- 함이라고 무조건 실패·불행을 단정하지 말라
- 별의 작용이 강한 것과 그 작용이 유익한 것을 구분하라
- 강약에 따라 해당 별의 장점, 부담, 안정성, 발휘 조건이 어떻게 달라지는지 설명하라
- 길성의 지원이 있다고 불리한 조건이 완전히 사라진다고 쓰지 말라
- 살성이나 화기가 있다고 모든 장점이 무효가 된다고 쓰지 말라
- 화록·화권·화과·화기의 작용을 주성의 성질과 강약에 연결해 읽어라
- 같은 궁에 주성이 둘 이상 있으면 각각의 강약과 조합을 설명하고 평균 점수로 합치지 말라
- 빈궁은 채택한 유파의 검증된 규칙에 따라 대궁과 삼방을 살피고, 차성 여부를 구분하라
- 차성한 별을 실제 본궁에 있는 별처럼 기록하지 말고 원래 위치와 강약을 보존하라
- 동궁·회조·대궁·협궁을 혼동하지 말라
- 격국은 실제 성립 조건과 파격 조건을 확인한 경우에만 적용하라
- 일월 등의 추가 조건은 관련 데이터와 채택한 규칙이 확인될 때만 사용하라

본명반의 강약과 대운·유년의 활성화는 구분하라
운한의 궁에 겹쳐 보인다는 이유만으로 본명성의 원래 강약을 새로 계산하지 말라
별도의 운한 배반을 제공하는 엔진이라면 그 층위와 출처를 명확히 구분하라

데이터에 없는 비성사화·자화·운한을 만들어 넣거나 다른 점술 체계를 섞지 말라

## 4. 고서의 원칙을 실제 근거로 연결하라

『紫微斗數全書』의 「諸星問答」「談星要論」 등 확인 가능한 원문을 우선 검토하라
『紫微斗數全集』 및 관련 부·론은 실제 접근하고 원문과 맥락을 검증한 자료만 추가하라

“모든 고서를 섭렵한 전문가”라는 역할 문구만 넣고 근거 없는 해석을 생성하지 말라

해석 규칙에는 다음을 남겨라

- 규칙 식별자
- 문헌명과 편·장 또는 위치
- 확인한 판본이나 링크
- 적용 조건과 예외
- 현대 상담을 위한 해석 요약
- 고전의 직접 진술인지 현대적 확장인지 구분

판본이나 유파 사이에 차이가 있으면 숨기지 말고 채택 기준을 기록하라
고서의 저자·연대·원문을 확인 없이 단정하지 말라
검증되지 않은 문장을 고서의 인용문처럼 작성하지 말라

고서 전체를 매번 LLM에 넣지 말고 해당 명반에 적용되는 검증된 규칙만 선별해 전달하라

고전의 신분 차별, 성별 편견, 형극·요절 등의 표현은 고객에게 그대로 단정하지 말라
현대 상담에서는 관련 주제의 부담과 대응 조건으로 설명하되, 고전의 문장과 현대적 재해석을 내부적으로 구분하라

고전의 전통적 해석을 과학적으로 입증된 예측처럼 소개하지 말라

## 5. 상담 생성 프롬프트를 다음 기준으로 개편하라

영냥이의 친근한 말투는 유지하되 본문은 숙련된 자미두수 상담가의 깊이로 작성하라
귀여운 표현이 근거 설명을 대신하지 않도록 하라

고객이 질문한 주제를 먼저 답하고, 그 결론에 사용한 궁과 별의 강약을 자연스럽게 설명하라

각 핵심 궁의 해석에는 다음 흐름을 적용하라

- 이 궁에서 두드러지는 주제
- 실제 주성의 이름과 강약
- 그 강약이 성향과 사건의 전개 방식에 미치는 해석
- 사화·동궁·삼방사정이 결론을 보완하거나 제한하는 이유
- 생활에서 나타날 수 있는 구체적인 양상
- 활용할 장점과 조심할 행동
- 판단에 필요한 정보가 부족한 경우 그 한계

“무곡이 있으니 재물운이 좋다” 같은 별 이름 중심의 문장으로 끝내지 말라
무곡의 실제 강약과 사화, 동궁 구성, 관련 궁의 지원·부담을 연결해 어떤 방식으로 재물을 다루는 성향인지 설명하라
이 예시를 특정 고객의 실제 결론으로 복사하지 말라

묘왕리함 용어는 처음 등장할 때 짧게 풀어 설명하고 이후에는 읽기 쉬운 한국어로 이어가라

내부적으로 중요한 해석 문장이 어떤 궁·별·강약·규칙에 근거했는지 추적할 수 있게 하라
고객 화면에는 개발용 필드나 규칙 코드를 노출하지 말고 필요한 근거만 보여라

전체 명반 데이터는 모든 가격 단계의 상담에 제공하라
가격별 차이는 설명의 깊이와 범위에 두고, 저가 상담이라고 정확성에 필요한 강약·사화·삼방 데이터를 빼지 말라

상품의 분량과 질문별 구성은 현재 정의를 확인한 뒤 유지·개선하라
문장을 늘리기 위한 반복이나 모든 궁에 같은 상투적인 조언을 붙이는 방식은 금지한다

시기 해석은 실제 제공된 운한과 기간 안에서만 작성하라
연애·결혼·직업·재물 등의 주제도 관련 궁들을 함께 살펴 해석하고, 별 하나로 결혼일·수익액·합격 여부 등을 확정하지 말라

## 6. 결과 화면과 기존 저장 결과도 정리하라

현재 명반에서 강약을 빠르게 확인할 수 있도록 별 이름 옆에 원본 체계에 맞는 작은 표기를 제공하라

색상만으로 구분하지 말고 텍스트를 함께 사용하라
모바일에서 한자와 등급이 읽히도록 하고, 강약을 누르면 짧은 설명을 볼 수 있게 하라

핵심 궁의 해석에서 “이 별의 강약을 어떻게 읽었는지”를 확인할 수 있도록 하되 모든 기술 정보를 처음부터 펼치지 말라

강약을 좋은 점수·나쁜 점수로 바꾼 임의의 운세 게이지는 만들지 말라

기존 구매 결과를 몰래 덮어쓰지 말라
원본 명반과 이전 해석을 보존하고, 강약 반영 재해석을 제공한다면 버전을 구분하라
기존 주문의 재해석이나 복구가 새 결제를 요구하지 않도록 기존 권한을 확인하라

영냥이 자미두수의 실제 상담 경로와 상품별 생성 경로를 모두 찾아 적용하라
공유 모듈을 수정하면 꿀꿀 운세 자미두수에 미치는 영향도 확인하라

## 7. 완료 기준과 검증

실제 유료 LLM 호출은 별도 승인 범위가 확인되기 전까지 실행하지 말고 mock과 고정 fixture로 먼저 검증하라

다음을 확인하라

- 원본 명반의 강약이 저장·상담 입력·화면까지 누락 없이 전달됨
- 채택한 표의 14주성 × 12지지 강약 대응이 검증 자료와 일치함
- 없는 강약 값과 미지원 별이 정상적으로 구분됨
- 알려진 필드명·한자 표기 차이가 정규화됨
- 같은 별의 강약만 바꾼 합성 fixture에서 적용 해석 규칙과 상담 지침이 달라짐
- 묘왕에 부담 조건이 있는 사례와 함지에 지원 조건이 있는 사례를 구분함
- 쌍성·빈궁·차성에서 위치와 강약이 뒤섞이지 않음
- 생년사화와 대운·유년사화가 섞이지 않음
- 제공하지 않은 별·강약·격국·시기를 생성하지 않음
- 실제 궁 관계와 다른 삼방사정을 사용하지 않음
- 각 가격 단계에서도 핵심 판단 근거가 유지됨
- 기존 구매 결과 조회·복구가 정상 작동함

합성 fixture는 로직 검증용임을 명시하고 실제 성립 가능한 명반의 사례와 구분하라
mock 검증으로 실제 LLM 상담 품질까지 입증했다고 보고하지 말라

최종 보고에는 발견한 원인, 변경 파일, 채택한 강약표와 문헌 기준, 수정 전후 상담 차이, 검증 결과, 남은 제한을 포함하라

목표는 모든 문장을 긍정적으로 만드는 것이 아니다
