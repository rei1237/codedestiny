## 0. 한 줄 요약

🔴 **먼저 알아야 할 것 — 이 사이트는 CrUX 에 데이터가 없다**(2026-08-28 실측, 8개 조합 전부 404).
그래서 **이 문서의 모든 CWV 판정은 랩 값 하나뿐이고, 구글은 이 사이트의 CWV 를 보고 있지 않다.**
CWV 를 SEO 근거로 삼는 대공사는 착수 근거가 없다 — 재현은 `npm run perf:crux`. §8-5 의 0번

✅ **그와 별개로 LCP 는 한 번 잡혔다** — 프로덕션 **3,116 → 2,632**(2026-08-28 승격, PR #1212).
레버는 "첫 화면에서 **안 쓰이는** 인라인 `<style>` 21개를 히어로 뒤로" 하나였다. §8-4-1

홈의 **LCP 는 순서 문제가 아니라 예산 문제다** — 히어로가 그려지기까지 회선을 건너야 하는 바이트가
**465KB**(문서 240KB + CSS 97KB + JS 75KB + 그 외 64KB)이고, 1.6Mbps 에서 **그 전송만으로 2,327ms** 다.
그래서 **바이트를 줄이는 안만 살고, 옮기기만 하는 안은 전부 죽었다**(§2-3 에 기각 5건).
🔴 이 문서 1차 작성분이 "다음 착수점"으로 지목했던 **§4-A(히어로 앞 파서 차단 스크립트 8개)는
2026-08-28 재측정에서 기각됐다** — 8개를 **통째로 지워도** LCP 는 56ms 밖에 안 줄었다(§8).
**INP 는 핸들러가 아니라 "다음 프레임을 그리는 비용"(스타일 재계산)** 이 좌우한다.
🔴 **그 INP 568ms 는 승격 전 값이라 지금은 미검증이다 — 다음 착수점이 그 재측정이다**(§8-5 의 2번).
**부팅 게이트는 LCP 의 원인이 아니다** — 실측으로 확인했다.

## 3. INP 568ms 의 정체 — 핸들러가 아니라 프레젠테이션 지연

게이트 해제 후 6초 정착시킨 뒤 12개 요소를 탭한 결과:

|---:|---:|---:|---:|---|
| **568** | 2 | **0** | **566** | `A.cd-mobile-bottom-nav__item` (`data-nav-key="fortunes"`) |

### B. 부팅 게이트 조기 해제 — 체감 전용, CWV 무관

사용자는 **7.6초간 베일만 본다**(1.2s→8.8s). §2-1 대로 LCP 숫자는 안 바뀐다.

- 🔴 **CWV 개선으로 보고하면 안 된다.** 이탈·체감 개선 과제로 분리할 것.
- 코드: `index.html` 의 `data-marker="cd-boot-gate-release-v20260730"` 블록.
  게이트는 `dom`·`auth`·`profile` 세 신호를 기다리는데, **비로그인 진입은 이미 `auth`·`profile`
  을 즉시 마킹**하므로 실질적으로 `DOMContentLoaded`(7.7~8.2초)만 기다린다.
  그 DCL 이 늦는 이유는 §4-C 의 파서 차단 스크립트 24개(717KB)다.
- 하드 상한은 비딥링크 8,000ms · 딥링크 5,000ms 이고, 그 8초의 근거(이용권 재시도 6.5초)가
  코드 주석에 적혀 있다 — **줄이려면 그 근거부터 다시 볼 것.**

### C. 스타일 재계산 범위 축소 — INP·TBT 의 진짜 원인, 대공사

- 홈 전체 파서 차단 `<script src>` 는 **24개 717KB**(상위 2개가 306,002B + 246,748B = 553KB).
  이들은 `scripts/externalize-dist-inline-scripts.mjs` 가 만든 것이고, **의도적으로 `defer` 가
  없다** — 남은 인라인 블록과의 실행 순서를 보존해야 하기 때문이다(그 스크립트 머리말에 근거).
  전부 defer 로 바꾸려면 8KB 미만 인라인 블록 53개까지 함께 외부화해야 순서가 유지된다.
- 🔴 그런데 INP 의 원인은 스크립트가 아니라 **클래스 토글의 무효화 범위**다(§3).
  셸 CSS 는 `!important` 4,990개에 `html body .x` 류 셀렉터가 많아 문서 전체를 무효화한다.
- 손대려면 범위를 먼저 자를 것: **하단 탭바 `is-active` 토글 한 경로만** 잡고
  `Performance.getMetrics` 의 `RecalcStyleCount` 로 전후를 재는 것이 최소 단위다.

### D. TTFB / 문서 캐시 — [seo-followups-2026-08-27.md](seo-followups-2026-08-27.md) §4 와 한 묶음

HTML 이 Worker 를 타고 `no-cache`·`cf-cache-status: DYNAMIC` 으로 나가 ETag 재검증이 없다.
TTFB ~650ms 는 기준 안이라 LCP 기여도는 A 보다 작다. 사용자가 2026-08-27 에 보류한 항목이다.

## 8. §4-A 착수 결과 — 기각, 그리고 LCP 의 진짜 제약 (2026-08-28, 같은 날 후속)

측정 대상은 **프로덕션 문서**(build `2988b09bdc58`) 하나이고, 조건은 §5 와 같다
(390×844 · DPR 3 · CPU 4x · Slow 4G 1.6Mbps/150ms).

🔴 **하네스가 §1 과 다르다 — 숫자를 §1 과 직접 빼지 말 것.** 여기서는 로컬 프록시가
문서를 내주므로 TTFB 가 ~20ms 다(프로덕션은 ~650ms). 그래서 **절대값이 §1 보다 낮게 나오고,
아래 판정은 전부 같은 하네스 안에서의 변형 간 차이로만 한다.** 베이스라인 A 의 절대값
2,440ms + 프로덕션 TTFB 617ms ≈ 3,057ms 로 §1 의 중앙값 3,116ms 와 맞는다.

재현: `npm run perf:lcp-budget -- --variants=A,B,C --runs=5` / `--variants=A,D,E --runs=5`

### 8-1. 파서 차단 스크립트 8개 — 지워도 안 움직인다 (중앙값 5회)

| 변형 | 내용 | LCP | vs A | FCP | CLS |
|---|---|---:|---:|---:|---:|
| A | 베이스라인 | **2,440** | — | 1,600 | 0 |
| B | 8개를 같은 자리에 인라인(요청 0회, 의미 동일) | 2,472 | **+32** | 1,576 | 0 |
| C | 8개 **삭제**(상한. JS 의미가 깨진다) | 2,384 | **−56** | 1,564 | 0 |

A 한 변형의 회차 편차만 2,288~2,472(**184ms**)다. **−56ms 는 그 안이다.**
"몇 개만 내려도 수백 ms" 라는 1차 작성분의 기대는 근거가 없었다 — 요청 8개는 프리로드
스캐너가 병렬로 당겨오고, 실행 합계도 4x 스로틀에서 이 정도 규모로는 유의미하지 않다.

### 8-2. 히어로 앞 인라인 `<style>` 을 뒤로 내리면 **크게 나빠진다** (중앙값 5회)

`<body>` 안·히어로 앞에 있는 인라인 `<style>` **32개(202,023B)** 를 옮겼다.

| 변형 | 옮긴 곳 | 히어로 앞 gzip | LCP | vs A | CLS | LCP 요소 |
|---|---|---:|---:|---:|---:|---|
| A | — | 122,645 | **2,440** | — | 0 | `H1.moon-hero__title` |
| D | `</body>` 직전 | 88,794 | 3,800 | **+1,292** | **0.403** | `IMG.cd-hero-island__img` |
| E | 히어로 `</header>` 직후 | 88,794 | 3,780 | **+1,272** | **0.483** | 회차마다 바뀜 |

히어로 앞 바이트를 **33,851B(gzip) 줄였는데도** 나빠졌다. 이유는 명확하다 — 히어로가
**스타일 없이 먼저 그려지고**, 그 상태에서는 LCP 후보가 더 큰 히어로 이미지로 넘어간다.
그리고 뒤늦게 규칙이 도착하며 시프트가 3~5건 터진다([late-css-blocks-are-cls-in-the-shell]
가 말하던 것과 같은 함정이다).

### 8-3. 그러면 무엇이 LCP 를 잡고 있나 — **회선 예산**

`npm run perf:lcp-budget` 의 예산 덤프(베이스라인 1회):

| 항목 | 회선 바이트(gzip/br) | 해제 후 |
|---|---:|---:|
| 문서 | 240,301 | 1,247,099 |
| 렌더 차단 CSS 7개 | 97,066 | 501,407 |
| JS 26개 | 74,764 | 197,161 |
| 그 외(이미지·폰트 등) | 64,488 | — |
| **합계** | **476,619 (465KB)** | — |

**1.6Mbps = 200KB/s 에서 465KB 는 그 전송만으로 2,327ms** 다. 측정된 LCP 2,440~2,772 와
거의 그대로 맞는다. 즉 홈 LCP 는 **대역폭에 묶여 있고**, 그래서 순서를 바꾸는 안(§2-3 의 1·2·4·5)이
전부 죽은 것이다.

문서 240KB 중 **히어로 앞이 122,645B(51.1%)** 이고 그 몸통은 인라인 `<style>` 72개다(§2-2).

🔴 **"인라인 CSS 를 중복 제거해서 줄인다"는 안도 미리 지운다** — 히어로 앞 인라인 CSS
542,848B 를 규칙 단위 1,582개로 쪼개 보면 **완전 중복은 1건(0.1%)** 뿐이다. 전부 서로 다른
규칙이라 dedup 으로 돌려받을 바이트가 없다. 줄이려면 **안 쓰는 규칙을 걷어내는**
커버리지 작업뿐이고, 그건 §8-2 가 보여준 CLS 위험을 그대로 안고 가는 대공사다.

렌더 차단 CSS 쪽 확인 결과(전수, 프로덕션 문서 1개 기준):
- 진짜 렌더 차단은 **7개**뿐이다. head 의 나머지 `<link rel="stylesheet">` 12개는 전부
  `<noscript>` 폴백이거나 `data-cd-noncritical-style-src` + `media="print"` 지연 로딩이다.
  **워터폴에서 요청조차 되지 않는다** — 이미 정리돼 있으니 다시 파지 말 것.
- 큰 둘은 `fortune-ui-home.css`(36,066B) · `cosmic-main.css`(36,040B) 로 CSS 예산의 74% 다.
- `fonts-serif.css`(27,691B)는 `media="print"` + `onload` 라 렌더를 막지 않지만 **LCP 창 안에서
  회선을 쓴다**. 바로 아래의 같은 파일 `<link>` 는 `<noscript>` 안이라 중복이 아니다(오진 주의).

### 8-4. 🟢 살아 있는 레버 하나 — 첫 화면에서 **안 쓰이는** 인라인 `<style>` 만 뒤로

§8-2 가 죽은 이유는 "히어로 앞 인라인 CSS 를 **전부**" 옮겼기 때문이다. 히어로를 그리는 규칙까지
같이 내려가니 히어로가 맨몸으로 먼저 그려졌다. **그럼 안 쓰이는 것만 골라 내리면 되지 않나** —
재 보니 **된다.**

먼저 첫 화면 CSS 사용률을 쟀다(`page.coverage`, 390×844, **스크롤 없음**, 게이트 해제 후 3초):

| | 전체 | 첫 화면 사용 | 사용률 |
|---|---:|---:|---:|
| 외부 `.css` 8개 | 599,094 | 103,939 | **17.3%** |
| 문서 인라인 `<style>` 84개 | 648,149 | 157,342 | **24.3%** |
| **합계** | **1,247,243** | **261,281** | **20.9%** |

개별로는 `cosmic-main.css` 23.2% · `fortune-ui-home.css` 17.2% · `core-ui.css` 10.4% 다.

🔴 **"미사용 = 삭제 가능"이 아니다.** 커버리지는 `@font-face`·`@keyframes`, hover/JS 토글로만
켜지는 규칙을 전부 미사용으로 센다(`fonts-serif.css` 가 0.0% 로 찍히는 이유). **뒤로 미루는**
판단에만 쓸 수 있는 숫자다.

그 숫자로 만든 변형 F — 히어로 앞 인라인 `<style>` 72개 중 **첫 화면 사용 0B 인 27개(133,222B)**
만 `</body>` 앞으로 옮긴다(대상은 손으로 적지 않고 매 실행 커버리지로 발견한다):

| 변형 | 히어로 앞 gzip | LCP (n=9 중앙값) | 밴드 | CLS | LCP 요소 |
|---|---:|---:|---|---:|---|
| A | 122,645 | 2,404 | 2,256~2,592 | 0 | `H1.moon-hero__title` |
| **F** | **100,329** | **2,216 (−188ms)** | 2,188~2,356 | **0** | `H1.moon-hero__title` |

**9회 중 8회에서 F 가 이겼다.** 밴드는 겹치므로(이 레포의 통상 판정 기준) 근거는 **쌍대 비교**다 —
1차 5회(4승)까지 합치면 **14쌍 중 12승**, 부호검정 p≈0.013. CLS 0 과 LCP 요소가 그대로인 것이
D/E 와 결정적으로 다른 점이다.

재현: `npm run perf:lcp-budget -- --variants=A,F --runs=9`

### 8-4-1. ✅ 반영 완료 — PR #1212, 프로덕션 승격 2026-08-28

**셸에 들어갔다.** 대상은 27개가 아니라 **21개**다. 뺀 3종과 이유:

| 뺀 것 | 이유 |
|---|---|
| `lsd-styles-placeholder` | JS 주입 대상인 빈 블록(이득 0B) |
| `featured-content-card-premium-polish-v20260703` | 🔴 정적 충돌 검사에서 **유일하게 실제 승자 뒤집힘 8건** — `#mobileRecommendedCards` 카드의 padding/gap/border-radius/font-size 가 `cd-mobile-flower-readable-v20260704` 과 **같은 셀렉터·같은 `!important`** 라 순서로 갈린다 |
| id 없는 블록 4개(6,185B) | dist↔소스 대응을 id 로 감사할 수 없어 제외 |

🔴 **위 "27개 ↔ 24개로 흔들린다"는 걱정은 실측으로 지웠다** — 4회차를 돌려 보니 **매번 정확히
같은 27개**였다(흔들림 0건). 흔들린 것은 회차가 아니라 스크래치 하네스와 레포 도구의 구현 차이였다.

**회귀 확인은 두 갈래로 했고 둘 다 0건이었다:**
1. **정적 캐스케이드 충돌 전수 검사** — 위 1건을 빼서 0건. 🔴 이 검사는 두 위양성을 반드시 걸러야
   쓸 만해진다: `@keyframes` 스텝(`0%`·`to`)은 셀렉터가 아니고, **`!important` 여부가 다른 쌍은
   순서와 무관하게 승자가 정해진다**(147건 → 15건 → 8건).
2. **런타임 computed style 전수 대조** — 요소 **1,954개 × 속성 42개**, 차이 **0건**.
   🔴 **A-vs-A 대조군이 필수다** — 없이 돌렸을 때 `#cdReviews` 가 `display:none → block` 으로 보여
   없는 회귀를 만들 뻔했다(비동기로 채워지는 섹션이 빨라진 변형에서 스냅샷 창에 들어온 것뿐).
