🔴 **다만 §3·§3-1 의 값과는 조건이 달라 그대로 비교하면 안 된다**(2026-08-28 실측으로 확인):
**네트워크 스로틀을 안 건다**(CPU 4x 만) · 정착이 **로드 기준 6초**라 게이트 해제 전에 탭이 들어간다 ·
하단 탭바 대상이 `data-nav-key='pass'` 이고 **이동을 막고 재서 렌더 성분을 신뢰하지 않는다**.
그 조건에서의 같은 날 프로덕션 값은 최악 **232ms [232–304]**(모바일 컬렉션 탭, 처리 0 / 렌더 231)이고,
**"처리 ≈ 0, 렌더가 전부"라는 결론만 §3-1 과 일치**한다. 이 도구는 못 잰 대상이 있으면 exit 1 이라
지금 프로덕션에서는 `#cdServiceSearchInput` 없음 · 컬렉션 펼치기 timeout 으로 **항상 실패로 끝난다**.

아래 나머지는 여전히 스크래치에서 손으로 돌린 것들이다.
전부 Playwright(`require.resolve('playwright')` = 저장소 루트 설치본) + CDP 다.

+ `Emulation.setCPUThrottlingRate({rate:4})`.

| 재고 싶은 것 | 방법 |

`zrt_lookup`) · 구글 iframe **3개** · `ins.adsbygoogle` **1개**였다.
그리고 문서에서 `250px` 문자열이 **사라졌다**(`bodyMinHeight250: false`) — 예약이 실제로 걷혔다.

LCP 편차(2.1~5.4초)는 이 측정의 관심사가 아니다. 홈 LCP 는 §1·§8 을 볼 것.

## 8. §4-A 착수 결과 — 기각, 그리고 LCP 의 진짜 제약 (2026-08-28, 같은 날 후속)

측정 대상은 **프로덕션 문서**(build `2988b09bdc58`) 하나이고, 조건은 §5 와 같다
(390×844 · DPR 3 · CPU 4x · Slow 4G 1.6Mbps/150ms).

🔴 **하네스가 §1 과 다르다 — 숫자를 §1 과 직접 빼지 말 것.** 여기서는 로컬 프록시가
문서를 내주므로 TTFB 가 ~20ms 다(프로덕션은 ~650ms). 그래서 **절대값이 §1 보다 낮게 나오고,
아래 판정은 전부 같은 하네스 안에서의 변형 간 차이로만 한다.** 베이스라인 A 의 절대값
2,440ms + 프로덕션 TTFB 617ms ≈ 3,057ms 로 §1 의 중앙값 3,116ms 와 맞는다.

재현: `npm run perf:lcp-budget -- --variants=A,B,C --runs=5` / `--variants=A,D,E --runs=5`

### 8-1. 파서 차단 스크립트 8개 — 지워도 안 움직인다 (중앙값 5회)

| 변형 | 내용 | LCP | vs A | FCP | CLS |
|---|---|---:|---:|---:|---:|
| A | 베이스라인 | **2,440** | — | 1,600 | 0 |
| B | 8개를 같은 자리에 인라인(요청 0회, 의미 동일) | 2,472 | **+32** | 1,576 | 0 |
| C | 8개 **삭제**(상한. JS 의미가 깨진다) | 2,384 | **−56** | 1,564 | 0 |

A 한 변형의 회차 편차만 2,288~2,472(**184ms**)다. **−56ms 는 그 안이다.**
"몇 개만 내려도 수백 ms" 라는 1차 작성분의 기대는 근거가 없었다 — 요청 8개는 프리로드
스캐너가 병렬로 당겨오고, 실행 합계도 4x 스로틀에서 이 정도 규모로는 유의미하지 않다.

### 8-2. 히어로 앞 인라인 `<style>` 을 뒤로 내리면 **크게 나빠진다** (중앙값 5회)

`<body>` 안·히어로 앞에 있는 인라인 `<style>` **32개(202,023B)** 를 옮겼다.

| 변형 | 옮긴 곳 | 히어로 앞 gzip | LCP | vs A | CLS | LCP 요소 |
|---|---|---:|---:|---:|---:|---|
| A | — | 122,645 | **2,440** | — | 0 | `H1.moon-hero__title` |
| D | `</body>` 직전 | 88,794 | 3,800 | **+1,292** | **0.403** | `IMG.cd-hero-island__img` |
| E | 히어로 `</header>` 직후 | 88,794 | 3,780 | **+1,272** | **0.483** | 회차마다 바뀜 |

히어로 앞 바이트를 **33,851B(gzip) 줄였는데도** 나빠졌다. 이유는 명확하다 — 히어로가
**스타일 없이 먼저 그려지고**, 그 상태에서는 LCP 후보가 더 큰 히어로 이미지로 넘어간다.
그리고 뒤늦게 규칙이 도착하며 시프트가 3~5건 터진다([late-css-blocks-are-cls-in-the-shell]
가 말하던 것과 같은 함정이다).

### 8-3. 그러면 무엇이 LCP 를 잡고 있나 — **회선 예산**

`npm run perf:lcp-budget` 의 예산 덤프(베이스라인 1회):

| 항목 | 회선 바이트(gzip/br) | 해제 후 |
|---|---:|---:|
| 문서 | 240,301 | 1,247,099 |
| 렌더 차단 CSS 7개 | 97,066 | 501,407 |
| JS 26개 | 74,764 | 197,161 |
| 그 외(이미지·폰트 등) | 64,488 | — |
| **합계** | **476,619 (465KB)** | — |

**1.6Mbps = 200KB/s 에서 465KB 는 그 전송만으로 2,327ms** 다. 측정된 LCP 2,440~2,772 와
거의 그대로 맞는다. 즉 홈 LCP 는 **대역폭에 묶여 있고**, 그래서 순서를 바꾸는 안(§2-3 의 1·2·4·5)이
전부 죽은 것이다.

문서 240KB 중 **히어로 앞이 122,645B(51.1%)** 이고 그 몸통은 인라인 `<style>` 72개다(§2-2).

🔴 **"인라인 CSS 를 중복 제거해서 줄인다"는 안도 미리 지운다** — 히어로 앞 인라인 CSS
542,848B 를 규칙 단위 1,582개로 쪼개 보면 **완전 중복은 1건(0.1%)** 뿐이다. 전부 서로 다른
규칙이라 dedup 으로 돌려받을 바이트가 없다. 줄이려면 **안 쓰는 규칙을 걷어내는**
커버리지 작업뿐이고, 그건 §8-2 가 보여준 CLS 위험을 그대로 안고 가는 대공사다.

렌더 차단 CSS 쪽 확인 결과(전수, 프로덕션 문서 1개 기준):
- 진짜 렌더 차단은 **7개**뿐이다. head 의 나머지 `<link rel="stylesheet">` 12개는 전부
  `<noscript>` 폴백이거나 `data-cd-noncritical-style-src` + `media="print"` 지연 로딩이다.
  **워터폴에서 요청조차 되지 않는다** — 이미 정리돼 있으니 다시 파지 말 것.
- 큰 둘은 `fortune-ui-home.css`(36,066B) · `cosmic-main.css`(36,040B) 로 CSS 예산의 74% 다.
- `fonts-serif.css`(27,691B)는 `media="print"` + `onload` 라 렌더를 막지 않지만 **LCP 창 안에서
  회선을 쓴다**. 바로 아래의 같은 파일 `<link>` 는 `<noscript>` 안이라 중복이 아니다(오진 주의).

### 8-4. 🟢 살아 있는 레버 하나 — 첫 화면에서 **안 쓰이는** 인라인 `<style>` 만 뒤로

§8-2 가 죽은 이유는 "히어로 앞 인라인 CSS 를 **전부**" 옮겼기 때문이다. 히어로를 그리는 규칙까지
같이 내려가니 히어로가 맨몸으로 먼저 그려졌다. **그럼 안 쓰이는 것만 골라 내리면 되지 않나** —
재 보니 **된다.**

먼저 첫 화면 CSS 사용률을 쟀다(`page.coverage`, 390×844, **스크롤 없음**, 게이트 해제 후 3초):

| | 전체 | 첫 화면 사용 | 사용률 |
|---|---:|---:|---:|
| 외부 `.css` 8개 | 599,094 | 103,939 | **17.3%** |
| 문서 인라인 `<style>` 84개 | 648,149 | 157,342 | **24.3%** |
| **합계** | **1,247,243** | **261,281** | **20.9%** |

개별로는 `cosmic-main.css` 23.2% · `fortune-ui-home.css` 17.2% · `core-ui.css` 10.4% 다.

🔴 **"미사용 = 삭제 가능"이 아니다.** 커버리지는 `@font-face`·`@keyframes`, hover/JS 토글로만
켜지는 규칙을 전부 미사용으로 센다(`fonts-serif.css` 가 0.0% 로 찍히는 이유). **뒤로 미루는**
판단에만 쓸 수 있는 숫자다.

그 숫자로 만든 변형 F — 히어로 앞 인라인 `<style>` 72개 중 **첫 화면 사용 0B 인 27개(133,222B)**
만 `</body>` 앞으로 옮긴다(대상은 손으로 적지 않고 매 실행 커버리지로 발견한다):

| 변형 | 히어로 앞 gzip | LCP (n=9 중앙값) | 밴드 | CLS | LCP 요소 |
|---|---:|---:|---|---:|---|
| A | 122,645 | 2,404 | 2,256~2,592 | 0 | `H1.moon-hero__title` |
| **F** | **100,329** | **2,216 (−188ms)** | 2,188~2,356 | **0** | `H1.moon-hero__title` |

**9회 중 8회에서 F 가 이겼다.** 밴드는 겹치므로(이 레포의 통상 판정 기준) 근거는 **쌍대 비교**다 —
1차 5회(4승)까지 합치면 **14쌍 중 12승**, 부호검정 p≈0.013. CLS 0 과 LCP 요소가 그대로인 것이
D/E 와 결정적으로 다른 점이다.

재현: `npm run perf:lcp-budget -- --variants=A,F --runs=9`

### 8-4-1. ✅ 반영 완료 — PR #1212, 프로덕션 승격 2026-08-28

**셸에 들어갔다.** 대상은 27개가 아니라 **21개**다. 뺀 3종과 이유:

| 뺀 것 | 이유 |
|---|---|
| `lsd-styles-placeholder` | JS 주입 대상인 빈 블록(이득 0B) |

같은 27개**였다(흔들림 0건). 흔들린 것은 회차가 아니라 스크래치 하네스와 레포 도구의 구현 차이였다.

**회귀 확인은 두 갈래로 했고 둘 다 0건이었다:**
1. **정적 캐스케이드 충돌 전수 검사** — 위 1건을 빼서 0건. 🔴 이 검사는 두 위양성을 반드시 걸러야
   쓸 만해진다: `@keyframes` 스텝(`0%`·`to`)은 셀렉터가 아니고, **`!important` 여부가 다른 쌍은
   순서와 무관하게 승자가 정해진다**(147건 → 15건 → 8건).
2. **런타임 computed style 전수 대조** — 요소 **1,954개 × 속성 42개**, 차이 **0건**.
   🔴 **A-vs-A 대조군이 필수다** — 없이 돌렸을 때 `#cdReviews` 가 `display:none → block` 으로 보여
   없는 회귀를 만들 뻔했다(비동기로 채워지는 섹션이 빨라진 변형에서 스냅샷 창에 들어온 것뿐).
   한계: **상호작용으로만 생기는 DOM**(타일 미리보기·컬렉션 전체화면·수쿄 달력)은 스냅샷에 없어

   남은 인라인 잔량은 13,845B 뿐이라(§8-4-1 "아직 안 한 것") 단독으로는 노이즈에 묻힌다.
4. TTFB(§4-D)는 여전히 보류 상태다. 승격 후 실측은 **436ms**(승격 전 ~650ms)로 더 내려갔다.

## 9. §4-C 착수 결과 — **기각.** INP 를 잡고 있는 것은 재계산이 아니라 한 줄의 강제 동기 레이아웃 (2026-08-28, 같은 날 후속)

측정 대상은 **프로덕션** `https://code-destiny.com/`(build `ec160efeeecd`), 조건은 §5 와 같다
(390×844 · DPR 3 · CPU 4x · Slow 4G 1.6Mbps/150ms · 게이트 해제 후 6초 정착).
탭 자리는 §3-1 이 못 박은 `#cdMobileBottomNav [data-nav-key='fortunes']` 하나다.

🔴 **도구는 레포에 들어갔다 — 스크래치로 다시 짜지 말 것**: `npm run perf:recalc-origin`
([scripts/measure-recalc-attribution.mjs](../../scripts/measure-recalc-attribution.mjs)).
§5 의 "recalc 원인" 줄이 시킨 그대로 `Tracing.start` 에
`disabled-by-default-devtools.timeline.stack` 을 켜서 `UpdateLayoutTree`·`Layout` 의
`args.beginData.stackTrace` 최상위 프레임으로 묶고, 별도 패스에서
`disabled-by-default-devtools.timeline.invalidationTracking` 으로 무효화 사유를 센다.

🔴 **이 도구의 절대 시간은 §3-1 의 616ms 와 비교하지 말 것** — 트레이싱 오버헤드가 실린다.
읽는 것은 비중과 엘리먼트 수이고, 판정은 **같은 하네스 안의 변형 간 밴드 비겹침**이다.

### 9-1. 🔴 §4-C 의 전제가 틀렸다 — 스타일 무효화 범위를 다 지워도 INP 는 안 움직인다

§4-C 는 "클래스 토글 한 번이 무효화하는 범위가 INP 를 정한다"를 전제로 했다. 그 전제의 **상한**을
직접 쟀다 — 탭 직전에 `*,*::before,*::after{animation:none!important;transition:none!important}`
를 넣어 문서의 애니메이션·트랜지션을 통째로 끈 변형 C 다(n=3, 재현:
`npm run perf:recalc-origin -- --passes=stack --variants=A,C --runs=3`).

| 변형 | 탭 지연 중앙값 | 밴드 | 입력지연 | 처리 | 프레젠테이션 |
|---|---:|---|---:|---:|---:|
| A 베이스라인 | **656** | 640–688 | 36 | 1 | 622 |
| C 애니메이션·트랜지션 전면 정지 | **648** | 632–648 | 1 | 0 | 647 |

**밴드가 겹친다 — 변화 없음.** 그런데 같은 창의 렌더 작업은 크게 줄었다:

| 탭 구간(1.5초) | A | C |
|---|---:|---:|
| UpdateLayoutTree | 1,055ms / 84회 | **585ms / 63회** |
| Paint | 66ms / 102회 | **18ms / 34회** |
| PrePaint | 86ms / 102회 | **25ms / 69회** |
| **Layout** | 422ms / 30회 | **408ms / 10회** |
| **FunctionCall** | 651ms / 183회 | **638ms / 176회** |

🔴 **스타일 재계산을 45% 지우고 페인트를 1/4 로 줄여도 탭 지연은 1ms 도 안 움직였다.**
안 움직인 두 항이 답을 갖고 있다 — **`FunctionCall`(651ms)과 `Layout`(422ms)** 이다.

같은 이유로 **변형 B(`cd-hero-ambient-idle` 부착)도 변화 없음**이었다(648 [632–680] vs 680 [664–736]).
🔴 다만 **B 는 애니메이션을 줄이지 않는다 — 바꿀 뿐이다.** 그 클래스가 붙으면 히어로 앰비언트는
멈추지만 폴드 아래 34개가 `:not(.cd-hero-ambient-idle)` 로 걸려 있어 **거꾸로 풀린다**
(index.html 의 "폴드 아래 장식 애니메이션" 주석). 상한 판정에 쓸 수 있는 것은 C 뿐이다.

### 9-2. 🔴 "처리 ≈ 0, 렌더가 전부" 는 오독이었다 — 비용은 클릭 핸들러 안에 있다

§3·§3-1 은 "처리 시간이 0~2ms 다. 자바스크립트 핸들러는 사실상 즉시 끝난다"로 읽었다.
**틀렸다.** 최댓값을 찍는 엔트리는 `pointerover`(5회 중 5회, 처리 0~1ms)이고, 그 엔트리의
프레젠테이션 620~650ms 안에서 **뒤이은 `click` 핸들러가 통째로 돌고 있다.**

같은 탭 창의 `FunctionCall` 상위(n=3, 회차 평균):

| 함수 | 횟수 | 시간 |
|---|---:|---:|
| **`B @ /js/shell/s-d6dc5634f99828ae.js:1:6100`** | **2** | **519~542ms** |
| `raf @ (익명)` | 2 | 32ms |
| `window.requestIdleCallback.timeout @ /js/noncritical-defer-loader.js` | 12 | 25ms |
| 그 외 전부 | — | 각 ≤ 11ms |

**한 함수가 전부다.** 그 `B` 는 **`activateNavItem`** — [index.html:14095](../../index.html#L14095),
`data-marker="mobile-bottom-navigation-v20260701"` 블록. `document.addEventListener('pointerup', …, true)`
와 `('click', …, true)` **두 곳에 걸려 있어 탭 한 번에 2회 호출**된다(index.html:14203-14204).

🔴 그리고 §3-1 은 이미 이 숫자를 갖고 있었다 — "5회 중 1회만 `click` 이 최댓값이 되며 **처리 508ms**
를 찍었다"를 이상치로 적었다. **그 508ms 가 곧 이 519~542ms 다.** 이상치가 아니라 정답이었다.

### 9-3. 🔴 범인 한 줄 — `openOverlay` 의 강제 동기 레이아웃 317ms

`Layout` 도 같은 자리에 스택을 달고 온다. 탭 구간의 Layout 을 유발 지점으로 묶으면(n=3):

| 유발 지점 | 횟수 | Layout 시간 | 같은 지점의 재계산 |
|---|---:|---:|---|
| **`F @ /js/shell/s-4756db6a8f33e6ba.js:1:14788`** | 1 | **317ms** | 36~47ms / 211 엘리먼트 |
| `H @ /js/shell/s-4756db6a8f33e6ba.js:1:12025` | 1 | 58ms | 85ms / **1,012 엘리먼트** |
| (스택 없음) | 24 | 45ms | — |
| `t @ …:1:12420` | 1 | 9ms | — |

**탭 구간 Layout 429ms 중 317ms(74%)가 한 지점이다.** 소스로 되짚으면:

**① `F` = `openOverlay`** — [index.html:13733](../../index.html#L13733)

```js
function openOverlay(collId){
  if (!isMobile()) return;
  if (window.__cdExpandHome) window.__cdExpandHome();          // ← 문서를 크게 더럽힌다
  if (isOverlayOpen && currentCollectionId === (collId || null)) return;
  savedScrollY = window.pageYOffset || document.documentElement.scrollTop || 0;   // ← 13738: 그 직후 강제 동기 레이아웃
```

`__cdExpandHome()` 이 홈을 펼쳐 놓은 **바로 다음 줄**에서 스크롤 위치를 읽는다. 읽는 순간
브라우저는 방금 더럽혀진 2,233 엘리먼트 문서의 레이아웃을 **동기로 전부 다시 계산해야 한다.**
그게 317ms 다.

**② `H` = 오버뷰 패널 열기** — [index.html:13598-13599](../../index.html#L13598-L13599)

```js
panel.classList.add('is-open');
panel.scrollTop = navigationStore.getState().allFortunes.overviewScrollTop || 0;   // ← 13599
```

같은 모양이다 — 무효화(`classList.add`) 직후 `scrollTop` 을 건드려 **1,012 엘리먼트**의
재계산(85ms) + 레이아웃(58ms)을 동기로 강제한다.

### 9-4. 무효화 사유 전수 — 클래스 토글은 범인이 아니었다

`invalidationTracking` 패스(n=1, 재현 `npm run perf:recalc-origin -- --passes=invalidation`):

| 로드 구간 (25,986건) | 비중 | 탭 구간 (3,723건) | 비중 |
|---|---:|---|---:|
| `Animation` | 50.2% | `Animation` | 48.3% |
| `PseudoClass` | 34.5% | `Style rule change` | 24.1% |
| `Invalidation set invalidates self` | 8.3% | `@keyframes rule change` | 22.7% |
| `Node was inserted into tree` | 2.3% | `Related style rule` | 1.9% |
| … | | **`Invalidation set matched class`** | **0.3%** |

🔴 **"클래스 토글이 무효화 범위를 넓힌다"는 §4-C 의 가설은 실측에서 0.3% 였다.**
무효화 건수의 절반은 애니메이션이고, 9-1 이 보였듯 그건 **끄더라도 INP 를 안 바꾼다.**

### 9-5. 🔴 §5 의 "스택 없는 것이 파서 몫" 은 **로드 구간에서만** 참이다

탭 구간에는 파싱이 없는데도 스택 없는 `UpdateLayoutTree` 가 **74회 / 869ms** 나온다.
그건 파서가 아니라 **애니메이션 틱**이다(9-1 의 C 에서 63회로 줄었다). 로드 구간의 92.6%
스택 없음은 파서·스타일시트 몫이 맞지만, **탭 구간에서 같은 해석을 하면 틀린다.**

### 9-6. 다음 착수점 — 최소 레버 하나

🔴 **§4-C(스타일 재계산 범위 축소)는 닫는다.** 상한이 0ms 로 측정됐다(9-1). 셸 CSS 의
`!important` 4,990개나 `html body .x` 셀렉터를 정리하는 대공사는 **이 지표를 근거로 착수할 수 없다.**

대신 **강제 동기 레이아웃 2곳**이 남았고, 둘 다 수술적이다:

1. **[index.html:13738](../../index.html#L13738)** — `savedScrollY` 를 `__cdExpandHome()` **앞에서**
   읽는다. 문서를 더럽히기 전에 읽으면 이미 계산된 레이아웃을 그냥 가져오므로 317ms 가 0 에 수렴한다.
   🔴 **이건 순수 최적화가 아니라 동작 변경이다** — `savedScrollY` 는 오버레이를 닫을 때
   복원하는 값이라, "펼치기 전 위치"와 "펼친 후 위치" 중 무엇을 복원할지가 달라진다.
   **사용자에게 먼저 물어라.** 값만 보면 옮기는 쪽이 맞지만 그 판단은 제품 결정이다.
2. **[index.html:13599](../../index.html#L13599)** — `panel.scrollTop` 대입을 `classList.add('is-open')`
   **앞으로** 옮기거나 `requestAnimationFrame` 뒤로 미룬다(143ms).
3. `activateNavItem` 이 `pointerup`·`click` **두 번** 도는 것(index.html:14203-14204)이
   519ms 를 2회로 나눠 쓰는지, 한 번만 무겁고 한 번은 디듀프로 빠지는지는 **아직 안 쟀다(미검증)**.
   위 1·2 를 고친 뒤에도 남으면 그때 볼 것.

**판정 기준**: 고친 뒤 `npm run perf:recalc-origin -- --passes=stack --variants=A --runs=3` 로
같은 하네스에서 A 를 다시 재고, 위 표의 **656 [640–688]** 과 밴드 비겹침을 본다. 겹치면
"변화 없음"으로 적는다. 프로덕션 INP 의 최종 확인은 별개로 §3-1 의 조건(616 [600–648])에서 한다.

🔴 **착수 근거의 한계는 그대로다** — 이 사이트는 CrUX 데이터가 없어 CWV 는 구글의 랭킹 입력이
아니다(§8-5 의 0번). 위 1·2 는 각각 한 줄짜리라 이탈·체감 과제로 값이 맞지만, 여기서 더 키우지 말 것.
