## 0. 목표 한 줄

모든 유료·무료 LLM 운세 결과의 **첫 섹션**에서, 엔진이 계산한 **결정적 근거**(일간·십성·오행·주성·별자리·낙샤트라·숙·카드)를 바탕으로 사용자의 **타고난 성향**을 "소름 돋을 만큼 확신에 찬" 문장으로 먼저 짚어준다.
**이 변경 때문에 결제 후 결과가 안 나오는 일은 단 1건도 생기면 안 된다.**

---

## 1. 절대 규칙 (위반 시 즉시 중단·보고)

1. **파일 경로를 추측하지 않는다.** 이 문서에 나온 경로·함수명은 전부 "예시"다. Phase 0에서 실제 경로를 grep/탐색으로 확인하고 보고서에 근거(파일:라인)와 함께 적는다.
2. **6개 점술 엔진 코드베이스는 읽기 전용이다.** 엔진 내부를 수정하지 않는다. 성향 추출은 **어댑터/후처리 레이어**에서 엔진 출력만 읽어서 한다.
3. `sajuAdapter.ts`의 `calculateLocalResult()`는 **불변**. `normalizeSaju.ts`에 timezone 필드를 추가하지 않는다. KASI prefetch에 timezone을 주입하지 않는다.
4. **PortOne/이니시스 결제 실행 파일은 별도 승인 게이트**를 거친다. 이번 작업에서 결제 실행 코드를 고쳐야 한다는 결론이 나오면, 수정 전에 반드시 따로 보고하고 승인을 받는다.
5. 결제 해제·차감 순서 정본은 **①이용권 ②월정석 ③코인**이다(CLAUDE.md §결제 게이팅, `docs/payment-policy-flow.md`). `Rules/agent-regression-guard.md` 10항은 폐기됐으니 적용하지 않는다.
6. 결제 데이터 형식, KV/R2 스키마, **사용자에게 이미 저장된 결과물 형식**은 **forward-fix only**다. 기존에 저장된 결과는 새 코드에서도 그대로 렌더링돼야 한다.
7. 사용자에게 보이는 모든 문자열(섹션 제목, 버튼, 안내문)은 **i18n 키**를 쓴다. LLM 입력용 지식베이스 텍스트는 예외지만, UI에 직접 출력하는 고정 문구는 예외가 아니다.
8. 960px 데스크톱 레이아웃을 유지한다. 폐기 코드는 `_graveyard/`로 격리한다.
9. 루트 `CLAUDE.md`를 다시 부풀리지 않는다. 새 규칙·근거는 `docs/context/<주제>.md`로 넣고 루트에는 한 줄 링크만 남긴다(`@import` 금지).
10. 브랜치 기반 작업 + Conventional Commits. 변경은 **최소·외과적**으로 한다.
11. `.claude/agents/`의 `regression-scout`, `deletion-auditor`, `paid-gate-auditor`를 적극적으로 활용한다(읽기 전용, 결론과 근거만 반환).
12. 운영(프로덕션) 배포는 **스테이징(codedestiny-staging) 검증 → 네오 승인** 후에만 한다.

### 3-1. LLM 기능 전수 목록
코드베이스의 **LLM 결과를 생성하는 모든 기능**을 찾는다. 이미 알려진 기능만이 아니라, LLM 호출부를 역추적해서 빠짐없이 찾는다. 최소한 아래는 반드시 포함해서 확인한다.

- 사주 분석(무료/유료 각 티어), 자미두수, 타로(모든 스프레드·기능 변형), 서양 점성술, 숙요점, 베다/낙샤트라
- 초융합 운세(6엔진 통합), Destiny Compass House(6축 점수), 운명의 섬(12궁 상담), 마스터 인연의 서, Love Code / Secret House(궁합)
- 운명 찻집(꽃돼지, 십성=손님 콘셉트), 네오 팩폭 전략실(1차 결과 + 후속 질문)
- 무료 운세 섹션, 훈민정음 작명 등 그 밖의 LLM 사용처

각 기능별로 다음 열을 채운다.

| 기능 | 엔진 | 무료/유료 | 결제 경로(웹 PortOne·Google Play·토스 앱인토스·이용권/월정석/코인) | 생성 방식(동기/스트리밍/큐) | 프롬프트 빌더 위치 | 모델·max_tokens·timeout | 출력 형식(마크다운/JSON 스키마) | 저장 위치(Mongo/KV/R2/캐시 키) | 실패 시 처리(재시도/재생성/환불/무처리) | 현재 첫 섹션 내용 |
|---|---|---|---|---|---|---|---|---|---|---|

### 3-2. 엔진 출력에서 이미 얻을 수 있는 데이터
성향 추출에 쓸 수 있는 필드가 **엔진 출력에 이미 있는지** 확인한다. 새로 계산하기 전에 있는 것부터 쓴다.

## 4. Phase 1 — 결제 → 생성 → 전달 무결성 감사 (서비스 하나하나)

"결제했는데 결과가 안 나온다"는 사고가 이번 변경으로 생기지 않는지, 그리고 **지금 이미 있는 구멍**은 없는지 기능별로 전부 점검한다. `paid-gate-auditor`, `regression-scout` 서브에이전트를 활용한다.

### 4-1. 기능별 체크리스트 (모든 유료 기능 × 모든 결제 경로)

각 항목을 **PASS / FAIL / 위험** 판정과 근거로 기록한다.

1. **권한 확정 → 생성 순서**: 결제 확정(웹훅/confirm) 후 권한이 부여되는 시점과 LLM 생성 트리거의 관계. 웹훅이 늦게 오거나 중복으로 와도 생성이 정확히 한 번 이뤄지는가.
2. **이용권/월정석/코인 차감과 생성 실패의 관계**: 차감 후 생성이 실패하면 → 재생성이 가능한가? 이중 차감은 없는가? 사용자가 다시 들어오면 결과를 받을 수 있는가?
3. **토큰·시간 예산**: 성향 섹션이 추가되면 입력·출력 토큰이 늘어난다. `max_tokens`에서 잘리는지, Workers wall-time/CPU/서브요청 타임아웃에 걸리는지, 스트리밍이 중간에 끊기는지 **수치로** 계산한다(현재 평균·p95 출력 길이 + 증가분 추정).
4. **출력 파싱**: JSON 스키마를 쓰는 기능이면 새 필드는 **optional**이어야 하고, 파싱 실패 시 결과 전체가 버려지는 경로가 없어야 한다.
5. **기존 저장 결과 호환**: 이미 결제하고 저장된 과거 결과가 새 렌더러에서도 깨지지 않는가. 캐시 키에 프롬프트 버전이 들어가 있다면, 버전을 올렸을 때 과거 결제 사용자가 결과를 잃거나 의도치 않게 재생성되지 않는가.
6. **큐 작업 호환**: MongoDB 기반 비동기 큐가 있다면, 배포 시점에 큐에 남아 있던 이전 형식의 작업이 새 코드에서도 처리되는가(payload 버전 필드, 하위 호환).
7. **LLM 공급자 장애**: 타임아웃·429·5xx 발생 시 재시도·폴백 모델·사용자 안내가 있는가. 실패가 "결제 완료 + 결과 없음" 상태로 그대로 남는가.
8. **고아 주문 탐지**: 결제 완료(또는 권한 차감) 상태인데 결과 문서가 없는 건을 찾는 **읽기 전용 점검 스크립트**를 만들어, 스테이징과 운영(읽기 전용 쿼리)에서 현재 몇 건이 있는지 보고한다.
9. **앱 경로**: Android WebView(Google Play Billing), 토스 앱인토스(토스 인앱결제), 웹(PortOne/이니시스) 각각에서 결제 후 결과 화면까지의 흐름이 같은 생성 파이프라인을 타는지, 클라이언트에 섹션 순서가 하드코딩돼 있지 않은지 확인한다.
10. **후속 질문형 기능**(네오 팩폭 전략실 등): 1차 결과의 성향 근거가 후속 질문 컨텍스트에도 이어지는지, 컨텍스트가 길어져 토큰 한도를 넘지 않는지 확인한다.
11. 기존 검증 스크립트 `verify:billing-pass-policy`, `verify:checkout-pass-card` 등이 통과하는지 확인한다.

## 5. Phase 2 — 성향 지식베이스 코드화 + 추출기

### 5-1. 설계 원칙
- **LLM에게 십성·오행·주성 계산을 시키지 않는다.** 계산은 전부 코드에서 결정적으로 하고, LLM에는 "확정된 사실 + 해석 재료"만 넘긴다. 그래야 틀린 근거로 단언하는 사고가 안 난다.
- 추출기는 **순수 함수**로 만들고 엔진 출력만 입력으로 받는다(엔진 코드 수정 금지).
- 부록의 KB를 타입이 있는 데이터 모듈로 옮긴다. 위치는 Phase 0에서 확인한 구조에 맞춘다(예시: `lib/traits/kb/saju.ts`, `ziwei.ts`, `western.ts`, `vedic.ts`, `sukuyo.ts`, `tarot.ts`).
- KB 문장은 **LLM이 재료로 쓰는 키워드·뉘앙스**다. 결과에 문장을 그대로 복사하지 않고 매번 자연스럽게 다시 쓰도록 프롬프트에 명시한다.
- KB 전체 내용은 네오(사주 상담 경력) 또는 자문 명리학자가 **최종 검수**한다. 검수용으로 `docs/context/trait-kb-review.md`에 표 형태로 내보낸다.

### 5-2. 공통 출력 타입 (예시)

```ts
type TraitFact = {
  key: string;              // 'saju.dayMaster.辛', 'saju.tenGod.官.absent' ...
  layer: 'core' | 'strong' | 'support' | 'contrast';
  label: string;            // '신금 일간', '관성 없음'
  evidence: string;         // 사용자에게 보여줄 근거 한 줄: '일간이 辛金(보석의 금)'
  keywords: string[];       // KB 키워드
  light: string[];          // 밝은 면
  shadow: string[];         // 그림자
  scenes: string[];         // "이럴 때 이렇죠" 장면 재료
  weight: number;           // 0~1, 우선순위 정렬용
};

type TraitProfile = {
  engine: 'saju' | 'ziwei' | 'western' | 'vedic' | 'sukuyo' | 'tarot';
  headline: TraitFact;      // 가장 강한 한 가지
  facts: TraitFact[];       // weight 내림차순, 최대 6~8개
  tensions: Array<{ a: string; b: string; synthesis: string }>; // 상충 성향 종합 힌트
  dataQuality: 'full' | 'partial'; // 출생시각 없음 등
};
```

### 5-3. 엔진별 추출 로직

**사주** (우선순위: 일간 > 월령·격국 > 십성 과다·부재 > 오행 과다·부족 > 일지 > 특수 조합 > 신강·신약)
1. **일간**: 무조건 headline 후보 1순위.
2. **십성 그룹 강도**: 비겁·식상·재성·관성·인성 5개 그룹으로 점수를 낸다.
   - 엔진에 오행/십성 강도 계산이 이미 있으면 **그것을 그대로 쓴다.**
   - 없을 때 기본값: 천간 1.0 / 지지 본기 1.0(월지 본기는 ×1.5~2.0) / 지장간 여기·중기 0.3. 일간 자신은 제외한다.
   - **과다**: 그룹 비율 ≥ 35% 또는 천간+지지 본기에 3개 이상
   - **발달**: 25~35%
   - **완전 부재**: 천간·지지 본기·지장간 모두 0
   - **잠재(표면 부재)**: 천간·지지 본기에는 0이고 지장간에만 있음 → "없는 듯 숨어 있다"는 뉘앙스로 쓴다
   - 정/편 구분(정관 vs 편관 등)도 하위 키로 보존한다.
3. **오행 과다·부족**: 엔진 오행 점수 기준. 과다 ≥ 35%, 부족 = 0 또는 5% 미만.
4. **특수 조합**: 부록 A-4의 조합 조건이 성립하면 fact로 추가한다(식상생재, 관인상생, 상관견관, 재다신약, 군겁쟁재, 살인상생, 식신제살, 편인도식, 인다신약 등). 판정 기준은 엔진 판정이 있으면 그것을 따르고, 없으면 보수적으로(확실할 때만) 추가한다.
5. **월지 계절(조후)**: 한겨울(亥子丑) 출생 + 화 부족 → 차분함·내면 온도, 한여름(巳午未) 출생 + 수 부족 → 열기·급함 같은 보조 fact.
6. **일지**: 배우자궁·속마음 성향 보조 fact(가중치 낮게).

**자미두수**
1. 명궁 주성(1~2개) + 묘왕리함 → headline. 묘·왕이면 밝은 면, 함지면 그림자 비중을 높인다.
2. 무주성 명궁이면 대궁(천이궁) 주성을 빌려 쓰고(차성안궁) "환경에 따라 색이 바뀌는 사람" fact를 추가한다.
3. 명궁 보조성·사화(특히 화기·화록) → strong/support.
4. **여러 궁으로 입체화**: 신궁(후천 성향), 복덕궁(내면 가치관·정신세계), 천이궁(밖에서 보이는 모습), 관록궁(일하는 방식), 재백궁(돈 쓰는 습관), 부처궁(연애 스타일), 형제·교우궁(대인관계). 각 궁에서 1개씩 support fact로 뽑는다.
5. 삼방사정(명궁·재백·관록·천이)에 길성·살성이 모이면 tension/support로 반영한다.

**서양 점성술**
1. 태양(정체성) + 달(감정·속마음) + 상승궁(첫인상) 3축 → headline은 태양, 단 달/상승이 원소적으로 강하게 대비되면 "겉-속" tension으로 만든다.
2. 수성(말투·사고), 금성(연애·취향), 화성(행동·분노 방식) → support.
3. 원소 분포(불·흙·공기·물) 과다·부재, 모드(활동·고정·변통) 편중, 스텔리움(한 별자리/하우스에 3개 이상).
4. 주요 하드 애스펙트(태양·달·금성·화성과 토성·명왕성·천왕성의 합·스퀘어·대립)를 부록 D-4에 따라 fact로 추가한다.
5. 출생 시각이 없으면 상승궁·하우스를 쓰지 않는다. 그날 달이 별자리를 옮기면 달도 쓰지 않는다 → `dataQuality: 'partial'`. 이때는 확신 어조를 유지하되 근거를 태양·행성 중심으로만 든다.

**베다/낙샤트라**
1. **달 낙샤트라(잔마 낙샤트라)가 headline**이다(베다에서 성향의 핵심). 파다(1~4)가 있으면 뉘앙스를 보조한다.
2. 라그나(상승) 라시 + 라그나 로드 → 겉으로 드러나는 기질.
3. 달 라시 → 감정 처리 방식.
4. 엔진이 아트마카라카를 제공하면 "영혼이 이번 생에 배우려는 것" fact로 추가한다.
5. 반드시 사이드리얼(엔진의 아야남샤 설정)을 따르고, 서양 별자리와 섞지 않는다.

**숙요점**
1. 본명숙 → headline + 부록 F의 키워드.
2. 엔진이 일요(日曜)·칠요 등을 주면 support로 쓴다.

**타로** (타고난 성향이 아니라 "지금 당신 안에서 가장 강하게 작동하는 성향"으로 프레이밍)
1. 스프레드에서 "나/현재 나/내면/본질" 포지션 카드 → headline. 그런 포지션이 없으면 첫 카드를 쓴다.
2. 메이저 아르카나 비율이 높으면(≥50%) "인생의 큰 흐름 한가운데 있는 사람"이라는 fact를 추가한다.
3. 수트 편중 → 완드(행동·열정), 컵(감정·관계), 소드(생각·말), 펜타클(현실·물질) 중 우세 모드.
4. 코트 카드 → 지금 쓰고 있는 페르소나(페이지·나이트·퀸·킹).
5. 역방향 → 그 성향이 막혀 있거나 안으로 향하는 상태(그림자 쪽).
6. 같은 카드 조합이면 같은 성향이 나와야 한다(결정적).

**궁합·다인 기능**: 두 사람 각각 TraitProfile을 만들고, 성향 대비를 "서로 끌리는 이유 / 부딪히는 지점"으로 연결한다.

**초융합 운세·Destiny Compass House**: 6개 엔진 TraitProfile에서 **서로 같은 말을 하는 성향**(예: 사주 식상 과다 + 자미 명궁 탐랑 + 쌍둥이자리 태양 = "호기심·표현 욕구")을 교차 검출한다. **"여러 점술이 동시에 가리킨다"가 가장 강한 소름 포인트**이므로 headline으로 올린다. 키워드 동의어 사전(`trait-synonyms.ts`)으로 일치 여부를 판정한다.

### 5-4. 단위 테스트
- 사주: 10일간 × {관 부재, 관 과다, 식상 과다, 재다신약, 인다, 비겁 과다, 무재, 무인} 조합 픽스처 최소 20개. 같은 입력이면 같은 TraitProfile이 나오는 결정성 테스트.
- 자미: 14주성 명궁 + 무주성 + 화기 명궁 픽스처.
- 서양: 출생 시각 있음/없음, 달 별자리 경계일.
- 베다: 27 낙샤트라 전부 매핑 테스트.
- 숙요: 27숙 전부 매핑 테스트.
- 타로: 78장 × 정/역 매핑 누락 0 테스트.

## 6. Phase 3 — 프롬프트 빌더 개편 + 출력 검증 + 폴백

### 6-1. 결과 구조 (모든 기능 공통, 첫 섹션 고정)

```
[섹션 1] 타고난 성향  (i18n 키 예: result.section.innateNature)
  ① 단언 한 줄 — headline을 정면으로 짚는다.
     예) "당신은 칼끝처럼 예리한 사람이에요. 남들이 못 본 0.1mm를 먼저 봐요."
  ② 근거 — 명리/주성/별자리 용어 1개 + 쉬운 풀이 1문장, 2~3개.
     예) "일간이 辛金, 보석의 금이에요. 그런데 사주에 관성이 하나도 없어요."
  ③ 겉과 속 — "겉으로는 A, 속으로는 B" 양면 구조 1~2개 (tensions 활용)
  ④ 구체 장면 3개 — "~할 때 ~하죠" 형태. 일상에서 바로 떠오르는 장면.
     예) "단체 대화방에서 다들 대충 넘어갈 때, 혼자 맞춤법 틀린 거 보이죠."
  ⑤ 연결 한 줄 — 이 성향이 이번 주제(연애·재물·올해 운 등)에 어떻게 작동하는지로 다음 섹션을 연다.
[섹션 2~] 기존 결과 내용 (기존 구조 유지)
```

분량 기준: 기존 결과 분량 정책(티어별 최소 분량)을 줄이지 않는다. 성향 섹션은 **추가**다. 단, Phase 1의 토큰 예산 계산 결과를 넘으면 성향 섹션 길이를 줄이고 다른 섹션은 건드리지 않는다.

### 6-2. 어조 규칙 (시스템 프롬프트에 넣는다)

- **단정형으로 말한다.** "~하는 사람이에요", "~하죠", "~잖아요".
  금지 표현: "~일 수도 있어요", "~경향이 있을 수 있습니다", "개인차가 있지만", "참고용으로".
- **근거를 짧게 보여준다.** 확신은 근거에서 나온다. 용어는 1개만 쓰고 바로 풀어준다.
- **양면을 같이 말한다.** 장점만 나열하면 뻔해지고, 그림자를 한 번 짚어야 "어떻게 알았지?"가 나온다. 그림자는 비난이 아니라 "그래서 피곤했죠" 같은 공감으로 쓴다.
- **누구에게나 맞는 말을 쓰지 않는다.** "때로는 외향적이고 때로는 내향적" 같은 문장은 금지한다. 반드시 이 사람의 fact에서 나온 구체적인 특징만 말한다.
- **캐릭터 화자를 유지한다.** 연이(따뜻함, 숙명론 금지) / 꽃돼지(치유·설명형, 대립 없음) / 네오·고양이(직설, 따뜻하지 않음) / 영냥이. 같은 성향이라도 화자 말투로 쓴다.
- **안전 경계**: 단정하는 대상은 **성격·기질·행동 패턴**으로 한정한다. 건강·질병·사망·사고·이혼을 확정하는 표현, 외모 비하, 특정 집단 고정관념, 정신질환 진단처럼 들리는 표현은 쓰지 않는다. 연이·꽃돼지 콘텐츠는 숙명론을 쓰지 않는다.
- **반복 방지**: 같은 사용자가 여러 서비스를 구매하면 같은 문장이 반복되면 안 된다. KB 문장을 그대로 쓰지 말고, 기능별로 다른 장면 재료를 고르도록 `seed = hash(userId + featureId)`로 scenes·keywords 선택을 결정적으로 바꾼다.

### 6-3. 프롬프트 주입 방식

- 기존 프롬프트 빌더에 `<trait_profile>` 블록(JSON 또는 간결한 목록)을 추가하고, 지시문에 "첫 섹션은 반드시 타고난 성향, trait_profile의 근거만 사용, 없는 근거 창작 금지"를 넣는다.
- 프롬프트 버전 상수를 올리고(예: `PROMPT_VERSION = 'trait-first-v1'`), 캐시 키·결과 메타데이터에 기록한다. 과거 결과는 과거 버전 그대로 서빙한다(Phase 1의 5번 확인 사항 준수).
- 후속 질문형 기능은 1차 결과의 TraitProfile 요약(짧게)을 대화 컨텍스트에 유지한다.

### 6-4. 출력 검증기 + 폴백 (결과 미제공 방지의 핵심)

검증기는 **결과 전달을 절대 막지 않는다.** 검증 실패는 "품질 보정" 트리거일 뿐이다.

1. 생성 결과의 첫 섹션 제목이 성향 섹션인지, headline 키워드가 1개 이상 들어 있는지, 금지 표현이 없는지 확인한다.
2. 실패 시:
   - (a) 시간·토큰 예산이 남아 있으면 **성향 섹션만** 짧게 1회 재생성해서 앞에 붙인다.
   - (b) 예산이 없거나 재생성도 실패하면 → TraitProfile로 **템플릿 기반 결정적 성향 섹션**(i18n 템플릿 + KB 문장 조합)을 만들어 앞에 붙인다.
   - (c) 그래도 문제가 있으면 → 원래 결과를 그대로 전달한다(성향 섹션 없이). **결제한 결과는 무조건 전달한다.**
3. 모든 폴백 발생을 로그·메트릭으로 남긴다(기능별 폴백률 확인용).

### 6-5. 기능 플래그

- 엔진·기능별 플래그(예: `TRAIT_FIRST_SAJU`, `TRAIT_FIRST_ZIWEI` …)를 `wrangler.toml`의 **`[vars]` 추가만으로** 만든다. `[observability]`·Analytics Engine 설정은 이번 작업 범위 밖이다.
- 플래그를 끄면 기존 프롬프트 경로로 즉시 돌아가야 한다(재배포 없이 롤백 가능한 구조가 이상적이고, 불가능하면 롤백 절차를 문서화한다).

### 8-1. 골든셋 LLM 평가
- 사주 20건 이상, 자미 15건, 서양 10건, 베다 10건, 숙요 10건, 타로 10회 이상의 고정 입력을 만든다.

|---|---|
| 첫 섹션 = 성향 | 100% |

### 8-2. 스테이징 E2E (codedestiny-staging)
모든 유료 기능 × 결제 경로마다 실제로 해본다.
- PortOne 테스트 결제 → 웹훅 → 권한 부여 → 생성 → 결과 화면 → **첫 섹션 성향 확인** → 새로고침·재접속해도 결과 유지
- 이용권·월정석·코인 차감 경로 각각
- 강제 실패 주입: LLM 타임아웃, 429, 5xx, 출력 잘림, 검증 실패 → 폴백으로 결과가 전달되는지
- 웹훅 지연·중복 → 생성 1회, 차감 1회
- 과거 형식으로 저장된 결과 렌더링
- Android WebView, 토스 앱인토스 미니앱 환경에서 결과 화면 렌더링
- 고아 주문 점검 스크립트 결과 0건
- `verify:billing-pass-policy`, `verify:checkout-pass-card` 등 기존 검증 통과
- p95 생성 시간·토큰 사용량 비교(변경 전/후)

결과를 `docs/handoff/trait-first-phase5-verification.md`로 보고한다.

5. 마지막에 `docs/context/trait-first.md`(설계·KB 위치·플래그·롤백 절차)를 만들고 루트 CLAUDE.md에는 한 줄 링크만 추가한다.
