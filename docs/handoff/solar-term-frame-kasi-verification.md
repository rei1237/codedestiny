# 절기 프레임 세차·월건의 KASI 대조 — 인수인계 (2026-08-28)

> 이 문서만 읽고 이어서 시작할 수 있어야 한다. **근거를 못 찾으면 추측하지 말고 사용자에게 물어라.**

## ✅ 결말 (2026-08-28 저녁 — 이 문서의 §1 은 이제 역사다)

**끝났다.** 사용자가 data.go.kr 에서 **특일 정보(`SpcdeInfoService`) 활용신청**을 받아 403 이 풀렸고,
tier-2 픽스처를 채집해 가드가 `tier-1 + tier-2` 로 돈다(검사 41건 · 지상값 provider 29개 ·
스윕 567,492분). 아래 §1~§2 의 "왜 못 했나"는 **해결된 경위**로만 읽을 것.

승인 직후 드러난 사실 셋 — 전부 403 뒤에 가려져 있었다:

1. 🔴 **KASI 24절기 커버리지는 `2000~2028`(29년)뿐이다.** 이 문서와 스크립트가 쓰던 `1930~2050` 은
   403 상태에서 적은 **가정**이었다. 실측(1995~2035 전수 조회): 1999 이하·2029 이상은 오류가 아니라
   **HTTP 200 + `totalCount 0`**. 같은 키의 음양력(`LrsrCldInfoService`)은 1391~2050 을 덮는다.
2. 🔴 **채집기가 KASI 의 `kst` 우측 공백을 안 벗겼다.** 실데이터는 `"1723      "`(10자)로 오는데
   `trim()` 없이 `padStart(4)` 해서 24행이 전부 버려졌다("행이 24개가 아니다(0)"). 403 탓에
   **한 번도 실데이터를 못 만나 본 코드**였다.
3. 🔴 **KASI 데이터 자체에 오류가 3건 있다.** 우리 코어(astronomy-engine)와 lunar-javascript(독립
   천체력)가 서로 1분 이내로 일치하고 KASI 만 벗어난다 — 즉 **KASI 가 틀렸다**:

   | 셀 | lunar-javascript(KST) | 우리 코어 | KASI | 성격 |
   |---|---|---|---|---|
   | 2011 대한 | 01-20 19:18 | 01-20 19:19 | **01-21** 19:18 | `locdate` 하루 뒤 (中氣) |
   | 2011 입동 | 11-08 03:34 | 11-08 03:35 | **09:26** | 5h51m (🔴 節 — 월건을 가른다) |
   | 2015 하지 | 06-22 01:37 | 06-22 01:38 | **01:58** | 20분 (中氣) |

   `scripts/verify-solar-term-frame-kasi.mjs` 의 `KASI_KNOWN_ERRATA` 가 이것을 **양방향 fail-closed**
   로 지킨다(적힌 오류가 재현 안 되면 실패 · 목록에 없는 새 이탈도 실패). 節 오류가 있는 해는
   그 해를 **통째로** 지상값에서 뺀다 — 節 하나만 빼면 그 節부터 다음 節까지 한 달이 밴드로 잡혀
   층화 밴드가 69 → 158 분으로 부풀고 슬랙에 묻힌다(실측).

🔴 **재채집이 필요하면**(KASI 가 2029 를 추가하는 등) `KASI_MIN_YEAR`/`KASI_MAX_YEAR` 를 먼저
실측으로 다시 잡고 `--probe` → `--live` 순서로 돌린다. 프로브 연도는 **커버리지 안**이어야 한다.

## ✅ 후속 (2026-08-29) — §4 의 "채집 후 확인할 것" 네 항목을 닫았다

## 1. 🔴 왜 아직 못 했나 — 업스트림이 403 이다

2026-08-28 실측. 프로덕션·스테이징 **양쪽 모두** 같다.

```
POST https://code-destiny.com/api/kasi/calendar
  {"method":"get24DivisionsInfo","params":{"solYear":"1997","numOfRows":"30"}}
    → 200  source="local"  warnings:["… KASI 응답 오류: HTTP 403"]

  {"method":"getLunCalInfo","params":{"solYear":"1997","solMonth":"02","solDay":"10"}}
    → 200  source="kasi"
```

즉 **음양력(`LrsrCldInfoService`)은 정상이고 24절기(`SpcdeInfoService`)만 403** 이다.

🔴 **`source:"local"` 응답을 정답으로 받으면 안 된다.** 그 폴백은 `worker/routes/kasi.js` 의
`computeLocalSolarTerms` 이고 그것이 곧 **우리 코어**다. 그걸로 대조하면 이 가드는 자기가 검증하려는
대상을 자기 자신으로 확인하는 회로가 된다. 기존 `verify-korean-calendar-kasi-samples.mjs` 가
머리말에서 같은 이유로 `source:"local"` 을 거부한다 — 그 규칙을 그대로 따를 것.

### 이 세션이 고친 것 (그리고 그것으로 안 끝날 수도 있는 이유)

`worker/routes/kasi.js` 에서 원인 후보 둘을 고쳤다(같은 브랜치 `fix/kasi-service-base-fallback`).

1. `buildBaseUrlCandidates` 가 `env.KASI_API_BASE_URL` 을 **메서드별 정답 서비스보다 먼저** 시도했다.
   그 값이 `LrsrCldInfoService` 로 고정돼 있으면 24절기 오퍼레이션이 음양력 서비스로 나가고,
   data.go.kr 은 그 조합을 403 으로 돌려준다. → `preferred` 를 앞으로.
2. `fetchKasiUpstream` 이 401/403 에서 **그 자리에서 던져** 남은 base URL 후보를 시도하지 않았다.
   → 그 base 의 키 후보·재시도만 건너뛰고 다음 base 로 넘어가게 했다.

덤으로 회로 카운트를 요청 단위로 바로잡았다(예전에는 base×키 후보마다 세서 403 한 번이
정상 동작하던 음양력 조회까지 10분간 죽였다 — probe 중 프로덕션이 실제로 그 상태였다).

🔴 **이것으로 살아난다고 단정할 수 없다.** 원격에서는 두 원인을 가를 수 없기 때문이다 —
`KASI_API_BASE_URL` 이 실제로 무엇으로 설정돼 있는지는 워커 시크릿이라 밖에서 안 보이고,
"키가 `SpcdeInfoService` 에 활용신청되지 않음" 도 똑같이 403 을 낸다.

## 2. 🔴 갈래가 정해졌다 — **갈래 B**(계정 작업). 2026-08-28 재측정

PR #1220 이 머지되어 스테이징에 배포된 뒤 같은 probe 를 다시 돌렸다.

```
POST https://staging.code-destiny.com/api/kasi/calendar
  {"method":"get24DivisionsInfo","params":{"solYear":"1997","numOfRows":"30"}}
    → 200  source="local"  "KASI 응답 오류: HTTP 403"      ← 그대로다
```

🔴 **새 코드가 배포된 것은 회로 동작으로 확인했다.** 403 요청을 연달아 세 번 보냈을 때 세 번째까지
실제 업스트림 시도(HTTP 403)가 일어났고 그 다음에야 회로가 열렸다. 옛 코드는 base×키 후보마다
실패를 세었으므로 **두 번째 요청에서 이미** 회로가 열렸을 것이다. 즉 #1220 은 살아 있고,
그런데도 403 이다.

⇒ **남은 원인은 코드가 아니다.** data.go.kr 에서 그 서비스키에 **`SpcdeInfoService`(특일 정보)
활용신청**이 안 돼 있는 것이다. `LrsrCldInfoService`(음양력)만 신청돼 있으면 24절기는 계속 403 이다.
🔴 **에이전트가 할 수 없는 계정 작업이다.**

## 3. 그래서 지금 무엇이 들어갔나 — `verify:solar-term-frame-kasi`

채집을 기다리지 않고 **지금 검증 가능한 것**으로 가드를 만들어 CI 에 배선했다(사용자 결정 2026-08-28).

### 두 층

```
verify:solar-term-frame-kasi            ← fast 잡에서 항상 돈다. 네트워크 0.
├─ tier-1  지상값 = 셸의 KASI 검증캐시(1990 12중절)   ← 지금 돈다
└─ tier-2  지상값 = KASI 픽스처(1930~2050)            ← 채집하면 자동으로 켜진다
```

🔴 **skip 이 아니다.** tier-2 픽스처가 없는 상태를
`__tests__/fixtures/korean-calendar/kasi-24divisions.pending.json` 마커로 **커밋해 선언**하게 하고,
마커와 픽스처의 존재를 3방향으로 배타 검사한다(검사 ①-e).

| 픽스처 | 마커 | 판정 |
|---|---|---|
| 없음 | 없음 | 🔴 실패 — 조용한 skip 이 불가능해지는 자리 |
| 없음 | 있음 | 통과(tier-1). 사유·측정일을 CI 출력마다 찍는다 |
| 있음 | 있음 | 🔴 실패 — 낡은 선언이 남았다 |
| 있음 | 없음 | tier-1 + tier-2 |

그리고 픽스처가 없어도 **실제 KASI 지상값 12개로 518,427분을 대조**한다. 지상값이 사라지면 실패한다.

### tier-1 이 실제로 잰 것 (2026-08-28, main 기준)

| 축 | 결과 |
|---|---|
| 절기 순간 (KASI ↔ astronomy-engine) | 12/12 · Δ초 범위 **−35 ~ +55** |
| 표기 (KASI ↔ 코어 표) | 12건 중 **5건이 1분 차** |
| 🔴 월건 프레임 | 대조 518,427분 · 밴드 **5분** · 밴드 밖 불일치 **0** |
| 🔴 세차 프레임 | 입춘 경계 불일치 **0** |
| 🔴 음력 프레임 대조 | 232표본 · 월건 차 **91** · 세차 차 **4** · **미설명 0** |
| 셸 경로 | null 0건 · 세차·월건 코어와 전건 일치 |

🔴 **"절사 가설"은 성립하지 않는다.** Δ초가 음수인 것이 3건이다(입춘 −2 · 입추 −35 · 백로 −31 —
KASI 표기가 정확 시각보다 **뒤**에 있다). 청명 +55 · 입하 +36 · 입동 +42 는 절사로 설명되지만,
둘을 함께 설명하는 규칙은 없다. 성립하는 사실은 **"같은 순간을 1분 미만 차로 가리킨다"** 하나뿐이라
가드의 임계는 부호 없는 60초다(`TERM_INSTANT_TOLERANCE_SEC`).

🔴 **그 1분 차가 월건 판정을 실제로 바꾸는 분이 1990 에 정확히 5분 있다** — 04-05 10:12 ·
05-06 03:35 · 08-08 03:45 · 09-08 06:37 · 11-08 01:23. 세차를 바꾸는 분은 0 이다.
검사 ⑤ 가 그 밴드를 매번 다시 열거하고, **밴드인데 답이 같으면 실패**시킨다.

🔴 **핸드오프 본문의 "45건" 은 재현되지 않았다.** 체크인된 289표본 중 간지가 있는 232건을 실제로
대조하면 **월건 91 · 세차 4**(전부 인접 지지 한 칸)다. 그리고 그 95건은 **전부 설명된다** —
월건차는 직전 節과 직전 초하루의 선후가 차의 부호와 일치하는가로, 세차차는 그 날짜가 설날과 입춘
사이인가로. 잔차 0.

### 지상값을 손으로 적지 않는다

12개 행을 적는 것이 아니라 `_VALIDATED_SOLAR_TERMS_BY_YEAR` 를 **테이블째 발견**한다
(`public/` 미러도 함께 — 갈리면 실패). 같은 것을 셸 런타임에서 다시 꺼내 집합을 대조해
스캐너가 죽어서 0 이 되는 경우를 가른다. 누가 그 표에 2000년치를 넣으면 **자동으로 2000년도 검증**하고,
`GROUND_TRUTH_LOCK` 에 지문이 없으므로 근거와 함께 등록할 때까지 실패한다.

음성 테스트 **12건 전건 확인**(경칩 오타 재발 · 지상값 삭제 · 코어에 맞춘 손질 · 라벨 제거 ·
미러만 손질 · 상수명 리네임 · 세차 경계 이동 · 월지 공식 · 오호둔 회전 · 마커 삭제 · 마커 사유 제거 ·
TZ 핀 제거).

## 4. 활용신청이 승인되면 — 명령 한 번

```bash
# ① 상태 확인 (회로 경고가 뜨면 10분 뒤 다시)
npm run verify:solar-term-frame-kasi -- --probe --endpoint https://staging.code-destiny.com/api/kasi/calendar

# ② source=kasi 를 확인한 뒤 — 🔴 실네트워크 121요청이므로 사용자 승인을 다시 받는다
npm run verify:solar-term-frame-kasi -- --live --endpoint https://staging.code-destiny.com/api/kasi/calendar

# ③ 픽스처 기록 · 마커 삭제까지 --live 가 한다. 이어서

```

채집기가 지키는 것:
- 🔴 `source:"local"` 이 **1건이라도** 나오면 픽스처를 쓰지 않고 중단한다(자기검증 방지).
  지금 상태에서 `--live` 를 돌리면 첫 요청에서 그렇게 멈추는 것을 **실측으로 확인했다.**
- 회로 경고가 보이면 즉시 중단하고 "10분 뒤"를 찍는다.
- 24행이 아니거나 이름/순서가 코어와 다르면 원문을 stderr 로 찍고 중단한다. 조용히 버리지 않는다.
- 121년 전건 채집이 아니면 쓰지 않는다(커버리지가 조용히 좁아지는 것을 막는다).

### 채집 후 반드시 확인할 것 — ✅ 네 항목 전부 닫혔다 (2026-08-29)

원문은 아래 인용으로 남긴다(그날의 계획이었다). **결말이 항목마다 붙어 있다.**

1. ~~🔴 **임계를 분포로 확정한다.**~~ ✅ **#1229 에서 닫혔다.** 표본이 12 → 348(節)건이 되며
   실측 범위가 −52~+72 초로 넓어져 임계를 60 → **90초**로 올렸고, 근거(분 반올림 ±30초를 뺀
   천체력 차 ~42초 = ΔT 모델 차 크기)를 커밋 메시지와 가드 주석에 박았다.
2. ~~🔴 **법정시 버킷**~~ ✅ **검증 불가로 닫는다 — 빈 버킷을 만들지 않았다.**
   KASI `get24DivisionsInfo` 의 실측 커버리지가 **2000~2028** 이라 법정시 구간(1954-03-21 ~
   1961-08-09 의 UTC+8:30)도, 서머타임 구간(1948~51 · 1955~60 · 1987~88)도 **한 해도 안 겹친다.**
   즉 30분·60분 계통 Δ를 관측할 표본 자체가 0 이다. 🔴 그러므로 "우리 표의 전 구간 UTC+9 가
   그 시대에도 맞다" 는 **여전히 미검증**이고, 이 가드는 그것을 검증하지 않는다 — 통과했다고
   해서 그 시대가 맞다는 뜻이 아니다. KASI 가 커버리지를 앞으로 넓히면 그때 다시 연다.
3. ~~🔴 **검사 ⑩ 교차검증**~~ 🟡 **못 했다 — 그리고 못 했다는 사실이 이제 매 실행에 찍힌다.**
   같은 이유다: 셸 검증캐시는 **1990** 한 해뿐이고 KASI 커버리지는 2000~2028 이라 **겹치는 해가 0**
   이다(실측 2026-08-29: 대조행 0건). 🔴 그런데 #1225~#1229 의 검사 ⑩ 은 `if (!entry) continue`
   로 1990 을 건너뛴 뒤 "픽스처와 검증캐시가 같은 절기 시각을 낸다" 를 **초록으로 냈다** — 0행을
   대조하고 통과하는 fail-open 이다(CLAUDE.md 원칙 10). 2026-08-29 에 갈래를 나눠 고쳤다:
   - **⑩-a** 픽스처에 없는 지상값 해는 KASI 커버리지 **밖에서만** 나온다 — 커버리지가 넓어지거나
     픽스처가 좁아지면 즉시 빨개져 재채집을 강제한다(양방향 실측 확인).
   - **⑩-b** 겹치는 해가 있으면 전건 대조, 없으면 그 사실이 커버리지로 설명되는지만 본다.
   - **⑩-c** 겹치는 해가 있는데 대조행이 0 이면 실패(⑪-g 와 같은 계약).
   - 겹침이 0 인 동안은 최종 보고에 🟡 한 줄이 매번 찍힌다.
   🔴 결론: *"검증캐시는 KASI 응답을 그대로 받아 적은 것"* 이라는 `js/core/kasi-calendar-service.js`
   의 주장은 **이 가드가 아직 증명하지 못한 주장**이다. 참이라고 인용하지 말 것.
4. ~~문서~~ ✅ **2026-08-29 에 닫았다.** [korean-calendar-migration-2026-08-27.md](korean-calendar-migration-2026-08-27.md)
   §(B) 의 "45건" 을 **월건 91 · 세차 4** 로 정정하고 403 서술을 결말로 갈았다.
   [ganji-wallclock-parts-migration.md](ganji-wallclock-parts-migration.md) 의 **R4** 는
   PR-2(#1246)가 이미 닫았고, 남아 있던 **TZ 축**을 이번에 닫았다(아래 §4-A).

### 4-A. R4 의 **TZ 축** — "KASI 응답 + 서머타임 구멍" 은 재현되지 않는다 (2026-08-29 실측)

R4 는 `_normalizeTerms` 의 `atLocal` 이 로컬 Date 왕복으로 접힐 수 있다는 위험이었다.
🔴 **R4 자체는 PR-C 가 이미 닫았고 PR-2(#1246)가 확인했다** — 그때 같은 자리에서 더 큰 결함
(셸이 `kst` 를 아예 안 읽어 절입 시각을 전건 자정으로 뭉갠 것)이 나와 검사 ⑪ 이 섰다.
🔴 **그런데 검사 ⑪ 은 러너를 `TZ=UTC` 로 못박은 채 돈다.** 그래서 R4 의 원래 문장인 "브라우저
타임존의 서머타임 구멍에서 접히는가" 는 여전히 안 재고 있었다. 그 축을 이번에 쟀다.

| 존 | 1월/7월 오프셋 | 유도한 구멍 벽시계 | 불일치 |
|---|---|---|---|
| UTC | 0 / 0 | (없음) | 0 |
| Asia/Seoul | +540 / +540 | (없음) | 0 |
| America/New_York | −300 / −240 | 2005-04-03T02:00 | 0 |
| Europe/Dublin | 0 / +60 | 2005-03-27T01:00 | 0 |
| Australia/Lord_Howe | +660 / +630 | 2005-10-30T02:00 | 0 |
| Pacific/Chatham | +825 / +765 | 2005-10-02T02:45 | 0 |

입력은 픽스처의 2005 실제 KASI 행 24개(우측 공백 포함 `kst`)에 **그 존의 구멍 벽시계를 절기
시각으로 밀어 넣은 행**을 더한 것이다. 원인은 `_normalizeTerms` 가 `_partsOf`(`Date.UTC`) →
`_partsToIsoLocal` 만 타고 **로컬 Date 캐리어를 안 만들기** 때문이다(PR-C·PR-E 의 부품 전환).

🔴 **1회 실측으로 끝내지 않았다.** 검사 **⑪-h** 가 그 축을 상시로 잡는다 — 자식 프로세스 하나를
`TZ=America/New_York` 로 띄워 같은 입력을 먹이고 UTC 부모와 결과를 대조한다. 음성 테스트에서
`_partsOf` 를 로컬 Date 왕복으로 되돌리면 **다른 검사 61건이 초록인 채 ⑪-h 만 빨개진다**(실측).

## 5. 실패한 시도 (다시 하지 말 것)

- **`/api/kasi/calendar` 에 `{year,month,day}` 로 POST** — 응답이 그 해의 24절기를 `isoLocal` 까지
  담아 편해 보이지만, 업스트림이 죽으면 `source:"local"` 로 조용히 코어 값을 돌려준다.
  레거시 형태(`{method,params}`)와 마찬가지로 **`source` 를 반드시 볼 것.**
- **`get24DivisionsInfo` 를 여러 해 연속 호출해 403 을 우회하려는 시도** — 첫 403 이 회로를 열어
  뒤 요청이 전부 `"circuit is open"` 이 된다. 위 수정 전에는 그 회로가 음양력까지 막았다.
- **`scripts/verify-korean-calendar-solar-terms.mjs` 를 근거로 삼는 것** — 이름과 달리 그 가드는
  KASI 가 아니라 **lunar-javascript** 와 절기 순간을 대조한다. `worker/routes/kasi.js` 주석의
  "KASI 와 평균 0.211분 차이다(verify:korean-calendar-solar-terms)" 는 그 가드가 실제로 하는 일과
  다르다. 절기의 KASI 대조는 아직 **어디에도 없다** — 그게 이 문서의 이유다.
