## 작업 규칙과 함정

- 🔴 프롬프트 전제 중 저장소와 다른 것(Phase 1 보고서 2절): 앱가=웹가, Android는 Capacitor, 앱 세션은 Bearer + localStorage, 엔드포인트는 `/api/...` 규칙. 프롬프트대로 구현하지 말고 실제 구조에 맞춘다.
- 🔴 프롬프트 Phase 2의 "세션은 HttpOnly 쿠키, localStorage 인증 제거"는 Android 앱 인증 구조 전체를 바꾸는 RED 변경이다. Android가 `https://localhost` 출처에서 Bearer로 동작하기 때문이다(`scripts/app-native-bridge.js:182-205`). 진단에서 iOS만의 방식으로 할지, 공통으로 바꿀지 선택지를 내고 사용자 결정을 받는다. 임의로 구현하지 않는다.
- 🔴 결제 진입 분기는 결제 동결·게이팅 규칙 대상이다. 손대기 전에 paid-gate-auditor로 감사하고, PortOne/Inicis 실행 파일은 바꾸지 않는다(프롬프트 불변 규칙 4). 앱 PortOne 봉인은 이미 있다: `scripts/app-payment-guard.js`, `scripts/verify-app-no-portone.mjs`, `app/_lib/billing-client.ts:2363`의 `isMobileAppRuntime()` 분기.
- 웹 SIWA 콜백은 `response_mode=form_post`(POST)라 기존 OAuth 콜백(`worker/routes/auth.js:1203` 근처, GET)과 다르다. 인증 RED.
- 서비스 워커: 앱 런타임에서는 이미 등록하지 않는다(`js/pwa-lifecycle.js:158`). iOS 판별이 같은 `native()` 경로를 타는지만 확인한다.
- 정적 셸(index.html)을 고치면 `sync:public` 미러 커밋이 필요하다(메모리: static-shell-pitfalls).
- 과금 LLM 호출 금지. 검증은 mock과 `npm run check:fast`.

## 설계 (진단에서 확정할 질문)

1. **iOS 셸 방식**: Capacitor iOS(Android와 같은 플러그인 계약) vs 프롬프트 D안(자체 WKWebView + `WKScriptMessageHandlerWithReply`). 프롬프트의 "C △" 판정은 "Android가 자체 브리지"라는 틀린 전제 위에 있었다. 이 결정이 `platform.ts`의 판별 방식(UA 토큰 vs Capacitor 감지)과 브리지 client 구조를 정한다. 추천과 근거를 보고서에 쓴다.
2. 플랫폼 판별 단일 유틸: 기존 `isMobileAppRuntime()`(`app/_lib/auth-client.ts:146`, `app/_lib/billing-client.ts:2757`)은 둘 다 `js/core/app-context.js` `isApp()`에 위임한다(2026-11-18 진단에서 정정). 이 둘과 `scripts/app-native-bridge.js`의 판별을 어떻게 `android | ios | web`으로 넓힐지. `html[data-platform]` 설정 위치.
3. 결제 진입 분기: ios → StoreKit 경로. PortOne 코드가 iOS에서 로드조차 안 되는지(동적 import) 현재 상태 실측.
4. 가격 표시: 앱에서 웹 가격·비교 문구가 남는 곳 전수 조사.
5. `alert`/`confirm`/`window.open`/파일 업로드 사용처 수(WKWebView UIDelegate 범위 산정).
6. 모달·시트의 `history.pushState` 연동 현황.
7. 입력 필드 font-size 16px 미만 사용처.
8. 웹 SIWA와 계정 연결 정책 초안(같은 검증 이메일이면 연결 제안, 자동 병합 금지; 릴레이 이메일이면 설정의 "기존 계정 연결").
