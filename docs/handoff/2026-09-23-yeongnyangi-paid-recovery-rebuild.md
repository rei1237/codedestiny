# 영양이 결제 상담 보관함 복구 재구현

## 사용자 요구사항

결제가 이미 완료된 사용자가 보관함에서 기존 영양이 상담을 다시 시도했을 때, 최초 생성이 실패했거나 일부 결과만 저장된 상담을 **추가 결제 없이** 끝까지 복구해야 한다. 사용자는 같은 상담의 결과를 계속 이어서 받아야 하며, 이미 생성·저장된 챕터를 다시 생성하거나 중복 과금해서는 안 된다.

초융합 결제는 이번 작업 범위가 아니다. 초융합 보호 로직·상품·결제 코드는 수정하지 않는다.

## 다음 모델에게 가장 중요한 지시

- 현재 워킹 트리나 이전 세션의 복구 후보 구현을 정답으로 사용하지 말 것.
- 기존 코드를 부분 패치하거나 기존 설계의 가정을 이어받지 말고, 요구사항 → 상태 전이 → 저장 계약 → 동시성/idempotency → UI 흐름 순서로 독립적으로 다시 설계할 것.
- 필요한 경우 기존 파일은 통합 지점을 확인하는 용도로만 읽고, 구현은 새 설계가 요구하는 최소 범위로 다시 작성할 것.
- 실제 결제, 실제 LLM, 운영 DB, 운영 사용자 결과에는 접근하지 말 것. mock/fixture 기반으로 검증할 것.
- 결제 정책·가격·이용권/월정석/단건 결제 의미·환불 정책은 변경하지 말 것.

## 반드시 만족해야 할 동작

1. 보관함의 재시도는 새 결제나 새 상담 ID를 만들지 않고 원래 유료 상담의 동일한 request/payment entitlement를 재사용한다.
2. 저장된 결과가 0개인 경우 남은 전체를 생성한다.
3. 일부 챕터가 저장된 경우 저장된 챕터는 그대로 재사용하고, 첫 미생성 챕터부터 이어서 생성한다.
4. 자동 중단·일시적 provider 오류·재시도 가능 상태와, 운영자 확인이 필요한 영구 실패 상태를 구분한다.
5. 이미 전체 결과가 저장된 상담은 provider를 다시 호출하지 않고 저장 결과를 재조회해 완료 처리한다.
6. 여러 번 클릭하거나 요청이 겹쳐도 같은 챕터가 중복 생성·중복 저장·중복 과금되지 않는다.
7. 저장 성공을 확인하기 전에는 완료 상태로 바꾸지 않는다. 완료 판정은 저장된 결과를 다시 읽어 확인한다.
8. 환불·취소·권한 없음 상태는 복구하지 않고 기존 안전한 차단/안내를 유지한다.
9. 재시도 이후에도 실패하면 사용자가 다음 행동을 알 수 있는 오류와 재시도 가능 여부를 보여준다.
10. UI의 보관함 재시도 버튼은 실제 서버 복구 계약과 같은 request ID를 사용한다. 새 결제 CTA로 우회시키지 않는다.

## 설계 전에 확정할 질문

- 유료 상담의 정본 상태와 저장된 챕터의 정본은 무엇인가?
- `paid`, `generating`, `completed`, `refunded`, `review required` 등의 상태 전이와 허용된 재시도 전이는 무엇인가?
- 큐 재개와 사용자의 보관함 재시도가 동시에 들어올 때 어떤 원자적 claim/idempotency 키를 사용할 것인가?
- 챕터 저장·완료 처리·실패 기록을 어떤 순서로 해야 중간 장애에서 재개 가능한가?
- 이미 저장된 결과를 다시 읽는 검증은 어디에서 수행하며, 완료 상태와 UI 응답 모두가 그 검증을 사용하는가?
- 재시도 횟수/비용 상한을 어떻게 정하고, 사용자 재시도와 자동 복구를 감사 로그로 구분할 것인가?

## 검증 완료 기준

- repository/service/queue/route/UI의 mock 테스트로 빈 결과, 부분 결과, 자동 중단, review 상태, 동시 재시도, 완료 재조회, 환불 차단을 각각 검증한다.
- “결제 1회 + 생성 실패 → 보관함 재시도 → 추가 결제 0회 + 미생성분만 저장” 시나리오를 브라우저 fixture로 검증한다.
- 저장된 챕터가 재생성되지 않았고 provider 호출 수가 미생성 챕터 수 이하임을 assertion으로 남긴다.
- `npm run check:fast`와 관련 targeted 테스트를 실행한다. 실패한 명령은 숨기지 말고 원인과 함께 기록한다.
- 구현을 확정하기 전까지 커밋·푸시·배포하지 않는다. 완료 후에도 별도 승인 없는 실결제/실LLM/운영 DB 검증은 하지 않는다.
