## 작업 규칙과 함정

- 🔴 새 워크플로는 **게이트가 아니다**. `CI required` 집계에 넣지 않고, 다른 필수 검사에도 엮지 않는다(메모리 "CI gate scope": 메인 CI 외 게이트 추가 금지). 트리거는 `workflow_dispatch`와, iOS 경로만 건드린 main push(`paths:` 필터)로 한정한다.
- 🔴 워크플로 추가 전에 워크플로 목록을 검사하는 가드가 있는지 본다: `git grep -n "\.github/workflows" -- scripts __tests__`. 예를 들어 `pages-config-guard`나 `verify-*`에 워크플로 인벤토리가 있으면 그 목록도 갱신한다. 새 워크플로에서 시크릿은 쓰지 않는다. `permissions: contents: read`, `timeout-minutes`, `concurrency`를 넣는다.
- 수정 금지: `package-lock.json`, `apps/mobile/ios/App/CapApp-SPM/Package.swift`(CLI 관리). 러너 위에서 `npx cap sync ios`가 다시 생성하는 파일은 커밋하지 않는다.
- 앱 의존성 설치: `npm install --prefix apps/mobile --no-package-lock --ignore-scripts`(`docs/android-release.md:109`). `@capacitor/ios` 8.4.3은 `apps/mobile/package.json`에 이미 있다.
- 웹 번들은 `npm run build:mobile:app`이 `dist/`를 만든다(`package.json`의 `mobile:ios:sync`). 이 명령이 러너에서 오래 걸리거나 비밀값을 요구하면, 먼저 무엇을 하는지 읽고 최소 경로를 고른다. 비밀값이 필요하면 멈추고 보고한다.
- Capacitor 8.4.3 iOS 사실(원본 소스로 확인함)
  - `CAPBridgeViewController.bridge`는 `CAPBridgeProtocol`이다. `webViewDelegationHandler`가 보이지 않아 `webView.uiDelegate as? WebViewDelegationHandler`로 얻는다.
  - `capacitorDidLoad()`는 `loadView` 안에서 `prepareWebView` 뒤에 호출된다.
  - 외부 최상위 이동은 기본적으로 Safari 앱으로 나간다. `window.open`은 기본적으로 `UIApplication.open`이다(우리 프록시가 대체).
- Bash 도구는 백슬래시를 한 겹 벗긴다. 정규식이 든 node 스크립트는 파일로 써서 실행한다. CRLF 파일(pbxproj 등)은 node로 줄바꿈을 보존해 패치한다.
- 컴파일 오류가 나면 덧대지 말고 원인을 고친다. 셸 동작을 바꾸는 큰 수정이 필요하면 `1a3dcac37`을 revert하고 다시 설계하는 것도 선택지다. Android에는 영향이 없다.
- 과금 LLM 금지. 시뮬레이터 실행 중 웹이 유료 생성 API를 부르지 않게, 홈·정적 화면만 연다.

- (단계 1 실측) `ios-shell-build`는 캐시 적중 때 약 24분, 캐시 없으면 약 50~56분이다. 대부분 웹 번들(`build:mobile:app`)이고 xcodebuild는 약 2분이다. 앱 이미지 캐시 키는 `mobile-images-v2-<os>-<arch>-<run_id>`이고 restore-keys로 직전 캐시를 물려받는다. 같은 ref 새 실행은 진행 중 실행을 취소한다(concurrency). 그래서 push 트리거 실행 중에 dispatch 하지 않는다.
- (단계 1 실측) Capacitor 콘솔은 버퍼링 때문에 `SIMCTL_CHILD_NSUnbufferedIO=YES` 없이는 비어 나온다. 셀프 테스트 결과는 artifact `selftest.txt`(`[cd-selftest]` JSON)에 있다.
- 🔴 (단계 1 발견, 범위 밖 후속) 홈 `<html>`에 `data-platform`·`data-runtime-target`이 없다. 브리지는 돌았지만(`__CODE_DESTINY_RUNTIME_TARGET=mobile-app`) 홈에서 React 하이드레이션 오류 #418이 나고, 재렌더가 속성을 지운 것으로 추정한다. Phase 4에서 `appUrlOpen` 경로를 볼 때 이 속성에 기대지 않는다. 고치는 일은 별도 작업으로 보고만 했다.
- (단계 1 발견) 시뮬레이터 `openurl com.codedestiny.app://...`는 `Open in "꿀꿀운세"?` 확인창에서 멈춘다. 스킴 등록은 확인되지만 `appUrlOpen` 수신은 이 방식으로 확인할 수 없다. Phase 4 유니버설 링크 수신 확인은 XCUITest(확인창 탭)나 셀프 테스트 쪽 로그 경로를 검토한다. https 유니버설 링크는 AASA·서명이 없으면 시뮬레이터에서도 앱으로 오지 않는다.

## 설계

### 단계 1 워크플로 `.github/workflows/ios-shell-build.yml` (안)

- runs-on: Xcode 26이 있는 macOS 이미지. 현재 GitHub 러너 이미지 문서로 레이블을 확인한다(`macos-26` 또는 `macos-15`에서 `xcode-select`로 Xcode 26 선택).
- 순서
  1. checkout → setup-node(`.nvmrc` 또는 `package.json` engines) → 루트 `npm ci`
  2. `npm run build:mobile:app`
  3. 앱 의존성 설치
  4. `cd apps/mobile && npx cap sync ios`
  5. `xcodebuild -project apps/mobile/ios/App/App.xcodeproj -scheme App -configuration Debug -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build`. SPM 해석 포함. 로그는 `xcbeautify`가 있으면 쓰고 원문도 artifact로 남긴다.
  6. 시뮬레이터 부팅(iPhone 최신 기종) → `simctl install` → `simctl launch com.codedestiny.app` → 약 20초 대기 → `simctl io booted screenshot`
  7. `simctl spawn booted log show --last 2m --predicate 'process == "App"'`에서 Capacitor 콘솔(`⚡️`)과 오류 줄을 추출해 artifact로 남긴다
  8. (선택) `simctl openurl booted com.codedestiny.app://auth?...`로 커스텀 스킴 복귀 동작 확인
- Mac 체크리스트 중 자동화가 어려운 항목(`getInfo()`, UA, `data-platform`)은 **Debug 빌드 전용** 자가 점검으로 대체할 수 있다. 실행 인자 `-cdSelfTest`가 있으면 첫 로드 뒤 `evaluateJavaScript`로 `navigator.userAgent`, `document.documentElement.dataset.platform`, `__cdNativeBridgeClient.getInfo()`를 읽어 `NSLog("[cd-selftest] ...")`로 찍는다. `#if DEBUG`로 감싸 Release에는 들어가지 않게 한다. 넣을지는 단계 1에서 판단하고, 넣으면 보고서에 적는다.
- 판정: 빌드 성공, 앱 프로세스 생존(20초 뒤 `simctl spawn booted launchctl list` 또는 로그), 스크린샷이 흰 화면이 아님(`visual-checker` 에이전트로 판정. 이미지를 메인 세션에서 직접 Read하지 않는다).

### 단계 3 Phase 4 메모(진단 출발점, 실측 2026-11-19)

- 저장소에 `.well-known` 추적 파일이 **0개**다(`git ls-files | Select-String well-known`).
- Android는 App Links가 없고 커스텀 스킴 `com.codedestiny.app://auth`만 있다(`apps/mobile/android/app/src/main/AndroidManifest.xml:38-39`). 프롬프트의 "Android App Links와 같은 경로 체계"는 새로 정해야 한다. Android App Links 추가는 이번 범위 밖이다. 표에 "후속"으로만 적는다.
- AASA의 `appIDs`에는 `<TeamID>.com.codedestiny.app`이 필요하다. Team ID가 없으니, Team ID가 있어야만 파일이 나오는 구조를 추천안으로 검토한다. 예: 빌드 시 `APPLE_TEAM_ID` 환경값으로 생성하고, 없으면 파일을 내지 않게 한다. 임의 값이나 자리표시자가 든 AASA를 배포하지 않는다.
- 제공 경로: `/api/*`만 독립 워커이고 나머지는 Pages 정적 파일이다(메모리 "워커·Cloudflare"). Pages `_headers`로 `Content-Type: application/json`을 지정하고, 워커와 Pages 리다이렉트(`_redirects`, `/index.html` 301 등)가 `/.well-known/`을 가로채지 않는지 확인한다. 🔴 RED(라우팅·배포): 위험·검증·롤백을 먼저 보고한 뒤 진행한다.
- iOS 쪽
  - `App.entitlements`(associated-domains `applinks:code-destiny.com`, `applinks:www.code-destiny.com`, `webcredentials:`)와 pbxproj의 `CODE_SIGN_ENTITLEMENTS`가 필요하다.
  - 유니버설 링크 수신은 `AppDelegate`의 `ApplicationDelegateProxy` → `@capacitor/app` `appUrlOpen`이다.
  - 웹 `scripts/app-native-bridge.js`의 `appUrlOpen` 처리가 https 링크를 앱 내부 경로로 보내는지 확인한다. 현재는 auth 복귀 위주다.
  - 콜드·웜 스타트와 로그인 필요 경로 복귀를 다룬다.
- SEO 동반 점검: `.well-known` 파일은 색인 대상이 아니다. sitemap·robots 영향 없음을 기록한다.
