## 초융합 모바일·계정별 복구 (2026-09-15)

- 서버에서 소유 미완료 기록을 찾고 최근 목록에도 미완료 상담을 포함한다. 로컬 입력 없이 재로그인/재진입해도 같은 요청을 이어가며, 목록에서 연 부분 결과도 동일하게 재개한다. 숨김/오프라인 중 새 회차를 시작하지 않고 복귀 시 같은 요청을 잇는다. 일시 장애 재개는 클라이언트 네 번/서버 기존 묶음 한도 내에서 제한한다.

- 최종 본문은 delivery_pending으로 저장·재조회한 뒤 기존 네 결제/환불 원장 검사와 completed 저장·재조회를 거친다. 새 호출 전과 소유 결과 조회에서도 취소·환불을 거부한다. 완료 응답 유실 뒤 POST 재시도는 저장된 완료본을 직접 반환하며 LLM/결제 증빙 조회를 다시 실행하지 않는다. 기존 완료본의 새 분량 재검사는 없다.
- 실제 라우트→생성 진입점→저장 helper mock 24개(결제 종류별 partial/same-stage/완료 재사용, 저장 throw/null/readback, 최종 저장 null/응답 유실, 취소 직전/후)와 기존/lease mock을 합쳐 90개 통과. 외부 fetch는 차단했다. 결제 검증기는 read-only mock이므로 실 세 결제 흐름 증명은 아니다.

- 다음: 초융합 순수 본문 floor/계정별 저장/백그라운드 복귀/모바일 동작, 나머지 상품 목록 대조와 짧은 LLM 기능을 이어간다. 모든 상품 완료는 아니며 실 LLM·실결제·운영 DB·실기기·배포는 미검증이다.

## 초융합 최초 근거 보존과 같은 단계 재개 (2026-09-15)

- 최초 입력과 여섯 체계 계산 결과를 사용자+원래 requestId에 묶인 비공개 generationSnapshot으로 생성 전에 저장·재조회한다. 재시도 입력이 달라도 보존된 입력/계산 시점을 재사용한다. 목록에는 snapshot을 노출하지 않으며 소유자 부분 결과 조회에서만 재개 입력을 반환한다.
- 묶음 호출은 실행 전에 서버에서 누적 예약하고 그룹별 세 번으로 제한한다. 예약 재조회 실패가 NaN 비교로 통과하던 경로를 mock으로 발견해 차단했다. 저장·예약 장애는 RESULT_STORAGE_UNAVAILABLE 503이며 불확실한 호출 수를 초기화하지 않는다.
- 미완료 묶음은 202/nextStage로 같은 단계를 이어가고 정상 묶음을 재사용한다. 화면은 원래 요청으로 최대 12회차까지 이어가며 완료 전 증빙을 지우지 않는다. 로컬 입력이 없을 때 소유 서버 snapshot으로 복구하고 재개 버튼이 결제 폼을 다시 제출하던 경로를 제거했다. 기존 30,000~60,000자 목표는 유지한다.
- 검증: 실제 생성 진입점/저장 helper/스트림 라우트와 결제 증빙 mock 86개, UI 로케일·동일 단계 재개 22개, 초융합 정적 UI 25개 통과. typecheck, Mongo query 912/위반 0, resilience 902, check:fast -- --plan 및 선택된 paid gate 초융합 네 항목 통과. lint 오류 0/기존 경고 4. 외부 fetch·실 LLM·실결제·운영 DB 호출 없음.
- 나침반 보정 a04b1d11717f32eab31c91e46b36a4c8e499c614의 main PR CI 34863146780 success 확인. 이 초융합 작업 단위는 커밋/push 후 CI를 확인한다.
- 남은 한계: 초융합 만료 잠금의 CAS 토큰, 완료 직전 취소·환불 재확인, 20,000자 순수 본문 floor, 계정 전환과 숨김/오프라인 자동 재개, 실제 모바일 화면 검증은 이어서 수행한다. 전체 LLM 완료가 아니다. 실 LLM 품질·실기기 결제 복귀·운영 DB·배포는 미검증이다.

## 이어받을 검증 방식

1. registry의 canonical 키를 상품별 행으로 확장하고 활성 판매/과거 구매/정적 해금을 구분한다. 위 표는 기능군 조사이며 모든 SKU의 E2E 완료표가 아니다.
2. 서비스 함수의 LLM·DB·결제 호출을 mock으로 주입한다. 저장 throw/null, 응답 유실, 동일 키 동시 요청, 취소·환불, 언어 오류, 잘린 JSON, 없는 근거, 상충 판정 뒤집기 fixture를 각각 분리한다.
3. 실제 API와 화면으로 원래 inputHash/requestId/결제 증빙을 유지한 재로그인·새로고침을 검사한다. 서버 저장 성공+필수 부분의 품질 통과만 완료. partial은 재열람 가능해야 한다.
4. `npm run check:fast -- --plan`으로 선택 검사를 보고 관련 검사 후 commit/push/main CI 확인. 기존 `verify:ai-consultation-flows`와 Paid Flow Gates 성공은 위 저장/의미 품질 시나리오의 전수 증명이 아니다.

실 LLM 문장 품질, 실 PG, 운영 주문 복구는 별도 승인 및 결과로 남긴다. 현재 감사에서는 외부 호출 0건이다.
